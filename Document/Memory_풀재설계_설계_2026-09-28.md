## 1. 목표

1. **고갈이 없다.** 크기 클래스가 비면 그 클래스에 페이지를 하나 더 붙인다. `nullptr`을 돌려주는 경로가 사라진다(현황분석 P0-1, 0-2 재현 (a)).
2. **1MB 한도가 없다.** 최대 클래스를 넘는 요청은 풀 API 안의 대형 블록 경로가 맡는다(0-2 재현 (b), `Graphics_TODO.md` 5-23).
3. **모든 블록은 청크 안에 있다.** 헤더 16바이트·`OwnerChunkID`로 소유 청크를 찾는 규칙이 그대로 성립한다. 대형 블록은 표식이 붙은 한 종류만 예외이고, 풀 API 밖에서는 구분할 필요가 없다.
4. **상주 메모리를 실측에 맞춘다.** 스레드마다 100.69MB(30,768블록)를 미리 잡는 대신 페이지를 필요할 때 만든다. 기준선의 메인 스레드 정상 상태는 약 1MB, 워커는 0.5MB 안팎이다.
5. **스레드 간 해제가 안전하다.** 소유 스레드만 자기 청크의 목록을 만지고, 다른 스레드의 반납은 lock-free 스택으로 받는다(P0-5). `shared_lock`을 풀고 쓰던 iterator(P0-6)와 `hash<thread::id>` 충돌도 없앤다.
6. **통계가 O(1)이다.** 클래스별 live·피크·페이지 수·성장 횟수를 카운터로 들고, 청크 전체를 걷는 `GetStatInfo`를 없앤다(P1-14). 위젯이 클래스별 표를 보인다.
7. **`HAllocator`가 완성된다.** `operator==`, `is_always_equal`, 정렬 인자(P1-12).

**바꾸지 않는 것.** 풀 바깥의 API 모양(`HMemoryPool::Allocate/Deallocate`, `GetMemoryPool()`, `GetMemoryHeader()`, `HAllocator<T>`, `GMemoryGlobalSystem::Allocate<T>`/`Wrap`), 헤더 16바이트 레이아웃, GC·등록 테이블(`AllocatedMemoryBlocks`)은 그대로다(Phase 4에서 따로 다룬다). 컨테이너 사용 코드는 한 줄도 바뀌지 않는다.

## 3. 새 구조

### 3-1. 상수

| 이름 | 값 | 비고 |
|---|---|---|
| `kHeaderSize` | 16 | `HMemoryHeader` 그대로 |
| `kMinClass` | 8 B | 빈 블록 안에 next 포인터(8B)를 두므로 4B 클래스는 없앤다. 4B 요청은 8B 블록(기준선 4B 피크 3개) |
| `kMaxClass` | **결정 2** (64KB 권장 / 1MB) | 이보다 큰 요청은 대형 블록 경로 |
| `kPageBytes` | **결정 1** (64KB 권장) | 페이지 목표 크기. 블록 수 = `clamp(kPageBytes / stride, 2, 4096)` |
| `kMaxChunks` | 256 | 청크 테이블 고정 크기(하드웨어 스레드 28 + 여유). 넘으면 Critical |
| `kLargeOwnerID` | `UINT64_MAX` | 대형 블록 헤더의 `OwnerChunkID` 표식 |
| `kLargeHeaderSize` | 32 | 대형 블록 헤더(뒤 16B가 `HMemoryHeader`와 같은 자리) |

### 3-2. 헤더

`HMemoryHeader`(16B: `EMemorySize MemorySize`, `EMemoryState State`, `uint64 OwnerChunkID`)는 위치·크기·필드가 그대로다. `GetMemoryHeader(ptr) = ptr - 16`도 그대로. 대형 블록은 그 앞에 16B를 더 둔다.

```
풀 블록:        [HMemoryHeader 16B][payload = 클래스 크기]           OwnerChunkID = 청크 인덱스
대형 블록:  [Raw 8B][Size 8B][HMemoryHeader 16B][payload = 요청 크기]  OwnerChunkID = kLargeOwnerID, MemorySize = Unknown
                                ↑ ptr-16 은 두 종류 모두 HMemoryHeader
```

`Deallocate(ptr)`는 `ptr-16`을 읽어 `OwnerChunkID`가 표식이면 대형 경로, 아니면 청크 테이블 `[OwnerChunkID]`로 간다. 표식 검사 한 번이 두 종류를 가르는 전부다.

### 3-3. 크기 클래스와 페이지

메인 스레드 정상 상태 = 페이지 16개 ≈ **1.0 MB**(지금 100.69 MB). 워커(에셋 로드)는 8·16·64·128·256·512 B·1 KB 각 1페이지 ≈ 0.4 MB, 1 MB급 버퍼 4개는 결정 2에 따라 대형 경로(로드 뒤 해제) 또는 2블록 페이지 2개.

페이지는 **lazy**로 만든다. 청크 생성 때 아무것도 예약하지 않고 클래스의 첫 요청에서 첫 페이지를 만든다(첫 페이지는 성장으로 세지 않는다).

### 3-4. 청크 (스레드마다 하나)

```cpp
struct HSizeClass                       // 소유 스레드만 만진다 (통계 필드는 atomic relaxed 로 다른 스레드가 읽기만)
{
	uint32 BlockSize;                   // 8 .. kMaxClass
	uint32 Stride;                      // BlockSize + 16
	uint32 BlocksPerPage;
	void*  FreeHead = nullptr;          // intrusive 빈 목록 (블록 payload 첫 8B = next)
	std::vector<void*> Pages;           // 페이지 시작 주소. 풀 자기 자신을 쓸 수 없으니 std::vector
	std::atomic<uint32> Live = 0;       // 통계
	std::atomic<uint32> Peak = 0;
	std::atomic<uint32> Total = 0;      // 페이지 수 × BlocksPerPage
	std::atomic<uint32> Growths = 0;    // 첫 페이지 이후 추가된 페이지 수
	std::atomic<uint64> AllocCount = 0; // 누적 (델타 감지·리플레이 대조용)
};

class HMemoryChunk
{
	uint64          Index;              // 청크 테이블 인덱스 = 헤더 OwnerChunkID
	std::thread::id OwnerThread;
	HSizeClass      Classes[kClassCount];           // 8B..kMaxClass, 인덱스 = log2(size) - 3
	std::atomic<void*>  RemoteFreeHead = nullptr;   // 타 스레드 반납 스택 (lock-free push / 소유자 pop-all)
	std::atomic<uint32> RemoteFreePending = 0;      // 통계: 아직 회수 안 된 원격 반납
	std::atomic<uint64> RemoteFreeTotal   = 0;      // 통계: 누적 (지금의 Dismatch 경고를 대신함)
	std::atomic<uint64> CommittedBytes    = 0;      // 페이지 합계
};
```

### 3-5. 풀

```cpp
class HMemoryPool
{
	std::atomic<HMemoryChunk*> Chunks[kMaxChunks];  // 인덱스 = OwnerChunkID. 읽기는 락 없음
	std::atomic<uint32>        ChunkCount;
	std::mutex                 CreateMutex;         // 청크 생성 때만
	std::unordered_map<std::thread::id, uint32> ChunkIndexByThread;   // CreateMutex 아래에서만
	// 대형 블록 통계 (풀 전체)
	std::atomic<uint64> LargeCount, LargeBytes, LargePeakBytes, LargeTotalCount;
};

// TLS 캐시. Core 는 정적 라이브러리라 DLL 마다 사본이 있지만, 각 사본이 같은 풀 객체에서 같은 청크 포인터를 얻으므로 문제없다.
thread_local struct { HMemoryPool* Pool; HMemoryChunk* Chunk; } tlsChunk;

HMemoryChunk& HMemoryPool::thisThreadChunk()
{
	if (tlsChunk.Pool == this && tlsChunk.Chunk != nullptr) return *tlsChunk.Chunk;     // 실제 코드는 중괄호 규칙 준수
	lock_guard lock(CreateMutex);
	auto iter = ChunkIndexByThread.find(std::this_thread::get_id());
	uint32 index = (iter != end) ? iter->second : createChunk();   // ChunkCount >= kMaxChunks 이면 Critical 로그 + 중단
	tlsChunk = { this, Chunks[index] };
	return *Chunks[index];
}
```

키가 `std::thread::id` 자체이므로 해시 충돌은 map 이 비교로 해결한다. 헤더에 들어가는 `OwnerChunkID`는 순번 인덱스라 `Deallocate`가 해시 없이 배열 한 번으로 청크를 찾는다.

### 3-6. 할당

```cpp
void* HMemoryPool::Allocate(uint64 size, uint64 alignment = 16)
{
	if (size > kMaxClass || alignment > 16) return allocateLarge(size, alignment);   // §3-9, §3-10

	HMemoryChunk& chunk = thisThreadChunk();
	uint32 idx = classIndex(size);                    // 올림 2의 제곱 (uint64, _BitScanReverse64), 최소 8B → log2 - 3
	HSizeClass& cls = chunk.Classes[idx];

	if (cls.FreeHead == nullptr)
	{
		drainRemoteFrees(chunk);                      // §3-7. 원격 반납을 클래스 목록에 되돌린다
		if (cls.FreeHead == nullptr)
		{
			if (growClass(chunk, cls) == false)       // §3-8. 페이지 추가. 실패는 시스템 힙 실패뿐
			{
				fatal("memory pool: page allocation failed", size, idx);   // Critical 로그 + 중단 (nullptr 을 돌려주지 않는다)
			}
		}
	}

	void* block = cls.FreeHead;
	cls.FreeHead = nextOf(block);
	HMemoryHeader* header = GetMemoryHeader(block);   // MemorySize / OwnerChunkID 는 페이지 생성 때 써 둔 값
	header->MemeoryState = EMemoryState::Allocated;
	uint32 live = ++cls.Live;  if (live > cls.Peak) cls.Peak = live;  ++cls.AllocCount;
	debugFillAlloc(block, cls.BlockSize);             // §3-12 (디버그 빌드)
	return block;
}
```

정상 경로에 락·map 조회·CRT 호출·로그가 없다. 지금은 `shared_lock` + `unordered_map::find` + `std::map::find` + deque pop + (트레이스 시) 로그 두 줄이 붙는다.

`AlignPowerOfTwo`는 `1 << Log2()`가 `int` 시프트라 이 파일 안에 `uint64` 전용 `roundUpPow2`를 따로 둔다.

### 3-7. 해제

```cpp
void HMemoryPool::Deallocate(void* ptr)
{
	if (ptr == nullptr) return;
	HMemoryHeader* header = GetMemoryHeader(ptr);
	if (header->OwnerChunkID == kLargeOwnerID) return deallocateLarge(ptr);              // §3-9

	check(header->MemeoryState == EMemoryState::Allocated, "double free or foreign pointer");   // 디버그 assert, 릴리스 Critical 로그
	header->MemeoryState = EMemoryState::None;

	HMemoryChunk& owner = *Chunks[header->OwnerChunkID];
	if (&owner == tlsChunk.Chunk)                       // 소유 스레드: 자기 목록에 되돌림
	{
		HSizeClass& cls = owner.Classes[classIndex(header->MemorySize)];
		debugFillFree(ptr, cls.BlockSize);
		pushFree(cls, ptr);  --cls.Live;
	}
	else                                                // 타 스레드: 소유 청크의 원격 스택에 lock-free push
	{
		void* head = owner.RemoteFreeHead.load();
		do { nextOf(ptr) = head; } while (!owner.RemoteFreeHead.compare_exchange_weak(head, ptr));
		++owner.RemoteFreePending;  ++owner.RemoteFreeTotal;
	}
}

void HMemoryPool::drainRemoteFrees(HMemoryChunk& chunk)      // 소유 스레드만 호출
{
	void* list = chunk.RemoteFreeHead.exchange(nullptr);     // 한 번에 전부 가져온다 (단일 소비자라 ABA 없음)
	for (; list != nullptr; list = next) { next = nextOf(list); pushFree(classOf(list), list); --Live; --RemoteFreePending; }
}
```

- 원격 반납은 소유 스레드의 다음 `Allocate`(빈 목록일 때) 또는 `RemoteFreePending`이 임계(예: 256)를 넘을 때 회수한다. 소유 스레드가 영원히 할당하지 않으면 그 블록은 그 청크 안에 묶여 있지만 새지는 않는다(종료 때 페이지 통째로 해제).
- 지금의 `Dismatch` Warning 로그(실행당 55줄)는 사라지고 `RemoteFreeTotal` 카운터가 대신한다.
- 소유 스레드 판정은 `std::this_thread::get_id()`가 아니라 TLS 캐시의 청크 포인터 비교라 비용이 없다.

### 3-8. 성장

```cpp
bool HMemoryPool::growClass(HMemoryChunk& chunk, HSizeClass& cls)
{
	uint64 pageBytes = (uint64)cls.Stride * cls.BlocksPerPage;
	void* page = malloc(pageBytes);                       // 16B 정렬 보장(x64 CRT)
	if (page == nullptr) return false;
	for (uint32 i = 0; i < cls.BlocksPerPage; ++i)        // 헤더 초기화 + 빈 목록에 잇기 (역순으로 이어 주소 오름차순 배포)
	{
		HMemoryHeader* h = (HMemoryHeader*)((char*)page + i * cls.Stride);
		h->MemorySize = (EMemorySize)cls.BlockSize;  h->MemeoryState = None;  h->OwnerChunkID = chunk.Index;
		pushFree(cls, (char*)h + 16);
	}
	cls.Pages.push_back(page);  cls.Total += cls.BlocksPerPage;  chunk.CommittedBytes += pageBytes;
	if (cls.Pages.size() > 1) { ++cls.Growths;  logGrowth(chunk, cls); }        // 첫 페이지는 성장이 아니다
	return true;
}
```

**성장 로그(결정 3).** 권장: 페이지 추가마다 **Info** 한 줄(`[Memory] chunk 0 class 32 B grew to 2 pages (2,730 blocks, committed 1.3 MB)`)과, 청크 `CommittedBytes`가 16·32·64·128 MB 문턱을 처음 넘을 때 **Warning** 한 줄. 이번 PSO 누수(프레임당 32B 3개)는 약 455프레임마다 Info 한 줄, 이후 문턱 Warning으로 드러나고, 자동 감지는 Phase 6-1(프레임별 델타)이 맡는다. 대안: 첫 페이지 이후 모든 성장을 Warning으로(128 B·256 B는 정상 상태에서도 2~3페이지라 매 실행 3줄이 경고로 찍힌다).

로그 호출은 재진입 가드 아래에서만 한다: `thread_local bool s_inPoolLog`가 참이면 로그를 건너뛴다. 로깅이 풀을 쓰게 되는 날에도 재귀하지 않는다.

### 3-9. 대형 블록 (결정 2)

```cpp
void* HMemoryPool::allocateLarge(uint64 size, uint64 alignment)
{
	uint64 align = max(alignment, 16);
	char* raw = (char*)malloc(size + kLargeHeaderSize + (align - 1));
	if (raw == nullptr) fatal(...);
	char* payload = alignUp(raw + kLargeHeaderSize, align);
	HLargeHeader* lh = (HLargeHeader*)(payload - kLargeHeaderSize);      // { void* Raw; uint64 Size; HMemoryHeader Header; }
	lh->Raw = raw;  lh->Size = size;
	lh->Header = { EMemorySize::Unknown, EMemoryState::Allocated, kLargeOwnerID };
	LargeBytes += size;  ++LargeCount;  ++LargeTotalCount;  (peak 갱신)
	return payload;
}
void HMemoryPool::deallocateLarge(void* ptr) { HLargeHeader* lh = (HLargeHeader*)((char*)ptr - kLargeHeaderSize);  LargeBytes -= lh->Size;  --LargeCount;  free(lh->Raw); }
```

- 이 경로는 **풀 API 안**에 있다. 호출자(`HAllocator`, `Allocate<T>`)는 모른다. 표식 검사는 `Deallocate` 첫 줄 한 번.
- 로그는 없다(1080p 리드백처럼 매 프레임 올 수 있다). 카운터(개수·바이트·피크·누적)가 위젯에 나온다.
- 지금 `std::vector`로 우회한 12곳(`HTexturePixels::Data`, DevScene RGBA 버퍼, `JGTexture` 압축 버퍼 등)은 이 경로가 들어오면 `HList`로 되돌릴 수 있다(2-6 뒤, 별도 항목).

**결정 2 — 대형 블록 기준.**
- **(B) 64KB 초과 → 대형 경로 (권장).** 클래스는 8B~64KB 14개. 64KB 이상 요청은 기준선에서 에셋 로드 때만 나온다(1MB×6, 512KB×2, 256KB×2 누적). 2의 제곱 라운딩(최대 50% 낭비)과 2블록 페이지가 사라지고, 큰 버퍼는 정확한 크기로 잡힌다.
- **(A) 1MB 초과 → 대형 경로.** 지금 클래스 표와 가장 비슷하다(18개). 128KB~1MB 클래스는 2블록 페이지(262KB~2MB)라 첫 요청에 두 배를 잡는다. "청크 안" 원칙에 더 가깝다.
- (C) 대형 경로 없이 Critical + 중단. `std::vector` 우회 유지. 권하지 않는다.

### 3-10. 정렬

- 페이지 시작은 `malloc` 16B 정렬. stride가 8B 클래스는 24(8의 배수), 16B 이상은 16의 배수 → payload 정렬은 8B 클래스 8, 그 위는 16. 지금은 개수 표에 기대던 것을 stride 규칙으로 보장한다.
- `alignment > 16` 요청(`alignas(32)` 등)은 크기와 무관하게 대형 경로로 보내 `alignUp`으로 맞춘다. 드문 경우라 클래스마다 정렬 변형을 두지 않는다.
- `HAllocator<T>::allocate`는 `Allocate(count * sizeof(T), alignof(T))`를 부른다. `GMemoryGlobalSystem::Allocate<T>`도 `alignof(T)`를 넘긴다.

### 3-11. 통계와 위젯 (2-2)

`HMemoryChunkStatInfo`는 위젯이 쓰는 `ChunkID`, `TotalMemorySize`(= CommittedBytes), `AllocatedMemorySize`(= Σ Live × BlockSize), `HeaderMemorySize`(= Σ Total × 16)를 유지하고, 블록 단위 벡터(`AllocatedMemories`/`EmptyMemories`)를 없앤다. 대신 `Classes[]{BlockSize, BlocksPerPage, Pages, Total, Live, Peak, Growths, AllocCount}`, `RemoteFreePending/Total`, `OwnerThreadID`를 넣고, `HMemoryPoolStatInfo`에 `LargeCount/Bytes/PeakBytes/TotalCount`, `ChunkCount`를 넣는다. `GetStatInfo`는 카운터를 relaxed로 읽기만 한다(다른 스레드 청크 값은 한 프레임 늦을 수 있다. 통계 용도라 허용).

위젯(`MemoryStatistics.cpp`): 루프 안 `[0]`을 `ChunkStatInfo`로. 스레드별 막대(커밋 vs live) 아래에 클래스별 표(크기 · live/total · 페이지 · 성장 · 사용률), 원격 반납 대기 수, 대형 블록 행. 사용률 90% 이상(다음 할당이 성장을 일으킴)과 성장 횟수 > 0 을 강조.

### 3-12. 디버그 채움과 격리 (결정 4)

빈 목록이 LIFO 스택이 되면 **방금 놓은 블록이 바로 다음 요청에 재배포**된다. 지금은 큐(FIFO)와 클래스당 수천 개 여유가 사실상 "격리 구역" 노릇을 해서, 해제된 컨테이너 버퍼를 가리키는 댕글링 포인터 같은 잠재 버그가 드러나지 않았을 수 있다. 재설계 뒤 그런 버그는 즉시 손상으로 나타난다. 그래서 디버그 빌드에 두 장치를 둔다.

- **채움**: 할당 시 payload를 `0xCD`, 해제 시 `0xDD`로 채운다(MSVC 디버그 힙과 같은 값. 대형 블록도). 해제 뒤 읽으면 `DDDDDDDD`가 보여 원인이 바로 잡힌다.
- **격리**: 클래스마다 최근 해제 N개(권장 32)를 링에 잡아 두고 그 뒤에 빈 목록에 넣는다. 재사용을 N번 늦춰 UAF가 값 손상으로 드러날 시간을 준다. 메모리 비용은 클래스당 N블록.

둘 다 `_DEBUG`에서만 켜고 릴리스 경로에는 코드가 없다(`#if`). 권장: 채움 켬, 격리 32.

### 3-13. 종료

`HMemoryPool::Shutdown`: 청크마다 클래스 페이지 전부 `free`, 원격 스택은 버림(페이지에 속하므로 따로 해제 없음). 대형 블록이 남아 있으면(`LargeCount > 0`) 개수·바이트를 Warning으로 남긴다(누수 리포트. Phase 4-3의 GC 생존 객체 리포트와 짝). TLS 캐시는 `Pool != this`로 무효화되므로 따로 지울 것이 없다. `HAllocator::deallocate`가 시스템 해제 뒤 불리면 지금처럼 무시하되 디버그에서 1회 `OutputDebugString`(정적 컨테이너 규칙 위반 감지).

### 3-14. 호출자 쪽 변경

- `Allocator.h`: `allocate(count)` → `Allocate(count * sizeof(T), alignof(T))`(현재 `int32 MemSize` 캐스트 제거), `operator==`/`!=`(항상 같음), `using is_always_equal = std::true_type`. 이후 `HList::swap`·이동 대입이 컴파일되므로 "복사 후 clear" 우회를 되돌린다.
- `Memory.h` `GMemoryGlobalSystem::Allocate<T>`: `MemoryPool.Allocate(sizeof(T), alignof(T))` + `JG_CHECK(MemPtr != nullptr)`(성장 뒤에는 도달하지 않지만 계약을 코드로 남긴다).
- `EMemorySize`: `_4_Byte`·`_1_GB`(실제 2MB)는 더 쓰지 않는다. 열거형은 헤더 필드 타입이라 남기고, `Unknown`을 대형 블록 표식으로 쓴다.

## 7. 검증 (Memory_TODO 2-6)

1. **빌드**: 전체 오류 0, 경고 기준선(C4244 4·LNK4098 1) 유지.
2. **0-2 재현 (a) `exhaust32`**: 32B 클래스에 페이지가 추가되며(Info 로그, `Growths` 증가) 4,097번째 이후도 계속 할당, `HList<uint8>(32)` 정상, 종료 코드 0. 임시 코드의 "survived" 로그가 찍히고 반납까지 끝난다.
3. **0-2 재현 (b) `oversize`**: 2MB `HList`가 대형 경로로 성공(`LargeCount` 1), 종료 코드 0. (결정 2가 (C)면 Critical 로그 뒤 중단.)
4. **상주 메모리**: 정상 상태에서 `Get-Process JGLauncher | % WorkingSet64` 또는 Private Bytes를 기준선(청크 2개 ≈ 201MB 커밋)과 비교. **150MB 이상 감소**가 합격.
5. **교차 스레드 스트레스** (`JG_MEMTEST=stress`): 로드 스레드에서 `HList` 10만 개 할당 → 메인에서 해제, 반대 방향도, 디버그 빌드 10회. 손상·assert 0, 끝나면 `RemoteFreePending` 0, 모든 클래스 `Live` 0.
6. **정렬** (`JG_MEMTEST=align`): `alignas(32)` 타입 `HList` 1,000개의 주소가 모두 32의 배수. `HList<T>::swap`·이동 대입 컴파일 확인.
7. **트레이스 빌드 리플레이**: `JG_MEMORY_TRACE=1`로 60초 → `memlog_stats.sh` → Allocate = Deallocate, 정상 상태 클래스 live 델타 0, 피크가 v2와 같은 자릿수(2,296 / 32B 123). 트레이스 로그 포맷은 그대로라 스크립트 수정 없음(`Dismatch` 0건이 정상이 된다). → 기준선 **v3**.

## 9. 이후 단계와의 연결

- **Phase 3(흡수 1차)**: 델리게이트·모듈 객체·문자열 참조 카운트가 들어와도 페이지 성장으로 흡수된다. 위젯 클래스별 표로 증가량을 본다.
- **Phase 4-1(GC 제어 블록)**: 제어 블록을 객체 앞 고정 오프셋에 둘 때 `Allocate<T>`가 `sizeof(T) + 제어블록`을 요청하면 되고, 헤더 16B는 그대로다. 헤더 확장을 택하면 이 문서의 stride 표만 다시 계산한다.
- **Phase 5(ImGui·rapidjson)**: 대형 경로가 있으므로 1MB 초과 요청이 안전하다. rapidjson `Realloc`은 할당·복사·해제로 구현.
- **Phase 6-1**: `AllocCount`·`Live` 카운터가 프레임별 델타 감지의 입력이 된다.
- **Phase 7-4(`PString` 풀 이전 재검토)**: 재진입 가드가 있어 문자열이 풀을 써도 성장 로그가 재귀하지 않는다.
