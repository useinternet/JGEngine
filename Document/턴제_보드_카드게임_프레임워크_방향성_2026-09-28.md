작성 2026-09-28. 대상 커밋 `033e988` + 워킹 트리. 소스 변경 없음(코드 읽기 + 문헌 조사).
전제 문서: `Document/게임프레임워크_설계방법론_조사_2026-09-21.md`(이하 "지난 조사"). 지난 조사는 장르를 가정하지 않은 일반 비교였고, 이 문서는 **목표 장르가 정해진 뒤** 그 결론을 다시 적용한 것이다.

목표 장르(사용자 제시): **보드게임 · 카드게임 · 턴제**. 참조작 **Baldur's Gate 3, Slay the Spire 2, Gloomhaven**.

## 0. 결론 요약

**장르가 설계 위험의 중심을 옮긴다.** 지난 조사는 "씬 오브젝트 모델(World / Actor / Component)을 어떻게 잡나"가 중심이었다. 턴제·보드·카드 장르에서는 **설계상 결정해야 할 것과 틀리면 되돌리기 어려운 것**이 씬 모델이 아니라 다른 곳에 몰린다. 실시간 틱이 없고 오브젝트 수가 수백을 넘지 않는 대신, **결정론(같은 입력 → 같은 결과), 되돌리기·리플레이, 어디서나 저장, AI 가 뷰 없이 상태를 시뮬레이션, 효과 트리거 순서, 연출과 규칙의 분리, 수백~수천 개의 데이터 콘텐츠**가 핵심 요구가 된다. 이 요구를 만족하는 것은 **룰 모델(게임 상태 + 명령 + 이벤트 + 효과 파이프라인)** 계층이다. 씬 모델(연출)은 그 **하류**에 있을 뿐 덜 중요한 것이 아니다 — 작업량은 오히려 연출 쪽이 크고, 룰/연출 분리는 연출을 규칙 타이밍에서 풀어 주기 위한 것이다(§4-6). (초판의 "부차적" 표현은 틀렸으므로 정정했다.)

**세 참조작의 실제 구조가 이를 뒷받침한다.** Slay the Spire 1편은 액션 큐 + 파워 훅의 OOP 구조로 상태와 연출이 한 큐에 섞여 있었고, 2편(Godot, 2026-03-05 얼리 액세스)은 **멀티플레이를 위해 "훨씬 모듈화된 프레임워크"로 처음부터 재구축**했다. Baldur's Gate 3 는 자체 엔진에 **ECS + 복제 레지스트리 + 데이터 스탯 파일 + 선언적 스토리 스크립트(Osiris)** 구조다. Gloomhaven 은 보드게임 규칙서가 곧 룰 엔진 명세이며, 디지털판(Unity)은 그 심판 역할을 구현한 것이다. 셋 다 "규칙은 데이터와 결정론적 처리, 연출은 그 결과"라는 방향으로 수렴한다.

**권장 방향(§4). 결정은 사용자.**
1. **룰 모델을 엔진과 분리된 계층으로 세운다.** Core 만 의존(Graphics/GUI 금지). 상태는 **값 타입(구조체 + 배열 + 세대 ID)** 이고 `JGObject`/`PSharedPtr` 을 쓰지 않는다. 모든 무작위는 상태 안의 시드 RNG. 상태 변경은 **명령 → 검증 → 실행 → 이벤트 로그** 경로로만. 되돌리기·AI 시뮬레이션·저장은 상태 복사로 해결한다.
2. **콘텐츠는 데이터 정의 + C++ 효과 프리미티브.** 카드·능력·상태·유닛·시나리오를 `JGAsset` 파생 정의 에셋(JSON, 리플렉션)으로 두고, 효과는 프리미티브(피해·방어·상태 부여·드로우·이동…)의 조합 + 조건 + 트리거로 기술한다. 복잡한 것은 C++ 클래스로 탈출구를 둔다.
3. **프레젠테이션은 지난 조사의 A안(World / Actor / Component)을 그대로 쓰되 역할을 축소한다.** 뷰는 룰 모델의 이벤트 로그를 소비해 연출하고, 입력을 명령으로 바꿔 넘길 뿐 상태를 직접 바꾸지 않는다.
4. **지금 당장 그래픽 없이 시작할 수 있다.** `JGConsole` 이 이미 그래픽 없이 코어를 띄우는 골격이고(`Source/Programs/JGConsole/Main.cpp`), ImGui 가 있으므로 카드 전투 수직 슬라이스는 Graphics 모듈의 성숙과 **병렬로** 진행 가능하다. 카드 게임은 본질적으로 UI 게임이다.
5. **범위 경고.** BG3 급 cRPG 는 1인 범위를 크게 넘는다. 세 참조작의 **공통 핵심(턴 상태 기계 · 효과 파이프라인 · 상태 효과 · 명령/이벤트 · 저장)** 을 먼저 만들고, StS 형 → Gloomhaven 형 → BG3 형 순으로 확장한다. BG3 의 대화·탐험·퀘스트는 각각 별개의 큰 모듈이다.

**지난 조사와 달라지는 것.** A안은 유지되고 역할이 바뀐다 — 상태의 **소유자**에서 상태의 **관찰자·연출자**로. 작업량은 줄지 않는다(§4-6). 틱 그룹은 룰 계층에서만 사라지고 뷰 계층에는 그대로 필요하며, 대량 오브젝트 성능 논의는 중요도가 떨어진다. 프리팹은 뷰 조립(유닛 외형)에 쓰고, 규칙 콘텐츠는 별도의 **정의 에셋**으로 간다. ECS 는 "성능"이 아니라 **"상태를 균일한 데이터로 두어 복사·직렬화·복제를 쉽게 한다"** 는 관점에서 룰 모델 표현에 부분 채택된다(BG3 의 방식).

## 1. 장르가 요구하는 것

| 요구 | Slay the Spire 2 | Gloomhaven | Baldur's Gate 3 | 아키텍처 결과 |
|---|---|---|---|---|
| 턴제 | ◎ | ◎ | 전투 ◎ / 탐험은 실시간 | 룰 계층에 프레임 틱 없음. **턴 상태 기계**가 중심. 뷰 계층(연출)은 프레임 기반 유지 |
| 결정론 | 시드 런, 데일리 | 보드게임 규칙 그대로 | 세이브 스커밍 가능 구조 | 모든 무작위는 **상태 안의 시드 RNG**. 시스템 시간·전역 RNG 금지. 수치는 정수 |
| 되돌리기·리플레이 | 시드 리플레이 | 이동 확정 전 취소 | 어디서나 저장 | **상태 스냅샷** 또는 명령 로그 |
| AI 가 상태를 시뮬레이션 | 적 인텐트(미리 결정·공개) | 몬스터 규칙 AI(포커스 → 이동 → 공격) | 전투 AI 평가 | 룰 계층을 **뷰 없이** 돌릴 수 있어야 함 |
| 은닉 정보 | 덱 순서 | 몬스터 능력 카드 | 주사위 | 상태 안 RNG + (멀티플레이 시) 관점별 가시성 |
| 효과 트리거 순서 | 파워·유물 훅 수백 개 | 원소·상태 효과 | 리액션·상태·패시브 | **트리거 순서 규칙과 큐** 필수. 가장 많은 버그가 나는 곳 |
| 보드 | 없음(1차원 배치) | 헥스 그리드, LOS, AoE | 자유 이동 + 거리·고저차 | 보드를 룰 계층에 추상화. 카드 전투는 "보드 없음" |
| 연출 | 카드 애니메이션(Spine2D) | 유닛 이동·공격 | 풀 3D 시네마틱 | 연출은 상태 변화의 **결과**. 이벤트 로그를 소비 |
| 콘텐츠 양 | 카드 575+, 유물 278, 포션 63 | 능력 카드 수백, 몬스터 수십 종 | 주문·상태 수천 | **데이터 정의 + 툴**. 코드 per 카드는 상한이 있음 |
| 오브젝트 수 | 수십 | 수십 | 수백(전투) | 대량 오브젝트 성능 무의미. ECS 의 성능 논거 소멸 |
| 멀티플레이 | 4인 협동 | 4인 협동 | 4인 협동 | 결정론 + 명령 스트림이면 자연스럽게 열림. 지금 구현 안 해도 **규약은 처음부터** |

이 표에서 나오는 것: **"룰은 순수 데이터와 결정론적 함수, 뷰는 그 결과를 그리는 것"**. 이것은 지난 조사 §3-9 의 "저작 모델 ≠ 런타임 모델"이 아니라 **"모델 ≠ 뷰"** 다. 둘은 다르다. 저작/런타임 분리는 지금도 필요 없고, 모델/뷰 분리는 이 장르에서 필수다.

## 2. 세 참조작의 실제 구조

### 2-1. Slay the Spire — 1편(Java · libGDX) → 2편(Godot)

**1편의 구조(모딩 커뮤니티가 역분석한 것. BaseMod/StSLib 문서 기준)**
- 카드 사용 = `AbstractCard.use()` 가 `ActionManager.addToBottom(new DamageAction(...))` 식으로 **액션을 큐에 쌓는다**. `ActionManager` 가 매 프레임 큐 앞의 액션을 `update()` 하고 끝나면 다음으로. 액션 하나가 **상태 변경과 연출(대기 시간)을 함께** 담당한다. 끼어드는 효과는 `addToTop`.
- 버프/디버프 = `AbstractPower` 파생 클래스가 **훅 메서드**(`atDamageGive`, `atDamageReceive`, `onAttacked`, `atStartOfTurn`, `atEndOfTurn`, `onCardDraw`, `onUseCard` …)를 오버라이드. 유물 = `AbstractRelic` 훅. 적 = `AbstractMonster` 가 `getMove()` 로 **인텐트를 미리 정하고 공개**, `takeTurn()` 에서 실행.
- 무작위 = **용도별 시드 RNG 스트림 분리**(카드, 몬스터, 맵, 상점, 이벤트, 보물, 유물, 포션, 셔플 …). 런 시드 하나로 전체 재현.
- 콘텐츠 = **코드 per 카드**(Java 클래스 하나). 모딩은 훅에 끼워 넣는 방식.

**장점** 단순·직관. 카드 추가가 클래스 하나. 훅으로 상호작용 표현이 쉽다. 액션 큐가 순차 연출과 자연스럽게 맞물린다. 시드 분리가 재현성을 준다.
**단점** 상태와 연출이 한 큐에 섞여 "연출 중 상태 질의" 타이밍 버그가 상시. 훅 호출 순서가 파워 등록 순서에 암묵 의존. 되돌리기 불가(스냅샷 없음). 헤드리스 시뮬레이션 어려움(액션이 렌더 프레임에 묶임). 코드 per 카드는 비프로그래머가 밸런싱할 수 없다.

**2편(2026-03-05 얼리 액세스, Godot)** Mega Crit 공식 설명: 처음부터 재구축, Spine2D 연출, **"멀티플레이(4인 협동)를 지원하기 위해 훨씬 모듈화된 프레임워크"**. 멀티플레이는 결정론적 명령 동기화를 전제하므로, 1편의 혼합 구조로는 안 되었다는 뜻으로 읽힌다(공식 문구가 아닌 추정).

### 2-2. Gloomhaven — 보드게임 규칙 → 디지털(Flaming Fowl · Unity)

- **규칙서가 곧 룰 엔진 명세다.** 이니셔티브 = 선택한 두 카드 중 앞 카드의 숫자. 카드 상단/하단 행동. 헥스 그리드 이동·사거리·시야(LOS). 몬스터 AI = 능력 카드 뒤집기 → **포커스 결정(규칙: 가장 적은 이동으로 공격 가능한 적, 동률 시 이니셔티브)** → 이동 → 공격. 원소 주입/소비. 상태 효과(독·상처·기절·무장해제·강화 …). 공격 수정자 덱(±카드, 축복·저주 삽입). 시나리오 목표와 특수 규칙, 문을 열면 방 공개·스폰. 캠페인(파티·레벨·아이템·은퇴·도시 이벤트).
- 디지털판 내부 구조는 비공개. 하지만 요구사항은 명확하다: **결정론적 규칙 AI, 이동 확정 전 취소, 시나리오 데이터(타일·스폰), 캠페인 저장, 4인 협동.**

**교훈** 보드게임 원작이 있는 장르에서 룰 계층은 **"심판"** 이다. 심판은 말을 옮기지 않는다. 판정하고 결과를 말한다. 뷰는 말을 옮기는 손이다. 이 은유가 모델/뷰 분리의 가장 정확한 설명이다.

### 2-3. Baldur's Gate 3 — Larian 자체 엔진

- **ECS.** Norbyte 의 Script Extender 가 밝힌 바로 엔진은 엔티티 + 컴포넌트 구조이고, **복제(replication) 레지스트리**가 컴포넌트 단위로 서버 → 클라이언트 동기화를 담당한다. Lua 에서 `Ext.Entity.Get(uuid)` 로 컴포넌트를 읽고 쓴다.
- **데이터 스탯 파일.** 주문(`SpellData`)·상태(`StatusData`)·무기·방어구 등을 텍스트 항목으로 정의하고 항목이 다른 항목을 상속(`using`)한다. 콘텐츠 수천 개가 코드가 아니라 데이터다.
- **Osiris.** 선언적 규칙 언어(조건 → 행동)로 스토리·퀘스트 로직을 기술. 일반 행동 스크립트와 별도.
- 전투 턴제 ↔ 탐험 실시간 전환. 어디서나 저장(월드 전체 상태 직렬화).

**장점** 콘텐츠·복제·저장이 균일한 데이터 처리. 방대한 규칙(D&D 5e)이 데이터로 흡수. **경고** 규모. 전투 핵심(턴·행동 경제·주문·상태·주사위)만이 다른 두 참조작과 공유되고, 대화·탐험·퀘스트·시네마틱은 각각 독립된 큰 시스템이다.

## 3. 후보 구조와 장단점

이 장르에서 실제로 선택지가 되는 구조 다섯 가지. 1~4 는 **룰과 뷰의 관계**, 5 는 **콘텐츠 정의 방식**으로 축이 다르며 5 는 1~4 어느 것과도 조합된다.

### 후보 1 — 단일 계층: 씬 오브젝트가 규칙까지 담당

Unity 로 만드는 취미 카드 게임의 기본형. 카드 Actor 의 컴포넌트가 클릭을 받고 자기 효과를 실행하며 적 Actor 의 체력을 깎는다.

- **장점** 가장 빨리 시작한다. 카드 하나 = 오브젝트 하나라 직관적. 지난 조사 A안만으로 된다.
- **단점** 규칙이 뷰에 묶여 **헤드리스 실행·AI 시뮬레이션·되돌리기·리플레이가 전부 불가능**해진다. 저장은 씬 전체를 직렬화해야 한다. 연출 중 상태가 바뀌는 타이밍 버그. 멀티플레이 불가. 테스트는 게임을 켜서 손으로.
- **판정** 프로토타입 1주짜리에는 되지만 이 장르의 요구(§1) 열 개 중 여섯 개를 구조적으로 막는다. **배제.**

### 후보 2 — 액션 큐 하이브리드(Slay the Spire 1편 형)

카드·파워·유물은 클래스, 효과는 액션 객체를 큐에 쌓고 순차 처리. 액션이 상태 변경과 연출 대기를 함께 한다.

- **장점** 검증된 구조(StS 1편이 이걸로 완성됐다). 순차 연출과 큐가 자연스럽다. 훅 기반 상호작용이 쓰기 쉽다. 코드 per 카드라 C++ 만으로 콘텐츠를 만들 수 있다.
- **단점** §2-1 의 단점 그대로. 특히 JGEngine 에서는 액션이 렌더 프레임 `Update` 에 묶이면 `JGConsole` 헤드리스가 불가능해지고, 훅이 `PSharedPtr` 객체 그래프에 걸리면 지난 조사의 GC 함정(§5-4)을 그대로 밟는다. 되돌리기를 나중에 붙이려면 사실상 재작성.
- **판정** 액션 큐 자체는 좋은 아이디어다. 문제는 "상태 변경"과 "연출"을 한 액션이 하는 것. **큐 개념은 가져오되 연출과 분리한다(후보 3).**

### 후보 3 — 룰 모델 분리 + 명령/이벤트(boardgame.io · Hearthstone 형)

룰 모델 = 값 타입 상태 + 시드 RNG + 명령 함수 + 이벤트 로그. 뷰는 이벤트를 소비해 연출하고 입력을 명령으로 바꿔 보낸다. 효과 처리는 큐로 하되 큐는 **상태만** 바꾸고 결과를 이벤트로 남긴다.

- **장점** §1 의 요구를 **구조로** 만족한다. 되돌리기 = 상태 복사. 리플레이 = 명령 로그 재생. AI = 상태 복사 후 명령 적용. 저장 = 상태 직렬화. 멀티플레이 = 명령 스트림 동기화. 테스트 = 콘솔에서 명령열 실행 후 체크섬 비교. 연출 타이밍 버그가 구조적으로 사라진다(뷰가 늦어도 상태는 이미 확정). Graphics 모듈 없이 **지금** 만들 수 있다.
- **단점** 규율이 필요하다. 상태 밖의 숨은 변수(전역, static, 시스템 시간)가 하나라도 있으면 결정론이 깨진다. 이벤트 종류를 설계해야 한다(뷰가 필요한 정보를 모두 담아야 함). 상태 복사 비용은 상태 크기에 비례하나 이 장르는 KB 단위라 문제없다. 처음에 "카드 클릭하면 바로 데미지" 보다 한 단계 더 돌아간다.
- **판정** **채택.** 이 장르의 표준 답이다.

### 후보 4 — 룰 계층을 ECS 로(BG3 형)

엔티티 = ID, 컴포넌트 = 데이터 배열, 시스템 = 규칙 함수. 후보 3 의 "상태 표현"을 ECS 방식으로 하는 것.

- **장점** 상태가 균일한 배열이라 복사·직렬화·복제·디버그 덤프가 기계적으로 된다(BG3 의 복제 레지스트리가 이것). 유닛/카드의 성질 조합이 컴포넌트 유무로 표현된다.
- **단점** 턴제 규칙은 "배치 순회"가 아니라 "한 행동의 깊은 분기"라 시스템 스케줄·아키타입·쿼리 같은 ECS 의 무거운 부분이 쓸모없다. 지난 조사의 결론대로 저작 툴링을 새로 세워야 한다. 관계(덱 → 손 → 버림 존 이동, 소유자)가 ECS 의 약점.
- **판정** **정신만 부분 채택.** "상태 = 값 타입 배열 + 세대 ID" 는 가져오고(후보 3 의 상태 표현으로), 시스템 스케줄·아키타입·제네릭 쿼리는 도입하지 않는다.

### 후보 5 — 콘텐츠 정의 축: 코드 per 카드 vs 데이터 정의 vs 스크립트 언어

| | 코드 per 카드(StS 1편) | 데이터 정의 + C++ 프리미티브(Larian Stats · Gloomhaven 데이터) | 스크립트 언어(Lua 등) |
|---|---|---|---|
| 콘텐츠 추가 | C++ 클래스 + 재빌드 | JSON 편집. 재빌드 없음 | 스크립트 편집 |
| 표현력 | 무제한 | 프리미티브 범위 안. 밖은 C++ 탈출구 | 무제한 |
| 밸런싱 반복 | 느림(빌드) | 빠름 | 빠름 |
| 툴링 | 없음 | 리플렉션 인스펙터로 편집·검증 가능 | 별도 에디터·디버거 필요 |
| 결정론 | 보장 쉬움 | 보장 쉬움(프리미티브가 순수) | 스크립트 안 숨은 상태 위험 |

| 상한 | 수백 장까지 실용 | 수천 개(BG3·Forge 규모) | 수천 개 |

- **판정** **데이터 정의 + C++ 프리미티브 레지스트리를 기본으로, 복잡한 카드는 C++ 클래스 탈출구.** 스크립트 언어는 콘텐츠가 프리미티브 조합으로 표현되지 않는 사례가 누적됐을 때 도입 여부를 다시 본다(§8-12).

               PSequencer: 이벤트 → 연출 단계 큐 (대기 · 병렬 · 스킵)

### 4-2. 핵심 규칙 여덟 가지

1. **룰 모델은 Core 만 의존한다.** Graphics/GUI/Devkit 헤더를 포함하지 않는다. 그래야 `JGConsole` 에서 돌고, 그래야 AI·테스트·밸런스 시뮬레이션이 된다.
2. **상태는 값 타입이다.** `JGObject`/`PSharedPtr` 을 룰 모델 안에서 쓰지 않는다. 구조체 + `HList` + 세대 ID. 이유: 스냅샷이 복사 한 번, 포인터 동일성이 없어 결정론이 지켜지고, 지난 조사의 GC 함정(§5-4) 전부를 우회하며, AI 가 상태를 수천 번 복사해도 싸다. 직렬화는 `IJsonable` 구조체(`HStaticSubMesh` 선례)로.
3. **모든 무작위는 상태 안의 시드 RNG 스트림이다.** 용도별 분리(StS 방식: 셔플·적 행동·보상·맵 …). 구현은 PCG32 급 자체 구현 — `std::mt19937` + `std::uniform_int_distribution` 은 **STL 구현마다 분포 알고리즘이 달라 플랫폼 간 결정론이 깨진다.** 시스템 시간·`rand()`·전역 RNG 금지. 수치는 정수.
4. **상태 변경은 명령 → 검증 → 실행 경로로만.** 뷰는 상태를 읽기만 한다. "합법 수 열거"(`EnumerateLegal`)를 처음부터 둔다 — UI 하이라이트·AI·테스트가 전부 이 함수를 쓴다.
5. **이벤트 로그가 뷰 갱신의 유일한 통로다.** `Execute` 가 반환하는 이벤트 목록에는 뷰가 연출에 필요한 정보(누가·무엇을·얼마나·어디서 어디로)가 모두 들어 있어야 한다. 뷰가 "왜 이렇게 됐지" 를 상태를 뒤져 추론하게 만들면 실패한 설계다.
6. **되돌리기는 스냅샷이다.** 플레이어 명령마다 상태를 복사해 스택에 쌓는다. 역연산 명령은 만들지 않는다(값 타입이면 복사가 더 싸고 버그가 없다).
7. **효과는 데이터 정의 + C++ 프리미티브다.** 프리미티브 레지스트리(`PName` → 함수), 타겟 선택기, 조건, 수치 계산 파이프라인(기본값 → 가산 → 배율 → 방어 → 최종. StS 의 힘 → 약화/취약 → 방어 순서가 이것). 트리거 = `(이벤트 종류, 조건, 효과 목록)`.
8. **트리거 순서는 문서화된 결정론 규칙이다.** 이벤트 발생 → 리스너 수집 → 정렬(명시 우선순위 → 소유자 순(행동자 먼저) → 부여 시각 오름차순) → 효과 큐에 `addToBottom`, 끼어들기는 `addToTop`. "대신에(replacement)" 류는 큐가 아니라 수치 파이프라인 단계로 처리. LIFO 스택(MtG)이 아니라 FIFO 큐(StS)를 기본으로 — 카드/보드 장르는 이쪽이 직관적이고 StS 가 검증했다.

### 4-3. 핵심 타입 스케치 (JGEngine 관용구)

설계 확정이 아니라 "기존 코드와 맞물리는지 보기 위한 스케치". 모듈 이름은 가칭.

```cpp
// Source/Runtime/GameRules/RulesDefines.h   (가칭 모듈. Core 만 의존. SharedLib)

// 엔티티 참조. 포인터가 아니라 인덱스 + 세대. 죽은 참조는 세대 불일치로 O(1) 감지 (지난 조사 §4-2)
struct HEntityId
{
    uint32 Index      = 0;
    uint32 Generation = 0;

    bool IsValid() const
    {
        return Generation != 0;
    }
};

// 결정론 RNG. 시드와 호출 횟수가 곧 상태라 직렬화된다. 용도별로 하나씩
struct GAMERULES_API HRandomStream : public IJsonable
{
    uint64 State;
    uint64 Increment;

    uint32 Next();
    int32  Range(int32 minInclusive, int32 maxInclusive);   // 자체 매핑. std 분포 금지
    // WriteJson / ReadJson
};

enum class ERngStream : uint8
{
    Shuffle, EnemyAction, Reward, Map, Misc, Count
};
```

### 4-4. 뷰 계층과의 접점

- 뷰는 `HGameState` 를 **읽기 전용**으로 받고 `HList<HGameEvent>` 를 소비한다. `PSequencer` 가 이벤트를 연출 단계(카드가 버림 더미로 날아감, 피해 숫자, 유닛이 경로를 따라 이동)로 바꿔 큐에 넣고, 대기·병렬·스킵(연타 시)을 관리한다. 연출이 끝나기 전에 다음 명령이 들어와도 **상태는 이미 확정**이라 규칙이 깨지지 않는다 — 후보 2 의 타이밍 버그가 구조적으로 사라지는 지점. 다만 "어떻게 느껴지느냐"는 별개의 정책이다(§4-6-4, §8-15).
- 입력: 피킹(`HRay` vs 카드 사각형 / 헥스 평면 — `Core/Math` 에 `HRay`·`HPlane` 있음) → `HCommand` 조립 → `Validate` 실패면 이유를 UI 에 → 성공이면 `Execute`.
- 지난 조사 A안(World/Actor/Component)은 그대로 뷰의 골격이다. 카드 액터·유닛 액터·타일 액터·카메라. 프리팹은 **유닛 외형 조립**(메시 + 상태 아이콘 앵커 + 피격 이펙트 소켓)에 쓴다. 규칙 콘텐츠는 프리팹이 아니라 정의 에셋이다.
- **첫 번째 뷰는 ImGui 다.** 카드 = 텍스트 버튼(`ImGui::Image` 로 카드 뒷면 PNG 표시 가능. `Content/RawResources/CardBack_*.png` 이 이미 있다), 적 = 텍스트 + 인텐트, 이벤트 로그 창, 상태 인스펙터. Graphics 모듈의 Phase 5 이후 작업과 **완전히 독립**이다.

### 4-5. 왜 이 조합인가

- 후보 3 이 §1 의 요구를 구조로 만족하는 유일한 후보이고, JGEngine 의 자산(리플렉션·JSON·`JGConsole`·ImGui)이 그 비용을 가장 많이 깎아 준다.
- 후보 4 의 "값 타입 상태" 만 가져온 이유: 이 장르에서 ECS 의 나머지(스케줄·아키타입·쿼리)는 비용만 있고 이득이 없다. 지난 조사 §3-4 결론과 같다.
- 후보 5 의 데이터 정의를 택한 이유: 리플렉션과 JSON 이 이미 있어 "정의 에셋 + 인스펙터" 가 거의 공짜이고, 참조작 세 개 중 두 개(BG3, Gloomhaven)가 데이터 방식이며, StS 2편의 콘텐츠 규모(카드 575+ · 유물 278)는 코드 per 카드의 실용 상한 근처다.
- 지난 조사 A안을 뷰로 유지하는 이유: 씬 조립·피킹·카메라·연출 액터는 여전히 오브젝트 트리가 가장 자연스럽고, 이미 그 방향으로 분석이 끝나 있다.

### 4-6. 룰 ↔ 연출 경계에서 양방향인 것 — "부차적" 표현의 정정

§0 초판에 "이 장르에서 씬 오브젝트 모델은 부차적이 된다"고 썼다. **틀린 표현이다.** 맞는 말은 둘이다.

- **설계 위험**은 룰 계층에 몰려 있다(결정론·되돌리기·트리거 순서·AI). 씬 모델의 설계는 지난 조사에서 이미 정리됐고, 이 장르가 새로 결정할 것이 적다.
- **작업량**은 연출 계층이 더 크다. StS2 가 Spine2D 에 투자한 것, BG3 의 대부분이 시네마틱·애니메이션·VFX 인 것이 그 증거다. 룰/연출 분리는 연출을 줄이기 위한 것이 아니라 **연출이 규칙 타이밍에 발목 잡히지 않고 마음껏 화려해지기 위한 것**이다. 콘솔 전용 게임이라면 분리할 이유조차 없다. 헤드리스 실행은 제품이 아니라 테스트·AI·밸런스용 부산물이다.

상태 변경은 단방향(룰 → 뷰)이지만, **경계 자체는 네 곳에서 양방향**이고 각각 설계가 필요하다.

1. **선택 프롬프트.** "카드를 한 장 골라 버려라", "리액션을 쓸 것인가"(BG3), "둘 중 하나를 골라라" 처럼 효과 해결 도중 플레이어 입력이 필요한 경우. 룰 엔진이 연출이나 입력을 기다릴 수는 없으므로 **해결을 중단하고 '선택 대기'를 상태 안에 노출**한다(`HTurnState.PendingChoice`: 누가·무엇을·후보 목록). 뷰는 이 상태를 보고 UI 를 띄우고, 선택은 별도 명령(`ResolveChoice`)으로 들어온다. 이때 미해결 효과 큐가 상태에 직렬화되어 있어야 스냅샷·저장이 중단 지점을 포함한다. boardgame.io 의 stage, Hearthstone 의 choose-one 이 같은 구조다. **C6 명령·C9 효과 큐 설계에 처음부터 포함**해야 한다 — 나중에 끼우면 큐를 다시 짠다.
2. **페이싱과 공개 순서.** 룰은 명령 하나에 이벤트 30개를 낼 수 있다(연쇄 반응). 그것을 어떤 속도로, 어떤 순서로, 무엇을 묶어 보여줄지는 **연출의 결정**이다(동시 피해는 한 번에, 연쇄 사망은 순차로, 카메라 컷). 시퀀서가 이 재량을 가지려면 이벤트에 **인과 관계(어느 명령·어느 효과에서 파생됐는지)** 가 있어야 한다 → `HGameEvent` 에 `CauseIndex`·`Depth` 를 둔다.
3. **이벤트의 정보량은 연출 요구가 정한다.** "피해 6" 만으로는 애니메이션을 만들 수 없다. 이전/이후 체력, 방어로 흡수된 양, 치명 여부, 원인 카드, 공격자 위치가 있어야 피해 숫자의 색·크기·방향과 카메라 타깃이 나온다. 이벤트 스키마를 룰 쪽에서 혼자 정하면 반드시 뒤집힌다 → **시퀀서 프로토타입을 Phase 2 에서 시작**한다(§6).
4. **연출 중 입력.** 연출이 진행 중일 때 플레이어가 다음 카드를 내면? (a) 큐가 빌 때까지 차단(StS 1편), (b) 명령을 버퍼링해 순서대로 실행, (c) 연출을 즉시 스킵하고 실행. 상태는 이미 확정이라 셋 다 규칙상 안전하지만 **느낌이 완전히 다르다.** 결정 항목(§8-15).

그리고 연출 계층 자체가 큰 씬 작업이다. 유닛의 연출 상태 기계(대기 → 피격 리액션 → 복귀, 사망 연출 중 추가 피격), 카드의 상태(손·드래그·호버 확대·비행), 카메라 포커스, VFX 수명, 사운드 큐. 이것이 지난 조사 A안(World / Actor / Component)이 실제로 하는 일이고, 여기에는 **프레임 틱이 그대로 필요**하다. 룰 계층만 프레임에서 풀려나는 것이다.

## 6. 단계별 로드맵 (제안)

각 단계 끝에 "확인 가능한 것"을 붙였다. 단계 1~3 은 **Graphics 모듈과 독립**이다. "독립"은 그래픽 없이도 진행할 수 있다는 뜻이지 연출을 뒤로 미룬다는 뜻이 아니다 — 시퀀서는 Phase 2 에서 시작한다(§4-6).

### Phase 0 — 선결 (지난 조사 §6 에서 이미 나온 것)
- 메모리 단계 A-2(`PSharedPtr` 대입) + `getJGObject` 실패 처리(지난 조사 §5-4-9). 정의 에셋 로드가 이 경로를 탄다.
- `JGSTRUCT` 구조체의 JSON 왕복 확인(`HEffectDesc`, `HHexCoord` 가 `IJsonable` 로 되는지). `HStaticSubMesh` 선례가 있으므로 될 것으로 보이나 **헤더 툴 산출물로 확인**.
- `HTransform`, `GameFrameWorks` SharedLib 전환은 Phase 4 전까지만 있으면 된다(뷰 계층).
- ✅ 확인: 정의 에셋 하나를 저장·로드해 프로퍼티가 왕복되고, 미등록 타입 로드가 크래시 대신 실패 로그로 끝난다.

### Phase 1 — 룰 코어 골격 (헤드리스)
- C1 RNG, C2 상태·ID, C6 명령 골격, C10 이벤트, C11 스냅샷·체크섬, C14 `JGConsole` 러너, C15 최소 테스트.
- 첫 규칙 하나: "Strike 를 내면 6 피해". 정의 에셋 하나, 명령 하나, 이벤트 하나.
- ✅ 확인: 콘솔에서 시드 고정 → 같은 명령열 100회 → 최종 체크섬 100회 동일. 되돌리기 후 체크섬 원복.

### Phase 2 — 카드 전투 수직 슬라이스 (StS 형 한 전투)
- 존·드로우·에너지·턴(C5, 5-2), 카드 5종·상태 3종(힘·취약·약화)·적 1종(인텐트 2개)·승패. C7 효과 파이프라인의 첫 프리미티브 6개(Damage, Block, ApplyStatus, Draw, GainEnergy, DecrementStacks), C8, C9.
- ImGui 뷰: 손패 버튼, 적 체력·인텐트, 이벤트 로그 창, 상태 인스펙터(리플렉션), 되돌리기 버튼.
- **시퀀서 프로토타입을 여기서 시작한다.** ImGui 드로우 리스트로 카드 이동·피해 숫자·적 피격 흔들림을 실제로 애니메이션해, 이벤트 로그의 정보량과 인과 관계(§4-6-2·3)가 연출에 충분한지 검증한다. 선택 프롬프트(§4-6-1)가 필요한 카드 한 장("카드 한 장을 골라 버린다")을 반드시 포함해 '선택 대기' 경로를 초기에 통과시킨다.
- ✅ 확인: ImGui 로 한 전투를 끝까지 플레이. 헤드리스 자동 플레이 1,000판 승률 통계(C13 무작위 AI, C16).

### Phase 3 — 보드 확장 (Gloomhaven 형)
- 5-3 의 헥스·이동·LOS·AoE·이니셔티브·몬스터 규칙 AI·시나리오 로딩. 카드 전투와 **같은 `PRuleEngine`** 위에 보드 명령이 추가되는지가 설계 검증 포인트.
- ImGui 헥스 도식 뷰(원과 선으로 충분).
- ✅ 확인: 시나리오 1개를 헤드리스 자동 플레이 + ImGui 수동 플레이. 몬스터 AI 결정이 시드 고정 시 100% 재현.

### Phase 4 — 프레젠테이션 (지난 조사 A안)
- World/Actor/Component + `PSequencer` + 피킹 + 카메라. 3D 보드에 정적 메시 유닛, 카드는 ImGui 유지 또는 자체 2D.
- ✅ 확인: Phase 3 의 같은 시나리오가 3D 뷰로 플레이되고, 뷰를 ImGui ↔ 3D 로 바꿔도 **룰 코드는 한 줄도 안 바뀐다.**

### Phase 5 — 메타 · 툴
- 런 구조 / 캠페인, 세이브 슬롯, 카드·시나리오 에디터(ImGui + 리플렉션 인스펙터), 밸런스 시뮬레이터 UI.

### Phase 6 이후 — cRPG 요소
- 5-4 의 각 大 항목을 **개별 문서**로. 탐험 실시간 계층은 엔진 성격을 바꾸므로 그때 지난 조사의 틱 그룹 논의가 다시 살아난다.
