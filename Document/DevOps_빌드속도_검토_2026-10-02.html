요약. 엔진 전체 빌드가 272.6초(4분 33초)입니다. 원인의 대부분은 한 프로젝트 안의 .cpp를 한 번에 하나씩 컴파일하는 설정입니다. 32스레드 머신에서 동시에 도는 컴파일이 평균 1.27개이고, 빌드 중 CPU 사용률은 20% 안팎입니다. GameFrameWorks가 09-28 파일 1개에서 10-01 95개로 커지면서 이 모듈 하나가 순서대로 약 150초를 차지하게 됐고, 그래서 체감상 갑자기 느려졌습니다.

권하는 것 (위에서부터, 아래 표의 BS 번호):

  1. BS-1 병렬 컴파일(/MP) 켜기. premake 템플릿 한 줄, 소스 변경 없음. 전체 빌드 272.6 → 약 57초.
  2. BS-2 PCH에 spdlog · rapidjson 넣기. PCH.h에 pragma 1줄 + include 6줄. 컴파일 CPU가 절반이 되고 전체 빌드는 약 50초. 공용 헤더 하나를 고친 뒤 빌드는 지금의 1/7~1/10.
  3. BS-3 worktree · 검증용 게임 프로젝트를 %TEMP% 밖에 두기. 작업 방식. 지금 에이전트 worktree는 헤더 수정을 증분으로 못 잡아 매번 전체를 다시 빌드합니다.

2. 무엇이 시간을 쓰나

2-1. 파일을 하나씩 컴파일한다 (가장 큰 원인)

지금 생성되는 프로젝트 설정에는 프로젝트 안 병렬 컴파일(/MP 또는 MSBuild MultiToolTask)이 없습니다. MSBuild -m은 프로젝트끼리만 병렬로 돌리는데, 의존이 Core → Asset → Graphics → GameFrameWorks → JGEditor · JGConsole 한 줄이라 실제로는 거의 한 개씩 돕니다. 컴파일이 이어진 271초 중 215초는 컴파일 1개만 돌았습니다.

2-2. 파일마다 같은 헤더를 다시 읽는다

컴파일 CPU 344초 중 323초(94%)가 헤더 처리(프런트엔드)입니다. PCH.h + Core.h + 빈 함수뿐인 AI/Main.cpp도 1.3초가 걸립니다. Core.h가 spdlog(로그) · rapidjson(JSON) · 엔진 Core 헤더 30여 개를 끌어오고, 엔진 헤더 59개가 Core.h를 include하므로 거의 모든 파일이 이 묶음을 다시 읽습니다. 지금 PCH에는 STL · DirectX 12 · Windows.h만 들어 있습니다.

2-3. 문제가 아닌 것

링크는 13번 합 9.6초(최대 1.4초)로 병목이 아닙니다. Core가 정적 라이브러리(Core.lib 54 MB)라 DLL마다 링크되지만 지금 크기에서는 괜찮습니다.

6. 측정 방법

머신: i9-13980HX 24코어 / 32스레드, RAM 64 GB, NVMe RAID0, Windows Defender 실시간 보호 켜짐. VS2022 Community MSBuild, MSVC 14.38, v143. 메인 트리는 다른 세션이 쓰므로 HEAD를 별도 worktree로 받아 쟀고, 설정은 명령줄(MSBuild 속성 · 환경 변수)과 worktree 안 PCH.h로만 바꿨습니다. 컴파일러 /Bt+로 파일별 시간과 시각을, 링커 /time으로 링크 시간을 받아 집계했습니다. 스크립트는 Memory/DevOps/Files/tools/build_timing/.

CL=/Bt+ LINK=/time BS_WT=<worktree> BS_LOG=<로그> bash run_build.sh r2 Rebuild -p:UseMultiToolTask=true -p:EnforceProcessCountAcrossBuilds=true
python analyze.py <로그>/r2.log
