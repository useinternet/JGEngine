# 엔진 ↔ 게임 분리 구조 분석

작성 2026-09-16. 대상 커밋 `04d9247` + 워킹 트리.
목표: **엔진 단독으로 솔루션 생성 가능**, **게임 프로젝트를 만들면 그 게임의 솔루션이 생기고 그 안에 엔진이 포함**되는 구조.

---

## 0. 결론 요약

구조상 **이미 절반은 준비되어 있다.** JGBuildTool·JGHeaderTool 양쪽에 `EngineWorkDirectory` / `UserWorkDirectory` 2분할이 들어가 있고(`Arguments.h`), BuildTool 은 유저 모듈을 별도 맵(`_userModuleInfoMap`)으로 모아 별도 premake 그룹으로 뽑는 코드까지 작성되어 있다. 빌드 Configuration 이름(`DevelopEngine` / `DevelopGame` / `ConfirmGame` / `ReleaseGame`)도 "엔진은 Release, 게임은 Debug" 같은 조합을 전제로 이미 설계되어 있다.

**막고 있는 건 단 하나의 가정이다: "엔진 루트 = 프로젝트 루트 = 프로세스 CWD 기준 `../../`".**

`HFileHelper::EngineDirectory()` 가 `"../../"` 리터럴을 반환하고(`FileHelper.cpp:298`), Bin·Temp·CodeGen·Content·Source·ThirdParty 가 전부 여기서 파생된다. 게임이 별도 폴더에 있으면 이 한 줄 때문에 전부 어긋난다. premake 템플릿의 경로도 전부 같은 가정의 문자열 리터럴이고(`BuildTemplate.lua:1-6`), workspace 이름도 `"JGEngine"` 로 하드코딩되어 있다(`BuildTemplate.lua:33`).

작업의 실체는 **"루트 1개 → 루트 2개(EngineRoot / ProjectRoot)"** 로 바꾸는 것이고, 영향 범위는 아래처럼 비대칭이다.

| 영역 | 손볼 곳 | 크기 |
|---|---|---|
| Core 경로 API (`HFileHelper`) | 1개 파일, 루트 해석 + Project* 계열 추가 | 中 |
| 런타임 호출부 | **단 5곳** (Asset 3, Graphics 1, Module 1) | 小 |
| JGBuildTool | 경로 프리픽스 + 템플릿 분할 + workspace 파라미터화 | 大 |
| JGHeaderTool | 유저 모듈 경로 대응 + `_userModuleSet` 미구현분 | 中 |
| premake 템플릿 | 엔진 모듈 정의를 include 가능한 파일로 분리 | 中 |
| 런타임 게임 개념 | `.jgproject`, GameContent, 런처 LaunchModule | 中 |

런타임 코드는 거의 건드릴 게 없다. **작업의 90%가 `Source/Programs` 의 두 툴과 premake 템플릿에 몰려 있다.**

## 3. 막고 있는 것 (블로커 목록)

### A. `EngineDirectory()` 가 `"../../"` 리터럴 — **최우선**

`Source/Runtime/Core/FileIO/FileHelper.cpp:298-306`

```cpp
const PString& HFileHelper::EngineDirectory()
{
    static PString enginePath;
    if (enginePath.Empty()) { enginePath = "../../"; }
    return enginePath;
}
```

Bin / Build / Content / Config / Source / ThirdParty / Temp / CodeGen / Shader 9개 함수가 전부 여기서 파생된다(`FileHelper.cpp:309-487`). 즉 **"엔진 루트"의 정의가 "프로세스 CWD 의 두 단계 위"** 다. 게임이 `D:\Games\MyGame` 에 있으면 게임의 PreBuild 는 `D:\Games\MyGame\` 를 엔진 루트로 착각한다.

**해야 할 일**
1. 루트 2개로 분리: `EngineDirectory()` / `ProjectDirectory()`.
2. 해석 우선순위: `--engine=` / `--project=` 인자 → 환경변수 `JGENGINE_ROOT` → CWD 에서 위로 올라가며 찾은 `*.jgproject` 의 `EngineRoot` → 폴백 `"../../"`(엔진 단독 모드).
3. 파생 함수를 소속에 따라 재배치.

| 엔진 소유 (읽기 전용) | 프로젝트 소유 (쓰기) |
|---|---|
| `EngineSourceDirectory`, `EngineRuntime/Editor/ProgramsSourceDirectory`, `EngineThirdPartyDirectory`, `EngineBuildDirectory`, `EngineShaderDirectory`, `EngineContentDirectory` | `ProjectBinDirectory`, `ProjectTempDirectory`, `ProjectCodeGenDirectory`, `ProjectConfigDirectory`, `ProjectContentDirectory`, `ProjectSourceDirectory` |

호출부는 생각보다 적다 — 런타임 5곳, 툴 6개 파일:

- `Asset/AssetDatabase.cpp:101`, `Asset/AssetPath.cpp:53,88` → 엔진 Content + 게임 Content 둘 다 마운트하도록
- `Graphics/Classes/ShaderLibrary.cpp:10` → 엔진 Shader + 게임 Shader
- `Core/Misc/Module.cpp` `HModuleSystemInfo::Get/Set` → **프로젝트** CodeGen 으로

크기: **中**. 위험도 낮음(컴파일러가 전부 잡아줌).

### B. premake 템플릿이 통짜 + workspace 이름 하드코딩

`Source/Programs/JGBuildTool/Template/BuildTemplate.lua`

```lua
local GEN_PROJECT_FILE_PATH = "Temp/ProjectFiles/"   -- :1
local BIN_PATH              = "Bin/%{cfg.buildcfg}/" -- :2
local OBJECT_PATH           = "Temp/Obj/%{cfg.buildcfg}/"

```

전부 "lua 스크립트가 엔진 루트에 있다"는 전제의 상대 경로다. 그리고 workspace 가 1개뿐이라 **솔루션을 2종류 만들 수 없다.**

생성 쪽도 같은 전제다 — `BuildTool.cpp:260-271` 이 `includedirs` 에 `"Source/"`, ThirdParty 경로를 문자열로 박고, `ModuleInfo.h:119-120` 이 CodeGenPath 를 만들 때 `EngineDirectory()` 의 **문자열 길이만큼 앞을 잘라내는** 방식을 쓴다.

```cpp
HFileHelper::CombinePath(HFileHelper::EngineCodeGenDirectory(), ModuleName + "/", &CodeGenPath);
CodeGenPath.Remove(0, HFileHelper::EngineDirectory().Length());   // "../../" 길이만큼 자름
```

`EngineDirectory()` 가 절대 경로가 되는 순간 이 코드는 깨진다. **A 를 고치면 반드시 같이 고쳐야 하는 자리다.**

**해야 할 일**
1. 템플릿을 3조각으로 분리
   - `Build/Premake/JGCommon.lua` — Config 함수, `SetCPPProjectConfig` 등 공용 정의. `ENGINE_ROOT` / `PROJECT_ROOT` 변수를 참조.
   - `Build/Premake/JGEngineModules.lua` — **엔진 모듈 프로젝트 정의(생성물)**. `include` 가능한 형태.
   - 프로젝트별 루트 스크립트(생성물) — `workspace "<ProjectName>"` + `ENGINE_ROOT` 설정 + 위 둘 include + 자기 모듈 정의.
2. `generateBuildScriptInternal`(`BuildTool.cpp:236-394`)에서 경로를 낼 때 엔진 맵이면 `ENGINE_ROOT ..`, 유저 맵이면 `PROJECT_ROOT ..` 프리픽스를 붙인다. 함수에 루트 종류 인자를 하나 추가하면 되는 수준.
3. `module.json` 의 `ModulePath` 를 **자기 루트 기준 상대경로**로 재정의한다(현재 `"Source/Runtime/Core/"` 는 엔진 루트 기준 — 의미는 같지만 문서상 명확히 해야 유저 모듈이 헷갈리지 않는다).

크기: **大**. 이 작업의 중심.

### C. 산출물 디렉터리가 공유됨 → 엔진을 소스로 빌드할지 바이너리로 붙일지 결정 필요

`BIN_PATH` 가 스크립트 기준 `Bin/<Config>/` 이고, 런타임은 DLL 을 **이름만으로** 로드한다. 게임 exe 가 `D:\Games\MyGame\Bin\DevelopGame\` 에서 돌면 엔진 DLL 도 거기 있어야 한다.

**선택지**

| | (A) 게임 솔루션이 엔진을 소스로 포함 | (B) 엔진은 미리 빌드된 바이너리 |
|---|---|---|
| 게임 Bin | 엔진 프로젝트도 게임 Bin 으로 출력 | 엔진 Bin → 게임 Bin 복사(스테이징) 필요 |
| 빌드 시간 | 게임마다 엔진 전체 재빌드 | 짧음 |
| 엔진 디버깅 | 그대로 됨 | pdb·소스 매핑 별도 처리 |
| 코드젠 | 프로젝트 Temp 하나로 통일 | 엔진 코드젠 + 게임 코드젠 병합 필요 |
| 구현 난이도 | 낮음 | 높음 |

**권장: (A).** 목표 문장 "게임 솔루션 안에 엔진이 포함" 자체가 A 다. B(Installed Engine)는 나중에 얹을 수 있고, 지금 단계에서 병합 코드젠까지 떠안으면 완성이 멀어진다.

A 를 택하면: 엔진 프로젝트의 `targetdir` / `objdir` / `location` 이 전부 `PROJECT_ROOT` 기준이 된다. 엔진 소스 경로만 `ENGINE_ROOT` 기준. premake 는 상대경로를 알아서 계산하므로 `ENGINE_ROOT` 를 절대경로로 두면 가장 안전하다.

크기: **中** (B 를 정책으로 확정하기만 하면 코드는 B 항목에 흡수됨).

### F. HeaderTool ↔ BuildTool 순환 의존 (기존 이슈, 분리 작업에서 더 나빠짐)

`Document/Memory/2026-09-16_Programs_현황파악.md` 에 기록된 P1. HeaderTool 은 BuildTool 산출물(`module_system_info.json`)이 필요하고, BuildTool 의 premake 는 HeaderTool 이 만든 파일이 **디스크에 있어야** vcxproj 에 포함한다(글롭을 생성 시점에 전개하기 때문).

루트가 2개가 되면 "프로젝트 최초 생성 시 `module_system_info.json` 이 아예 없다" 는 상황이 상시화되어 **1회차 생성이 반드시 깨진다.**

**해야 할 일** — 기존 메모의 (B)안 권장: HeaderTool 이 `*.module.json` 을 직접 스캔해 코드젠 대상을 판단하게 하여 의존을 끊는다. 그러면 순서는 HeaderTool → BuildTool 1패스로 정리된다. 단 BuildTool 의 `HModuleSystemInfo::Set()` 은 유지해야 한다 — 런타임(`ObjectGlobalSystem.cpp:249`)이 읽는다.

크기: **中**. **B 작업보다 먼저 하는 게 좋다.**

### G. `headertool_arguments.json` 이 통째로 무시됨 — **선행 필수**

`Source/Programs/JGHeaderTool/Class/Arguments.h:38`

```cpp
virtual void ReadJson(PJsonData& json)          // ← const 없음, override 없음
```

`IJsonable::ReadJson` 은 `virtual void ReadJson(const PJsonData&)`(`Core/FileIO/Jsonable.h`). **시그니처가 달라 오버라이드가 성립하지 않는다.** 따라서 `headertool_arguments.json` 의 내용은 읽히지 않고 생성자 기본값(`EngineWorkDirectory = EngineSourceDirectory()`, `UserWorkDirectory = Source/Dummy`)이 항상 쓰인다.

엔진/게임 분리는 **이 인자 파일로 프로젝트 경로를 넘기는 설계**이므로, 이게 고쳐지지 않으면 이후 작업이 전부 무반응으로 보인다. `const ... override` 한 줄. **가장 먼저 고칠 것.**

크기: **極小**. 효과 큼.

### I. `Source/Runtime/Game` 모듈의 정체성 충돌

`Source/Runtime/Game/Main.cpp` 는 `int dummy()` 뿐이고 `GameFrameWorks/Main.cpp` 도 동일하다. 그런데 `Game` 은 SharedLib 로 등록되어 `Game.dll` 이 빌드되고 `module_system_info.json` 의 코드젠 대상에도 들어가 있다.

유저 게임 모듈 이름이 `Game` 이면 **엔진의 `Game` 모듈과 이름이 충돌**한다(DLL 이름으로 로드하므로 실제 충돌). 분리 전에 정리 필요:

- `Source/Runtime/Game` → **삭제**하거나 게임 템플릿 쪽으로 이동
- `GameFrameWorks`(World / Actor / Component 예정) → 엔진 런타임으로 유지가 맞음

크기: **小**. 결정만 하면 됨.

## 6. 리스크 / 주의

- **지금 Graphics 모듈이 컴파일되지 않는다.** `Document/Graphics_TODO.md` Phase 1 의 1-2 ~ 1-6 이 미완이라 DevelopEngine 전체 빌드가 Graphics 에서 실패하고 GUI·Devkit·Editor 계열은 빌드 시도조차 되지 않는다. 빌드 시스템을 고치는 동안 "내가 깼나, 원래 깨져 있었나"를 구분할 수 없다.
  → **Graphics 1-2 ~ 1-5(작은 항목 4개)를 먼저 끝내 초록 기준선을 만들고 시작하는 것을 권한다.** 최소한 Phase 1 의 회귀 테스트(생성물 동일성 비교)는 빌드 성공 여부와 무관하게 가능하니, 그 안전망만은 반드시 먼저 세울 것.
- **premake 글롭 전개 시점** — `files { path .. "**.cpp" }` 는 프로젝트 생성 시점에 디스크를 훑어 파일 목록을 vcxproj 에 박는다. 코드젠 파일이 아직 없으면 조용히 빠진다. 새 게임 프로젝트의 1회차 생성에서 반드시 밟게 되는 함정이다 (F 와 연결).
- **`Bin/` 이 git 추적 중**(99개 파일)이라 툴 exe 를 다시 빌드할 때마다 바이너리 diff 가 생긴다. 부트스트랩 때문에 필요한 구조이긴 하나, 분리 후에는 "엔진 배포본에 툴 exe 포함" 이라는 의미로 정리해두는 게 좋다.
- **C4819 인코딩 경고** — BOM 없는 UTF-8 소스가 CP949 로 읽히는 문제. 게임 템플릿 소스에도 그대로 재현된다. 템플릿의 Config 함수에 `buildoptions { "/utf-8" }` 를 넣으면 한 번에 정리된다 (`Graphics_TODO.md` 1-6 과 동일 작업).
- `jgengine.lua` / `JGEngine.sln` / `Temp/CodeGen/*` 는 **전부 생성물이다.** 직접 수정하지 말 것 — 다음 PreBuild 에서 날아간다. 고칠 곳은 `Template/BuildTemplate.lua` 와 BuildTool 코드.
