## 설계 (확정한 그림)

### 원칙
1. **요청과 실행 분리.** `Request*`는 어느 스레드, 프레임의 어느 시점에 불러도 스테이징만 만들고 대기 목록에 넣는다. API가 호출 순서에 의존하지 않는다.
2. **실행은 정해진 자리에서만.** 업로드는 프레임 제출의 맨 앞, 리드백은 맨 뒤. 같은 프레임에 요청한 업로드는 그 프레임의 드로우보다 먼저, 리드백은 그 프레임의 드로우 결과를 담는다.
3. **완료는 펜스 값으로.** 리드백 콜백은 다음 BeginFrame에 메인 스레드에서 불린다(실패해도 한 번은 불리며 `HTexturePixels::IsValid()`가 false).
4. **`ReadbackTextureImmediate`만 예외.** 전용 리스트 쌍을 `PCommandQueue::ExecuteImmediate`로 따로 제출하고 GPU 완료를 기다린다. 프레임 리스트의 기록과 리소스 상태 추적은 건드리지 않는다.

### 프레임 타임라인 (`PDirectX12API`)
```
BeginFrame : 큐 Begin(지난 제출 펜스 대기) → ResourceStagingManager.BeginFrame(펜스 지난 리드백 Map/언패킹/콜백)
프레임 중  : 드로우 기록 (Default 우선순위 리스트)            ← Request*는 어디서든
EndFrame   : RecordUploads (Upload 리스트, 맨 앞)
             FrameBuffer.Update (Present 리스트, 맨 뒤)
             RecordReadbacks (Readback 리스트, 드로우 뒤)
             큐 End (우선순위 순서로 Close·보류 배리어 확정·Execute·Signal)
             OnFrameSubmitted(펜스 값) → 이번에 제출된 리드백에 펜스 값을 찍는다
             Present
```
커맨드 리스트 우선순위(`ECommandListPriority`, `CommandQueue.h`): `Upload`=0 < `Default`=1000 < `Readback`=MAX-1 < `Present`=MAX. `RequestCommandList`의 기본값이 `Default`로 바뀌었다(이전 0). 같은 버킷 안의 리스트 순서는 정해져 있지 않으므로 서로 의존하는 작업은 다른 버킷에 둔다.

### ReadbackTextureImmediate 절차
1. 검사: 메인 스레드, 텍스처 유효, 지원 포맷(깊이 제외). 프레임 안(BeginFrame~EndFrame)이면 경고 1줄(스톨이 프레임 시간에 더해지는 걸 보이게).
2. 준비: 풋프린트 계산 → READBACK 스테이징 생성(비동기 경로와 같은 `createReadbackRequest`).
3. 기록: 전역 상태 맵에서 텍스처의 현재 상태를 읽어 둔다(열린 프레임 리스트는 커밋 전이라 이 값이 GPU 실제 상태). 같은 텍스처의 **대기 업로드를 먼저** 같은 리스트에 기록하고 대기 목록에서 뺀다. 배리어(→COPY_SOURCE) → `CopyTextureRegion` → 원래 상태로 복원.
4. 실행: `ExecuteImmediate` — 큐 뮤텍스 → `Close(pend)`로 첫 사용 배리어 확정 → 그 리스트만 `ExecuteCommandLists` → 펜스 Signal → 완료 대기 → 두 리스트 Reset. 프레임 펜스 값(`_fenceValue`)은 바꾸지 않는다.
5. 회수: Map → 행 피치 제거 → Unmap → 스테이징 해제 → `HTexturePixels` 반환.

돌려주는 값은 GPU가 마지막으로 완료한 내용(렌더 타깃이면 지난 프레임). 같은 큐라서 그 시점에 큐에 들어가 있던 작업이 모두 끝나야 돌아온다. 지금 구조(프레임마다 Begin에서 펜스 대기)에서는 프레임 중간 호출 시 큐가 비어 있어 복사 시간만 기다리지만, 프레임 파이프라이닝(5-5)이 들어가면 진행 중인 프레임을 전부 비우는 진짜 스톨이 된다. 그래서 일반 코드용 기본 경로는 `RequestTextureReadback`다.

### 이름 규칙
`Request*` = 비동기 요청(`RequestBufferUpload`, `RequestTextureUpload`, `RequestTextureReadback`), `*Immediate` = 동기 실행(`ReadbackTextureImmediate`). 함수 이름만 보고 스톨 여부를 알 수 있게 한다.

## 이번 세션에서 잡은 버그 / 발견 (원인 → 수정)
1. **1080p 리드백 직후 종료 코드 3, 로그 없음** — 엔진 메모리 풀은 블록 하나가 최대 2MB(`EMemorySize::_1_GB`)라 `HList<uint8>` 16.5MB 할당이 `MemoryQueues.at()`에서 `std::out_of_range`를 던져 프로세스가 죽었다. → 큰 픽셀 버퍼(`HTexturePixels::Data`, DevScene RGBA 변환 버퍼, `JGTexture` 압축 작업 버퍼)는 `std::vector`. 풀 자체는 5-23으로 등록.
2. **스테이징 리소스 이름이 "(null)"로 등록** — `PString::Format`이 `_rawString`에 직접 써서 해시 코드가 NULL_ID → `PName` 변환이 NAME_NONE. `operator==`도 Format 결과끼리 항상 참이었다. → Format 끝에 `updateHashCode()`(5-24).
3. **`HList::swap` 컴파일 오류 C2678** — `HAllocator`에 `operator==`가 없어 `std::vector`의 swap/move 대입(할당자 비교)이 컴파일되지 않는다. → 대기 목록은 복사 뒤 `clear()`.
4. **업로드와 드로우가 같은 우선순위 버킷(0)** — 이전 `InitializeByMemory`는 Base 리스트(우선순위 0)에 복사를 기록했고 드로우 리스트도 0이라 `HHashMap` 순회 순서에 따라 실행 순서가 임의였다. 또 업로드 뒤 텍스처가 COPY_DEST 상태로 샘플링됐다(디버그 레이어는 GBV 없이는 잡지 않음). → 업로드는 `Upload` 버킷, 드로우는 `Default`, 업로드 뒤 PSR|NPSR 전이.
5. **5-12** 버퍼 크기 변경 시 개수 0 / 구조화 버퍼 0바이트.
6. **도구 메모** — Bash 툴의 heredoc은 약 6KB를 넘으면 명령이 잘려 "unexpected EOF"가 난다. 큰 파일은 Write 툴로 쓴다. 루트(`/`)에는 임시 파일을 만들 수 없다(스크래치 폴더 사용).

## 2026-09-21 이름 변경 2 — 리드백 API
사용자 결정으로 언리얼식(대상 + 동작) 이름으로 바꿨다. 원래 이름은 `RequestReadPixels` / `ReadPixelsImmediate` / `HOnReadPixelsComplete`였다(이 문서의 이전 절에 나오는 새 이름은 sed로 일괄 치환한 것).
- `RequestTextureReadback(texture, callback)` — 비동기. 나중에 `RequestBufferReadback(buffer, callback)`이 짝으로 들어온다.
- `ReadbackTextureImmediate(texture, outPixels)` — 동기·도구용. 짝은 `ReadbackBufferImmediate`.
- `HOnTextureReadbackComplete` — 완료 콜백. 결과 타입 `HTexturePixels`는 그대로.
- 내부 업로드 요청도 같은 어순으로: `RequestBufferUpload`, `RequestTextureUpload`.
이유: "Pixels"는 결과물(텍스처 이미지)에 붙은 이름이라 버퍼 리드백이 들어오면 짝이 어긋나고, D3D12 용어(READBACK 힙, ResourceStagingManager)와도 맞지 않았다. `Request*` = 비동기, `*Immediate` = 동기 규칙은 유지.
