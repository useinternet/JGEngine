## 3. 제안 설계

### 3-1 API

```cpp
// HGameplaySessionConfig
int32 MaxSessionDataBytes = 64 * 1024;   // 세션 데이터 전체(키 + 값 바이트 합)

// PGameplaySession — 읽기 · 알림. 방장 · 참가자 · 싱글 모두 같은 함수 (화면 코드가 한 길)
const PString* FindSessionData(const PName& key) const;      // 없으면 nullptr (FindSlot 과 같은 모양) — 요청서의 GetSessionData
const HList<HGameplaySessionDataEntry>& GetSessionData() const;   // 전체 (디버그 표시 · 검사)
HMulticastDelegate<const PName&> OnSessionDataChanged;         // 바뀐 키(지움 포함). 방장도 자기 Set 에 받는다

// PGameplayHostSession — 쓰기는 권한 쪽만 (클라에는 함수가 없다)
bool SetSessionData(const PName& key, const PString& value);   // 빈 키 · 크기 초과면 false + Warning, 이전 값 유지. 같은 값이면 아무것도 안 함
bool RemoveSessionData(const PName& key);
void ClearSessionData();
```

| 결정 | 이유 |
|---|---|
| 키 → 값(글자) 여러 개, 덩어리 하나 아님 | 덩어리 하나는 키 하나로 된다. 시나리오 선택 · 캠페인 기록처럼 따로 바뀌는 값은 따로 보내는 편이 싸다 |
| 값은 `PString`(보통 JSON) | 게임이 이미 캠페인 기록을 JSON 글로 다룬다. 엔진은 내용을 해석하지 않는다 |
| 저장은 `HList`(넣은 순서) | 키가 몇 개뿐. `PName` 해시 · 순서가 기계마다 달라도 상관없게 목록으로 두고 선형으로 찾는다 |
| 쓰기는 호스트 클래스에만 | 권한이 형으로 갈린다. 게임은 `HostSession` 이 돌려준 세션이나 `RawDynamicCast<PGameplayHostSession>(GetSession())`(엔진이 이미 쓰는 방식, `GameInstance.cpp:127`) |
| 묶어서 바꾸기 API 없음 | 함께 바뀌어야 하는 값은 한 키(JSON 하나)에 넣는다. 키 두 개를 차례로 바꾸면 참가자가 그 사이 상태로 알림을 한 번 받을 수 있다(보통 같은 틱에 둘 다 도착) |

### 3-2 메시지 · 프로토콜

| 항목 | 내용 |
|---|---|
| 새 종류 | `EGameplayNetMessage::SessionData`(호스트 → 전원). `Ping` 뒤 · `Count` 바로 앞에 두어 기존 종류 번호를 바꾸지 않는다 |
| 본문 | `HGameplayNetSessionData { HList<HGameplaySessionDataEntry> Entries; }`, 항목 `{ Key, Value, bRemoved }`. 바뀐 항목만 보낸다 |
| `Welcome` | 필드 `SessionData`(전체 목록) 추가. 클라는 이것으로 표를 통째로 바꾼다 |
| 키 직렬화 | 글자로 쓴다. 빈 키(NAME_NONE)는 `SetSessionData` 가 거부 — PName 을 그대로 JSON 에 쓰면 NAME_NONE 이 `"(null)"` 로 왕복한다(현황 §5, Phase 5 함정) |
| 버전 | `HGameplayNetProtocol::Version` 1 → 2 |
| 압축 | 하지 않는다(64 KB 상한). zlib 은 지금처럼 Document 만 |
| 순서 | 같은 키는 마지막 값 — 피어마다 TCP 한 줄 + 호스트 한 스레드라 보낸 순서대로 도착한다 |

### 3-3 동작

| 상황 | 호스트 | 참가자 |
|---|---|---|
| 값 정하기 · 지우기 | 표 갱신 → 연결된 참가자에게 `SessionData` → `OnSessionDataChanged(key)` | 받으면 표 갱신 → `OnSessionDataChanged(key)`. 게임 메시지와 달리 보관하지 않고 바로 적용(GameMaster 와 무관) |
| 나중 참가자 | `Welcome` 에 그 순간 전체 표 | 슬롯 표 → 세션 데이터 → `OnSlotsChanged` → 키마다 `OnSessionDataChanged` → (월드가 있으면) 이동 |
| 핸드셰이크 중(연결 됨, Hello 전)에 바뀜 | 그 피어는 아직 슬롯이 없어 방송을 못 받지만, `Welcome` 이 그 뒤 표로 만들어지므로 빠짐 없음 | — |
| 재접속(같은 토큰) | `Welcome` 전체 | 끊긴 동안은 마지막 값을 그대로 읽는다. `Welcome` 으로 통째로 바꾸고, 끊긴 사이 바뀐 키 · 지워진 키마다 알림 |
| 판 진행 중 | 언제든 정할 수 있다. 명령 순번 · 체크섬과 무관 | 진행 중 입장은 `Welcome`(데이터) → `Document` 순서 |
| 월드 이동 | 유지(세션 것) | 유지 |
| 세션 교체(Host · Join · Leave) | 새 세션은 빈 표. 방장은 방을 연 뒤 넣는다 | 같음. Leave 하면 방장의 방 정보는 사라진다 |
| 싱글(Standalone) | 정하기 · 읽기 · 알림이 로컬로만 | — |
| 세션 닫힘 | — | 마지막 값을 계속 읽을 수 있다(닫힘은 `OnClosed` 로 게임이 처리) |
| 게임 인스턴스 교체 | 세션째 넘어가 유지(`replaceGameInstance`) | 같음 |

세션 교체 때 표를 옮기지 않는 이유: 옮기면 참가자가 Leave 할 때 방장의 방 정보가 참가자의 싱글 세션에 남는다. "새 세션은 빈 표" 한 규칙이 단순하다.

### 3-4 체크섬 · 결정론

- 세션 데이터는 GameMaster 상태 밖에 있다 → 체크섬 · 문서 · 순번에 들어가지 않는다. 불일치 검출 · 덤프 · 재동기는 그대로다.
- 대신 **규칙 코드(규칙 · 흐름 · 에이전트)는 세션 데이터를 읽지 않는다.** 기계마다 도착 시점이 다르다 — 참가자는 게임 메시지를 GameMaster 가 붙을 때까지 보관하지만 세션 데이터는 바로 적용한다. 판에 영향을 주는 값(시나리오 · 난이도)은 지금처럼 방장이 판을 시작할 때 초기 상태에 넣는다. 세션 데이터는 화면용이다.
- 엔진이 막을 수는 없다. API 주석, 생성 가이드(DevOps) 4절 규칙 표 한 줄, 게임 알림으로 지킨다.

## 8. 게임 쪽에 알릴 것 (결정 뒤 총괄이 전달)

- 요청서 "엔진 현황"은 코드와 맞다.
- API 이름은 `FindSessionData(key)`(없으면 nullptr, `FindSlot` 과 같은 모양) — 요청서의 `GetSessionData`. 쓰기는 `PGameplayHostSession::SetSessionData` · `RemoveSessionData`.
- 규칙 코드는 세션 데이터를 읽지 않는다. 판에 쓰는 값(시나리오 · 난이도 · 캠페인 기록)은 지금처럼 판 시작 값에 넣고, 세션 데이터는 방 화면 표시에 쓴다.
- 방장은 `HostSession` 이 돌려준 세션에 넣는다. Host · Join · Leave 로 세션이 바뀌면 표는 비어서 시작한다.
- 함께 바뀌어야 하는 값(예: 시나리오 + 난이도)은 한 키(JSON 하나)에 넣는다.
- 반영되면 엔진을 받은 뒤 게임을 다시 빌드하고 패키지를 다시 쿠킹한다. 옛 패키지와는 같이 할 수 없다("protocol" 거절).
- 게임 쪽 우회(메뉴 월드 방 GameMaster)는 넣지 않는 것이 맞다(§3-7).
