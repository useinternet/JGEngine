## 0. 구조 요약

- **세션이 권한 경로의 유일한 입구다.** `PGameMaster::Submit` 은 세션만 부른다. 입력(컨트롤러 · AI) → 세션 → GameMaster → 관찰자 → 연출, 한 방향 고리다.
- **세션은 두 종류다.** 호스트 세션(싱글플레이 = 원격 참가자 없는 호스트, 리슨 서버)과 클라 세션. 싱글플레이가 호스트 경로를 그대로 탄다.
- **게임 규칙 · 연출 코드는 넷 모드를 모른다.** 게임이 멀티 때문에 따로 하는 일은 "초기 상태 구성과 시작은 권한 쪽에서만"과 "행동자 → 조작 주체 함수" 둘이다.
- **세션은 `JGGameInstance` 가 소유한다**(월드가 바뀌어도 연결 유지). GameMaster 는 지금처럼 월드가 소유하고, 세션에는 붙었다 떨어진다.
- **전송은 바이트만 안다.** `INetTransport` 아래는 게임을 모르고, 위는 TCP 인지 루프백인지 모른다. 전부 메인 스레드 폴링이다.

## 1. 구조 선택

| 지점 | 채택 | 대안 | 이유 |
|---|---|---|---|
| 세션 소유자 | `JGGameInstance` | 월드 · GameMasterActor | 로비는 월드 전에 있고, 월드 이동 중에도 연결이 살아 있어야 한다 |
| 모드 구현 | 호스트 세션(Standalone · ListenServer) + 클라 세션 | 모드마다 클래스 3개 / 한 클래스 안 분기 | 싱글이 호스트 경로를 그대로 타서 멀티 경로 버그가 싱글에서 드러난다. 호스트와 클라는 가진 상태(슬롯 표 · 명령 줄 vs 승인 대기 명령)가 달라 나눈다 |
| 권한 입구 | 세션만 `Submit` | GameMasterActor 가 `Submit`(지금) | 명령 순서를 정하는 곳이 하나여야 복제가 된다 |
| GameMaster 연결 | 붙기 / 떼기 (붙어 있는 동안 참조) | 세션이 GameMaster 소유 | GameMaster 수명을 월드 · 게임 코드가 정하는 지금 구조를 그대로 둔다. 약참조 대신 명시적 떼기(Core 약참조 주의, 리뷰 D11) |
| 스레드 | 메인 스레드 폴링 | 네트워크 스레드 | 커널이 단일 스레드이고 턴제 트래픽은 프레임당 폴링으로 충분하다 |
| 순번 | 상태의 `Sequence` | 세션 전용 카운터 | 커널이 검증 통과 명령마다 1 올린다(`GameplayRuleEngine.cpp:136`, 거절은 안 올림). 클라는 적용 후 같은 값인지로 한 번 더 확인 |

## 2. 계층 · 소유

```
프로세스 (JGLauncher / JGConsole)
└ HGameFrameWorksModule ─소유▶ JGGameInstance ─────────────────────── 프로세스 수명
                                 ├ 소유▶ PGameplaySession ──────────── 호스트 · 접속 ~ 떠날 때
                                 │         ├ 소유▶ INetTransport       (TCP · 루프백 · Standalone 은 없음)

                                 └ 소유▶ PWorld ─────────────────────── LoadWorld ~ UnloadWorld
                                           ├ JGGameEntryActor (게임 파생)   규칙 등록 · (권한이면) 초기 상태 + 시작
                                           ├ JGGameMasterActor ─소유▶ PGameMaster
                                           │     BeginPlay: 세션에 붙이기 · EndPlay: 떼기 · 이벤트 → 큐 재생
```

| 객체 | 수명 | 해제 |
|---|---|---|
| `PGameplaySession` | 호스트 시작 · 접속 ~ 세션 종료 | `JGGameInstance` 종료(모듈 `ShutdownModule` 안)에서 전송 · 소켓까지 정리 |
| `INetTransport` | 세션과 같음 | 세션이 해제 |
| `PGameMaster` | 월드 안 GameMasterActor 와 같음(지금 그대로) | 떼기 후 월드가 해제 |

## 4. 구조 불변식

| # | 불변식 | 이유 |
|---|---|---|
| 1 | `PGameMaster::Submit` 은 세션만 부른다(자체 테스트 제외). 나머지는 읽기만(`GetState` · `Validate` · `EnumerateLegal` · `GetPendingChoice`) | 순서가 한 곳에서 정해져야 결정론 복제가 된다 |
| 2 | 연출은 권한을 막지 않는다. 입력 정책(Block · Buffer)은 로컬 입력이 세션에 들어가기 **전에만** | 원격 · 승인 명령이 연출을 기다리면 한 사람의 연출 속도가 전원을 묶는다(`GameMasterActor.cpp:101, 116, 124`) |
| 3 | 게임 규칙 · 연출 코드는 넷 모드를 모른다 | 싱글에서 검증한 코드가 멀티에서 그대로 돈다 |
| 4 | 규칙 등록은 모든 기계, 초기 상태 구성과 시작은 권한 쪽(호스트 세션)만 | 등록은 코드라 기계마다 같다. 초기 상태는 호스트가 만든 것을 받는다 |
| 5 | AI 는 호스트 세션이 돌린다(싱글 포함) | AI 구동은 지금 자체 테스트에만 있다(`GameMasterSelfTest.cpp:565`). 월드 쪽 자리가 비어 있다 |
| 6 | 세션은 한 번에 GameMaster 하나에 붙는다. 붙기 전에 온 게임 메시지(시작 · 승인 · 문서)는 보관했다가 붙을 때 적용 | 월드 로드 중에 메시지가 도착한다 |
| 7 | 전부 메인 스레드. `JGGameInstance::Tick` 맨 앞에서 세션 폴링, 그다음 월드 틱 | 같은 프레임에 새 이벤트가 연출로 넘어간다. 스케줄 작업을 늘리지 않는다(리뷰 C16) |

## 6. 게임 코드와의 접점

| 게임이 하는 것 | 어디서 | 넷 모드별 차이 |
|---|---|---|
| 규칙 · 컴포넌트 등록 | 엔트리 액터 (GameMaster 설정) | 없음 — 모든 기계 |
| 초기 상태 구성 + `Session.StartGame(seed)` | 엔트리 액터 | `IsAuthority()` 일 때만 |
| 행동자 → 조작 주체 함수 | GameMaster 설정 (`SetTeamOfActorFunction`, `GameMaster.h:99`) | 없음 |
| 슬롯 ↔ 조작 주체 배정 | 로비 UI → 호스트 세션 | 호스트만 바꾼다 |
| 끊김 정책 | 세션 알림 콜백 | 대기 · 에이전트 대리 중 게임이 고른다 |
| 연출 · 입력 | GameMasterActor · 큐 · 컨트롤러 | 없음. 컨트롤러는 `IsLocallyControlled` 로 입력만 제한 |

## 7. 프로토콜

- 봉투 `{Type, Payload}`, 페이로드는 JSON(`IJsonable`). TCP 라 연결마다 순서 · 신뢰가 보장되어 재전송 · 순서 번호가 필요 없다.
- 호스트의 방송 순서 = 순번 순서. 클라는 받은 순서대로 적용한다.

| 분류 | 메시지 | 방향 |
|---|---|---|
| 연결 | `Hello{프로토콜 버전, 스키마, 이름, 재접속 토큰}` · `Welcome{슬롯, 규칙 지문, 월드, 진행 여부, 슬롯 표}` · `Refuse{사유}` · `Ping` | 클라 → 호스트 / 호스트 → 클라 |
| 로비 · 월드 | `SlotChanged` · `Travel{월드}` | 호스트 → 전원 |
| 시작 | `StartGame{시드, 규칙 지문, 초기 상태}` | 호스트 → 전원 |
| 명령 | `CommandRequest{clientSeq, 명령}` | 클라 → 호스트 |
| | `CommandAccepted{seq, 슬롯, clientSeq, 명령, 체크섬}` · `CommandRejected{clientSeq, 사유}` | 호스트 → 전원 · 보낸 클라 |
| 동기화 | `ResyncRequest` / `Document{seq, 문서}` | 클라 → 호스트 / 호스트 → 클라 |

## 8. 상태 기계

```
호스트 세션 : Standalone ─────────────────────────▶ Closed
              Listening ─▶ Lobby ⇄ Traveling ─▶ Playing ─▶ Closed
클라 세션   : Connecting ─▶ Handshaking ─▶ Lobby ⇄ Traveling ─▶ Playing ⇄ Resyncing ─▶ Closed
              (Traveling = 월드 로드 중, GameMaster 떨어져 있음 → 게임 메시지 보관)
호스트의 피어 : Handshaking ─▶ Joined(슬롯) ─▶ Disconnected(슬롯 유지, 토큰 대기) ─▶ Removed
클라의 로컬 명령 : Draft ─▶ Sent ─▶ Accepted | Rejected   (Sent 동안 다음 로컬 명령은 보내지 않고 보관)
```

## 9. 흐름

| 흐름 | 순서 |
|---|---|
| 시작 | 호스트 `LoadWorld` → 세션이 `Travel` 방송 → 전원 월드 로드 → 엔트리 액터가 규칙 등록 · GameMasterActor 가 세션에 붙음 → 호스트만 초기 상태 + `StartGame` → 방송 → 전원 `Start(seed)` |
| 명령 | 로컬 입력 → 입력 정책 → `SubmitLocal` → (클라면 전송) → 호스트 줄 → 소유 검사 → `Submit` → `CommandAccepted` 방송 → 클라 `Submit` → 체크섬 비교 → 관찰자 → 큐 재생 |
| 진행 중 입장 · 재접속 | `Hello(토큰)` → `Welcome` → (월드가 다르면 `Travel`) → `Document{seq}` → Import → seq 를 넘는 승인만 적용 |
| 불일치 | 체크섬 다름 → 양쪽 상태 JSON 덤프 → `ResyncRequest` → `Document` |
| 월드 이동 | 호스트 `LoadWorld` → `Travel` 방송 · 떼기 → 클라 따라 로드 → 붙기 → 보관 메시지 적용 |
| 끊김 | 전송 끊김 → 호스트: 피어 Disconnected + 게임 콜백 / 클라: 호스트가 사라지면 세션 Closed + 게임 콜백 |

## 11. 입력 자격 — 세션과 커널의 경계

- "지금 누가 명령을 낼 수 있나"는 두 층이 나눠 판단한다. **세션**: 보낸 슬롯이 그 명령의 행동자를 조작하는가(선택 대기 중이면 선택자). **커널**: 그 명령이 지금 규칙상 합법인가(`Validate`).
- 여러 사람이 같은 시점에 입력해도 호스트가 도착 순으로 줄 세우므로 커널에게는 연속된 명령일 뿐이다.
- 그래서 커널의 입력 모델(선택 대기가 한 명의 답을 받는지 여러 명의 답을 받는지)은 네트워크 구조와 독립이고, 세션의 소유 검사 모양도 같다. 네트워크 설계의 결정 항목이 아니다.
