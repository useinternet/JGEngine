# 2026-09-17 작업 기록 — 모듈 수명 관리 1~3 적용 (4단계 일부)

## 요청
4단계로 정리한 항목 중 1~3 적용.
1. Asset 모듈 로그 오타 / 2. 순회 중 컨테이너 변경 / 3. 연결 순서 기록 + 역순 Shutdown
(4번 "모듈 RefCount" 는 **미적용**)

## 결과
**적용 완료. 전체 빌드 성공(에러 0, 신규 경고 0), 실행 검증 통과(ExitCode 0).**

### 변경 파일 (3개)
- `Source/Runtime/Asset/AssetModule.cpp`
- `Source/Runtime/Core/Misc/Module.h`
- `Source/Runtime/Core/Misc/Module.cpp`

### 1. Asset 로그 오타
`JG_LOG(Graphics, ..., "Start/Shutdown Graphics Module...")` → `JG_LOG(Asset, ..., "Startup/Shutdown Asset Module...")`.
이 오타 때문에 앞선 조사에서 "ShutdownModule 이 두 번 호출된다"고 오진했었다.

### 3. 연결 순서 기록 + 역순 Shutdown  ★ 핵심
`GModuleGlobalSystem` 에 `HList<IModuleInterface*> _moduleOrder` 추가.

**기록 시점이 중요하다. 등록 시점이 아니라 `StartupModule()` 이 "끝난" 시점에 push_back 한다.**
`StartupModule()` 안에서 의존 모듈을 `ConnectModule` 하므로 의존 모듈이 먼저 기록되고
자신은 그 뒤에 기록된다. 그 결과 `_moduleOrder` 가 의존성 위상 순서가 되고, 역순이 곧 안전한 종료 순서다.

```
_moduleOrder = [Graphics, GUI, Asset, DevStatistics, DevConsole, Devkit, JGDev_Graphics]
역순         = [JGDev_Graphics, Devkit, DevConsole, DevStatistics, Asset, GUI, Graphics]
```

등록 시점에 기록했다면 `[JGDev_Graphics, Graphics, GUI, ...]` 가 되어 역순이 **틀린다**
(JGDev_Graphics 가 마지막에 내려가서, 이미 내려간 모듈들을 또 Disconnect 하게 된다).

### 2. 순회 중 컨테이너 변경 제거
`Destroy()` 가 `_modulesByType` 을 range-for 로 돌면서 그 안의 `ShutdownModule()` →
`DisconnectModule()` 이 같은 맵을 erase 하고 있었다.
→ `_moduleOrder` 끝에서 **하나씩 빼내는** 방식으로 변경. 뺀 모듈은 맵에서도 먼저 지운다.
그래서 다른 모듈의 `DisconnectModule` 이 이미 내려간 모듈을 또 내리지 않는다.
공통 제거 로직은 `unregisterModule(IModuleInterface*)` private 헬퍼로 뺐다. (`_mutex` 를 이미 잡은 상태에서 호출)

### 추가로 고친 것 — 잠재 데드락 (작업 중 발견)
`DisconnectModule()` 이 `_mutex`(= `std::mutex`, **비재귀**)를 잡은 채
`moduleIf->ShutdownModule()` 을 호출하고 있었다.
그런데 `HJGDev_GraphicsModule::ShutdownModule()` 은 `DisconnectModule()` 을 6번 부르고,
`HJGEditorModule::ShutdownModule()` 도 1번 부른다. `FindModule()` 도 같은 뮤텍스를 쓴다.

→ **`DisconnectModule("JGDev_Graphics")` 또는 `DisconnectModule("JGEditor")` 를 부르면 즉시 데드락**이었다.
지금까지는 이 둘이 `Destroy()` 경로로만 내려가서 안 걸렸을 뿐이다.
잠금 범위를 맵 조작으로 축소하고 `ShutdownModule()` 은 잠금 밖에서 부르도록 고쳤다.
`Destroy()` 도 같은 규칙을 지킨다.

### 검증
- `JGEngine.sln` DevelopEngine|x64 전체 빌드 성공 (에러 0, 신규 경고 0)
- `JGLauncher.exe` 실행 → WM_CLOSE → **ExitCode 0**, `Memory Chunk Shutdown.` 까지 완주
- 종료 순서 로그 확인:
  ```
  Startup : Graphics → Asset → JGDev_Graphics
  Shutdown: Asset → Graphics → JGDev_Graphics(자신의 로그가 마지막)
  ```
  `Destroy()` 가 역순으로 JGDev_Graphics 를 먼저 집었고, 그 `ShutdownModule()` 안의
  수동 Disconnect(Devkit→DevConsole→DevStatistics→Asset→GUI→Graphics)가 돌았다.
  Asset 이 Graphics 보다 먼저 내려간다(= 의존성 역순). **이제 해시 운이 아니라 보장된 순서다.**

## 다음 작업자에게
- **4번(모듈 RefCount) 미적용.** `DisconnectModule()` 에 참조 카운트가 없어서,
  두 모듈이 같은 모듈을 Connect 한 상태에서 한쪽이 Disconnect 하면 나머지가 죽은 모듈을 쓴다.
  현재 Graphics 를 Connect 하는 곳: `JGDev_Graphics.cpp:36`, `JGEditor.cpp:38`, `CoreSystem.cpp:57`.
  JGEditor 와 JGDev_Graphics 가 같이 뜨면 바로 재현된다. 지금은 LaunchModule 이 하나뿐이라 안 걸린다.
- P3(그래픽스 API 를 GC 큐에서 빼고 동기 파괴)도 그대로 남아 있다.
  3단계의 null 가드가 무해화하고 있을 뿐, "GC FIFO 때문에 API 가 먼저 죽는다"는 구조는 그대로다.
- `HAssetModule::ShutdownModule()` 이 `GAssetDatabase` 를 UnRegister 하지 않는다. (StartupModule 에서는 Register 함)
- 그 외 미해결: `ResourceStateTracker.cpp` JG_LOG `{0}` 포맷, `HMemoryPool` 스레드 불일치 경고,
  `garbageCollectionInternal` 의 WeakCount 무시(Memory.cpp:92), `UAVBarrier` if/else 인자 반전
