# 2-5 검토: 값 타입에서 `IMemoryObject` 분리 (2026-09-29)

> **결정 (2026-09-29, 사용자): 하지 않는다.** 다시 열 조건도 두지 않는다. 4-1에서 GC 기반 클래스에 필드를 넣는 설계를 택하더라도 값당 +16B 수준이라 같은 이유로 작고, 그런 설계는 권장안도 아니다("오버 엔지니어링 하지 말 것").
>
> **재평가 (2026-09-29): 권장을 A에서 C(보류)로 바꾼다.** 사용자 질문("메모리 절감도 적은데 왜 빼야 하나")을 받고 다시 따져 보니 뺄 이유가 약하다.
> - 메모리: 값 하나당 8B이고 메인 청크 풀 할당이 336KB 규모라 절감 상한이 수십 KB다.
> - 타입 검사 구멍: 실제 오용은 `JGType` 4곳(GC 객체 수백 개 이하)뿐이고 해가 없다. 고치려면 `JGType`만 값으로 바꾸면 되고 상속을 끊을 필요는 없다.
> - 4-1 전제: 아래 결론 3과 §4의 "4-1 전에 결정"은 과장이었다. 권장 4-1(객체 앞 제어 블록)은 GC 기반 클래스에 필드를 두지 않으므로 2-5와 무관하다.
> - 7-1 뒤 `PName` 8B: 필요하면 7-1 안에서 `PName` 하나만 상속을 뺀다(1파일).
> - 버그 경로 확인: 가상 소멸자와 DLL 언로드가 얽히는 경로는 없다(`JGDevelopUnit::ReloadDevelopUnit`은 호출처가 없고, 모듈 DLL은 모든 시스템을 해제한 뒤 `CoreSystem.cpp:111`에서 언로드된다). 값 타입이 든 구조체를 바이트 단위로 해시하는 곳도 없다(`HHash::HashState`는 D3D 구조체에만 쓴다).
> - **다시 열 조건:** 4-1에서 GC 기반 클래스에 참조 카운트 같은 필드를 넣는 설계를 택할 때. 그때는 문자열·스마트 포인터가 모두 같이 커진다.

**처음 결론 (재평가 전)**
1. `IMemoryObject`는 "GC가 만들고 파괴하는 객체"의 표식인데 **값 타입 9개도 상속**하고 있다. 그래서 값마다 vptr 8B·가상 소멸자가 붙고, `Allocate<T>`의 타입 검사가 값 타입을 걸러내지 못한다(실제로 `JGType`을 GC 객체로 만드는 곳이 4곳).
2. 권장 **방안 A: 값 타입만 상속을 끊고 이름(`IMemoryObject`)은 그대로.** Core 12파일·약 40줄, GC 클래스와 GameFrameWorks는 손대지 않는다. 실수는 모두 컴파일 오류로 드러난다.
3. 메모리 절감은 작다(메인 청크 풀 할당이 336KB 수준). 가치는 **GC 타입 규칙을 정확히 하고 4-1(제어 블록)·7-1(`PName` 8B)의 전제를 만드는 것**이다. 그래서 4-1 전에 결정한다.

## 1. 지금 무엇이 섞여 있나

`IMemoryObject`(`Core/Memory/Memory.h:7`)가 주는 것은 가상 소멸자와 `Construct()`/`Destruction()` 훅뿐이고, 쓰는 곳은 GC 두 군데다.
- `GMemoryGlobalSystem::Allocate<T>`: `static_assert(is_base_of<IMemoryObject, T>)`(Memory.h:617), 생성 뒤 `Construct()`(Memory.h:646)
- GC 파괴: `((IMemoryObject*)ptr)->Destruction()` → `->~IMemoryObject()`(`Memory.cpp:99-100`)

훅 오버라이드는 `JGWidgetComponent::Construct`(WidgetComponent.h:55) 1곳, `Destruction` 0곳. 이 두 곳 말고 `IMemoryObject*`로 다루는 코드는 없다.
