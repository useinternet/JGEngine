## 3. 제안 설계

| 항목 | 제안 |
|---|---|
| 자리 | GFW `UI/GameUIElement.h/.cpp` · `GameUIManager.cpp` · `GameUIScrollBox.h/.cpp`. 새 파일은 없다(프로젝트 다시 생성 불필요). 다만 요소 헤더가 바뀌므로 게임 DLL 은 다시 빌드한다 |
| 켜기 | `PGameUIElement::SetWheelInput(bool)` / `IsWheelInput()`. 기본은 꺼짐이고, 스크롤 칸만 생성자에서 켠다 |
| 받기 | 요소 이벤트 `OnWheel(요소, 세로 칸 수, 가로 칸 수, 포인터 자리)`. 요청서 예처럼 파생 없이 람다로 받는다. 파생 요소는 가상 함수 `onWheel(세로, 가로, 자리) → bool` 을 쓴다. 기본 구현은 `OnWheel` 을 알리고 true. false 를 돌려주면 "안 받음"이라 바깥으로 넘어간다(예: 최대 배율에 닿은 확대 요소) |
| 길 · 우선순위 | 누르기와 같은 판정에서 위젯 루트까지의 길을 가장 안쪽부터 바깥으로 본다. 휠을 켜고 켜진(`SetEnabled`) 요소마다 `onWheel` 을 부르고, true 면 끝난다. 스크롤 칸은 이 길 위의 한 요소다 — `onWheel` = 지금의 `handleWheel` 이라 끝에 닿으면 false 로 바깥에 넘긴다. 지금 규칙(가장 안쪽 칸부터, 끝이면 바깥 칸, 꺼진 칸 제외)은 그대로이고, 코드는 "스크롤 칸만 모으기"에서 "길 위 요소 모두"로 바뀐다 |
| 소비 · 통과 | 누가 받으면 소비한다(에디터 카메라 줌 없음). 아무도 받지 않으면 지금과 같다 — UI 위면 소비, 빈 곳이면 통과, Menu 위젯이 떠 있으면 소비. 람다(`OnWheel`)로 받는 요소는 늘 소비한다(알림에는 돌려줄 값이 없다). 넘기고 싶으면 파생 `onWheel` 로 false |
| 끄는 동안 | 끄는 요소가 휠을 켰으면 그 요소가 먼저 받는다 — 지도를 끌면서 확대 · 축소. 안 켰으면 지금처럼 끄는 요소를 뺀 그 아래 길로 간다 — 카드를 끌면서 아래 목록 넘기기는 그대로 |
| 입력 받기 | 길이 누르기 판정이라, 휠 요소의 빈 곳(자식이 없는 자리)에서도 받으려면 `SetHitTestVisible(true)` 를 켠다. 끌기와 같은 규칙이고, 끄는 지도는 이미 켜져 있다. `SetWheelInput` 이 입력 받기를 몰래 켜지는 않는다(클릭이 아래 · 월드로 가던 화면이 바뀌지 않게) |
| 포인터 자리 | 캔버스 논리 단위(기준 해상도 좌표 — 끌기 이벤트 · `GetPointerPosition` 과 같다). 요소 자리는 `CanvasToLocal(자리)` 로 얻는다. 휠 처리 직전에 레이아웃을 다시 계산하므로(`HandlePointer` 앞머리 `UpdateLayout`, `GameUIManager.cpp:598`) 앞 휠에서 바꾼 배율 · 옮기기까지 반영된다 |
| 포인터 기준 확대 식 | 지도 요소의 그리기 변환(D-24)으로 확대한다. 포인터 아래 요소 자리 q = `CanvasToLocal(자리)`, 피벗 자리 P = 배치 사각형 왼쪽 위 + 피벗 × 크기, 지금 배율 s · 옮기기 t, 새 배율 s' 일 때 **t' = t − (s' − s) × (q − P)** 면 q 가 포인터 아래 그대로 남는다. 조상 변환은 q 에 이미 들어 있어 따로 셀 필요가 없다. 배율은 `pow(1.15, 세로 칸 수)` 처럼 칸 수에 비례하게 바꾼다 |
| 부드럽게(움직임 D-32) | 엔진은 칸 수만 넘긴다. 부드러운 확대는 게임이 배율(`Scale`)과 옮기기(`Translation`) 트윈을 한 동시 묶음(`Parallel`, 같은 길이 · 같은 이징)으로 재생하면 된다. 그러면 움직이는 동안에도 q 가 포인터 아래 그대로다(두 값이 같은 진행도로 함께 바뀌므로 위 식이 매 프레임 성립). 연달아 굴리면 목표 배율을 쌓고, 지금 값과 지금 q 로 목표 옮기기를 다시 구해 새 묶음을 건다. 같은 속성 겹치기 규칙으로 옛 묶음은 취소되고 새 묶음이 지금 값에서 이어 간다. 스크롤 칸의 `SmoothSeconds` 같은 엔진 쪽 부드럽게는 확대 · 이동 칸(선택지 (나))의 몫 |
| 헤드리스 | 자체 검사(`gameui.selftest`)로 길 · 소비 · 자리를 본다(GPU 불필요) |

쓰는 법(수락하면 게임 연출 구현에 보낼 내용):

```cpp
map->SetHitTestVisible(true);   // 끌기를 켰으면 이미 켜짐
map->SetWheelInput(true);
map->OnWheel.AddLambda([this](PGameUIElement& element, float32 wheel, float32 wheelHorizontal, const HVector2& pointer)
{
    zoomAt(element, element.CanvasToLocal(pointer), std::pow(1.15f, wheel));   // t' = t − (s' − s) × (q − P)
});
```

### 3.1 위험 · 주의

| 항목 | 내용 |
|---|---|
| 지도 안 스크롤 칸 | 지도 안에 스크롤 칸이 있으면, 그 칸이 끝에 닿은 뒤의 휠은 지도로 넘어가 확대된다. 스크롤 칸끼리와 같은 규칙이다(웹 브라우저 칸 → 페이지와 같고, 요청서도 이 규칙을 그대로 두라고 했다). 거슬리면 스크롤 칸에 "끝에서도 넘기지 않음" 선택을 더한다(지금은 문제가 없어 하지 않는다 — 보류 스크롤 칸 다음 단계(GG-H30) 후보) |
| 소수 칸 수 | 정밀 휠 · 터치패드는 0.25 칸 같은 작은 값을 자주 보낸다. 요청서 예의 "> 0 이면 1.15배"는 그런 장치에서 너무 빨리 확대된다 → 칸 수의 거듭제곱(`pow(1.15, wheel)`) |
| 호버 | 확대한 뒤 포인터 아래 요소가 바뀌어도 호버는 다음 포인터 이동 때 바뀐다(스크롤 칸과 같은 규칙). 에디터 뷰포트는 매 프레임 이동을 보내 바로 바뀌고, 게임 호스트는 다음 이동 때 바뀐다 |
| 람다가 붙잡는 것 | 요소의 `OnWheel` 람다가 그 요소나 조상의 `PSharedPtr` 를 잡으면 서로 붙잡아 풀리지 않는다 → 인자로 오는 요소를 쓴다(버튼 `OnClicked` · 스크롤 칸 `OnScrolled` 와 같은 주의) |
| 요소 크기 | 모든 요소에 이벤트 하나(목록 + 잠금 수, 수십 바이트)가 붙는다. 끌기처럼 관리자 이벤트로 두면 0 이지만, 위젯이 활성인 동안 구독 · 해지하고 요소로 걸러야 해서 요청서 쓰임(요소에 람다)과 맞지 않는다. 요소 이벤트는 요소와 함께 사라져 구독 정리가 필요 없다 |
| 스크롤 칸의 OnWheel | 스크롤 칸은 휠을 넘기기에 쓰고 `OnScrolled` 로 알린다. `OnWheel` 은 오지 않는다(설명에 적는다). 스크롤 칸에 `SetWheelInput(false)` 를 하면 그 칸은 휠을 바깥에 넘긴다 |
| 지금 화면 | 휠을 켜지 않은 화면은 결과가 그대로다 — 스크롤 칸 검사(게임 UI 445 검사)가 그대로 통과하는 것이 완료 기준 |
