# 게임 프레임워크 설계 방법론 사전 조사

작성 2026-09-21. 대상 커밋 `033e988` + 워킹 트리. 소스 변경 없음(코드 읽기 + 문헌 조사).
목적: `Source/Runtime/GameFrameWorks`(현재 빈 StaticLib. `Main.cpp` 주석 "World / Object / Data / Function")의 설계에 착수하기 전에, **게임 오브젝트 모델 · 조립 단위(프리팹/씬) · 수명 · 업데이트 · 통신 규약**을 어떤 방식으로 잡을지 상용 엔진 3종과 그 밖의 방법론을 비교한다. 각 방법론의 장단점을 정리하고, 마지막에 JGEngine 의 기존 자산(리플렉션·GC·모듈·에셋·스케줄러·Graphics)과의 적합도와 결정해야 할 항목을 붙였다. **결정은 사용자 몫**이고, 이 문서의 "제안"은 근거를 붙인 권고다.

## 0. 결론 요약

**방법론은 다섯 갈래로 정리된다.**
① 상속 계층(클래식 OOP) ② 컴포넌트 기반 게임 오브젝트(Unity GameObject/Component, UE Actor/Component) ③ 노드 트리(Godot Node/SceneTree, Roblox Instance, Flax Actor) ④ 데이터 지향 ECS(Unity Entities, UE Mass, flecs, Bevy, EnTT, Overwatch) ⑤ 프로퍼티/데이터 모델 중심(Dark Engine, Dungeon Siege, Our Machinery The Truth).
여기에 **횡단 축**이 걸린다 — 조립 단위를 클래스로 보나 프로토타입으로 보나(UE Blueprint vs Unity Prefab/Godot Scene), 수명을 무엇이 관리하나(트레이싱 GC / 참조 카운트 / 트리 소유 / 핸들+세대), 업데이트 순서를 누가 정하나, 통신은 참조·이벤트·메시지·쿼리 중 무엇인가, 저작 모델과 런타임 모델을 분리하나.

**상용 엔진은 전부 하이브리드다.** UE = 리플렉션 오브젝트(Actor/Component) + Mass(ECS). Unity = GameObject/Component + Entities(ECS, 저작 GameObject 를 베이킹). Godot = Node 트리 + 서버(RID 핸들 기반 데이터 지향 백엔드). 공통 결론은 **"사람이 다루는 게임플레이 계층은 객체 모델, 핫패스(렌더·물리·군중)는 데이터 지향"** 이고, 차이는 그 경계를 어디에 두는가다. 순수 ECS 를 게임플레이 계층까지 밀어붙인 사례(Overwatch, Bevy)는 있으나, 저작 도구와 관계(계층) 표현을 새로 세워야 했다.

**JGEngine 기반과의 적합도.** 이미 있는 것 — JGHeaderTool 리플렉션(`JGCLASS`/`JGPROPERTY`), `JGObject` + `IJsonable`(`SaveObject`/`LoadObject`), `PSharedPtr`/`PWeakPtr` + GC, DLL 모듈 시스템, GUID 에셋 DB(비동기 로드), 스케줄러 6 버킷 — 은 **UE 의 UObject 계열**이다. 이 자산을 그대로 살리는 것은 ②와 ③이고, ④는 리플렉션·GC 자산의 활용도가 낮고 저작 모델을 따로 만들어야 하며, ⑤는 구현 규모가 1인 개발 범위를 넘는다.

**제안(§5-2, 결정은 사용자).** 뼈대는 ②(World / Actor / Component). 계층은 ③처럼 **Actor 자체가 트랜스폼과 부모-자식을 갖고 컴포넌트는 트랜스폼이 없는** 절충(UE 의 SceneComponent 트리 대신 Flax·Unity 방식). 프리팹은 **"Actor 서브트리 에셋 + 인스턴스 오버라이드(리플렉션 프로퍼티 JSON 델타)"** 의 프로토타입 기반(Godot/Unity 식. JGEngine 에 CDO 가 없고 `IJsonable` 로 바로 구현 가능). 렌더·물리 같은 핫패스는 **핸들 기반 SoA 컨테이너**(Bitsquid 식 컴포넌트 매니저)로 Graphics 쪽에 두고 게임 오브젝트는 핸들만 참조. 착수 전 선결 조건은 `Document/Memory_현황분석_2026-09-21.md` §5 의 단계 A~B(스마트 포인터 대입, GC 파괴 순서, 풀 고갈)다 — 오브젝트 모델은 그 위에 얹히는 첫 대량 소비자가 된다.

**이번 조사에서 코드로 확인한 두 가지(§5-3).**
- **프리팹의 핵심 기계는 이미 있다.** `PSharedPtr<T>` 프로퍼티가 `[JGType, 데이터]` 쌍으로 **타입을 함께 저장**하고 읽을 때 구체 파생 클래스를 복원한다(`Json.h:695`, `1416`). `HList` 가 원소마다 이 경로로 위임하므로 **"컴포넌트·자식 목록을 가진 Actor 서브트리" 의 JSON 왕복에 새 직렬화기가 필요 없다.** GUI 가 같은 패턴(`Widget.h:44`)을 이미 쓰고 있다. 남는 일은 델타(오버라이드) 비교와 오브젝트 간 참조 해석뿐이다.
- **대신 확정 크래시 경로가 하나 있다(§5-4-9).** 컴포넌트 클래스를 **삭제·개명**하거나 해당 모듈이 로드되지 않은 채 프리팹을 읽으면 `getJGObject` 가 실패 대신 기반 객체를 반환(`Json.cpp:48`) → 캐스트 실패로 빈 포인터 → **빈 포인터 대입이 no-op 인 기존 버그**로 갱신 누락 → 널 역참조. 프레임워크 개발 중 클래스 개명은 상시로 일어나므로, 메모리 단계 **A-2 는 선택이 아니라 프리팹의 선행 조건**이다.

## 1. 비교 축과 용어

| 축 | 질문 |
|---|---|
| 조합(Composition) | 행동/데이터를 어떻게 붙이나 — 상속, 컴포넌트, 자식 노드, 컴포넌트 매니저, 시스템 |
| 계층(Hierarchy) | 트랜스폼 부모-자식을 무엇이 갖나 — 오브젝트, 컴포넌트, 관계(relationship) |
| 조립 단위(Prefab/Scene) | 재사용 템플릿을 어떻게 저장·인스턴싱·오버라이드하나 — 클래스 기반 vs 프로토타입 기반 |
| 수명(Lifetime) | 누가 소유하고 언제 죽나 — 트레이싱 GC, 참조 카운트, 트리 소유, 핸들+세대 |
| 업데이트(Tick) | 순서를 누가 정하나 — 암묵적, 그룹, 트리 순서, 시스템 스케줄 |
| 통신 | 직접 참조, 이벤트/델리게이트, 메시지, 시그널, 쿼리 |
| 메모리 배치·병렬 | 캐시 친화도, 잡 병렬화 가능성 |
| 저작·직렬화 | 인스펙터 자동화, 저장 포맷, diff/merge 친화 |
| 구현 비용 | 1인이 JGEngine 위에 세울 때의 비용 |

용어. **게임 오브젝트** = 월드에 존재하는 것의 단위(Unity GameObject, UE Actor, Godot Node, ECS Entity). **컴포넌트** = 오브젝트에 붙는 데이터/행동 조각. **시스템** = 컴포넌트 조합을 처리하는 함수(ECS). **프리팹** = 오브젝트(서브트리)의 재사용 템플릿. **CDO** = UE 의 Class Default Object(클래스 기본값 인스턴스). **저작 모델/런타임 모델** = 에디터에서 편집하는 표현과 게임이 실행하는 표현.

## 2. 상용 엔진 3종

### 2-1. Unity — GameObject + Component + Prefab

**구조**

```
Scene
 └ GameObject   (이름·태그·레이어·활성 여부. 빈 컨테이너. Transform 컴포넌트 필수)
     ├ Transform          (부모-자식 = 계층. 계층은 Transform 이 갖는다)
     ├ Renderer / Collider / Rigidbody …   (엔진 컴포넌트)
     └ MonoBehaviour 파생  (사용자 스크립트 = 데이터 + 행동. 한 오브젝트에 여러 개 가능)
```

- **Prefab** = GameObject 서브트리를 직렬화한 에셋. 씬에 놓인 인스턴스는 "원본 참조 + 바뀐 프로퍼티 목록(`m_Modifications`) + 추가/제거된 컴포넌트·오브젝트" 만 저장한다. 2018.3 부터 Nested Prefab(프리팹 안의 프리팹)과 Prefab Variant(프리팹을 베이스로 한 프리팹). 원본 수정은 모든 인스턴스에 전파되고 인스턴스 오버라이드는 유지된다.
- **ScriptableObject** = 씬에 놓이지 않는 데이터 에셋(설정, 테이블).
- **생명주기** Awake → OnEnable → Start → (FixedUpdate)* → Update → LateUpdate → OnDisable → OnDestroy. 매직 메서드 방식 — 엔진이 타입마다 어떤 메서드가 정의됐는지 리플렉션으로 한 번 조사해 캐시하고, 네이티브에서 관리 코드로 호출한다. 순서는 암묵적이며 Script Execution Order 로 타입 단위 우선순위만 준다.
- **통신** `GetComponent<T>()` 직접 참조, UnityEvent(인스펙터 바인딩), C# event, `SendMessage`(문자열 디스패치, 느림).
- **수명** 관리(C#) 객체와 네이티브 객체가 1:1 쌍. `Destroy()` 는 현재 업데이트 루프가 끝난 뒤 네이티브를 파괴하고, 관리 객체는 "죽은 껍데기" 로 남아 `== null` 이 true 가 되는 특수 비교로 처리된다. 씬 언로드가 소속 오브젝트를 파괴.
- **Entities(DOTS, 1.x)** 별도 ECS. 저작은 여전히 GameObject 로 하고(SubScene), **Baking** 이 GameObject + MonoBehaviour 를 Entity + Component 로 변환한다. 즉 저작 모델과 런타임 모델을 분리했다(§3-9).

**장점**
- 개념이 적다(오브젝트·컴포넌트·프리팹). 디자이너가 코드 없이 조합·오버라이드한다.
- 컴포넌트 단위 재사용이 실제로 잘 된다. 같은 스크립트를 어떤 오브젝트에도 붙일 수 있다.
- 프리팹 워크플로(원본 수정 전파 + 인스턴스 예외 유지 + 변형 + 중첩)가 성숙하고, 인스펙터가 오버라이드를 시각화한다. "씬에 놓인 것을 그대로 프리팹으로" 가 한 번의 드래그다.
- 리플렉션 기반 인스펙터/직렬화가 자동.

**단점**
- 오브젝트당 비용이 크다(네이티브 + 관리 이중 객체, 컴포넌트마다 `Update` 호출 경계 비용). 수만 개 동적 오브젝트는 Entities 나 수동 매니저로 우회해야 한다.
- 실행 순서가 암묵적이라 컴포넌트 간 의존이 생기면 "이번 프레임 값인가 지난 프레임 값인가" 문제가 잦다.
- 컴포넌트 간 참조가 스파게티가 되기 쉽다. 어떤 컴포넌트가 어떤 컴포넌트를 전제로 하는지 타입 시스템이 강제하지 않는다(`RequireComponent` 속성 정도).
- Transform 이 필수라 트랜스폼이 필요 없는 순수 논리 오브젝트도 트랜스폼을 갖는다.
- 프리팹 중첩이 깊어지면 오버라이드 출처 추적이 어렵다. YAML 이라 diff 는 되지만 fileID 참조는 사람이 읽기 어렵다.
- 저작(GameObject)과 고성능 런타임(Entity)이 두 세계로 갈라져 있고 상호운용이 번거롭다.

**JGEngine 교훈.** 인스펙터·직렬화 자동화는 리플렉션이 핵심이고 이것은 이미 있다. Transform 을 필수 컴포넌트로 둘지, 오브젝트 자체가 가질지(§4-5)는 결정 항목.

### 2-2. Unreal — World + Level + Actor + Component

**구조**

```
UGameInstance (프로세스 수명)
 └ UWorld
     ├ ULevel  (Persistent Level + 스트리밍 레벨 / World Partition 셀)
     │   └ AActor  (월드에 배치·스폰되는 단위. 이름·태그·소유자·복제 설정·Tick)
     │       ├ RootComponent : USceneComponent   (트랜스폼 + 어태치 트리)
     │       │   └ UPrimitiveComponent            (렌더/충돌: StaticMesh, Skeletal …)
     │       └ UActorComponent                    (트랜스폼 없음. 순수 행동/데이터)
     └ 게임플레이 프레임워크 Actor: GameMode, GameState, PlayerController, Pawn/Character, PlayerState, HUD
```

- **상속 + 조합 이중 구조.** Actor 는 상속으로 종류를 나누고(APawn, ACharacter …) 기능은 컴포넌트로 붙인다. 트랜스폼 계층은 Actor 간이 아니라 **SceneComponent 트리**다. Actor 를 Actor 에 붙이는 것은 루트 컴포넌트를 상대 컴포넌트에 어태치하는 것.
- **UObject 리플렉션(UHT)** 이 직렬화·GC 참조 추적·네트워크 복제·에디터 디테일 패널·Blueprint 노출을 한 체계로 묶는다.
- **프리팹 대응물이 여러 개다.**
  - Blueprint 클래스 — "프리팹 = 클래스". 인스턴스는 CDO 와 다른 프로퍼티만 저장(델타 직렬화). 변형은 Blueprint 상속(자식 클래스). 컴포넌트 구성은 SCS(Simple Construction Script)로 클래스에 기록.
  - Child Actor Component — 컴포넌트 자리에 다른 Actor 클래스를 스폰(중첩 프리팹 대체. 제약 많음).
  - Level Instance / Packed Level Actor(UE5) — 레벨 조각을 인스턴싱(씬 단위 프리팹). Packed 는 스태틱 메시를 ISM 으로 묶어 렌더 최적화.
  - Data Asset / Data Table — 데이터 에셋.
- **GC** 루트 집합에서 UPROPERTY 참조를 따라가는 도달성 분석(mark & sweep). 순환 참조 문제가 없다. 원시 포인터로 들고 있으면 GC 가 모른다(`TObjectPtr`/UPROPERTY 규약). 5.4 부터 증분 도달성 분석(실험적).
- **Tick** Actor 와 컴포넌트 각각 FTickFunction. TickGroup(PrePhysics / DuringPhysics / PostPhysics / PostUpdateWork …)과 `AddTickPrerequisite` 로 순서를 명시할 수 있다. 비활성 Tick 은 등록만 되고 비용이 거의 없다.
- **통신** 델리게이트(단일/멀티캐스트/다이내믹), UInterface, Gameplay Tag, GAS(Gameplay Ability System) 같은 상위 프레임워크.
- **Mass Entity(5.x, 실험적)** Fragment(데이터) / Tag / Archetype(같은 구성의 청크 배열) / Processor(시스템) / Trait(저작 시 프래그먼트 묶음). 군중·교통 같은 대량 오브젝트용. Actor 와의 브리지(Representation)는 별도 계층.

**장점**
- 게임플레이 프레임워크가 완성형(멀티플레이어 권한 모델, 입력, 카메라, 스폰 규약). 1인칭/3인칭 게임이면 "채우기" 만 하면 된다.
- 리플렉션이 모든 것을 관통한다. 마크업 한 줄로 저장·복제·에디터·GC 참조 추적을 동시에 얻는다.
- 클래스 상속 기반 변형(Blueprint 파생)이 강력하고, CDO 델타 직렬화로 기본값 변경이 인스턴스에 전파된다.
- 레벨 스트리밍·월드 파티션이 성숙.
- Tick 순서를 명시할 수단이 있다.

**단점**
- Actor 가 무겁다(UObject 헤더, 컴포넌트 배열, 복제 메타, Tick 함수, 이름 테이블). 수천 개 이상의 동적 스폰은 Mass 나 ISM 으로 우회한다.
- "Actor 파생으로 할까, 컴포넌트로 할까" 의 이중 선택지가 항상 있고 팀마다 규약이 다르다.
- 트랜스폼 계층이 컴포넌트 트리라서 "Actor 계층" 이 직관과 다르다. 아웃라이너의 어태치 = 루트 컴포넌트 어태치이고, 부모 Actor 를 파괴해도 자식 Actor 는 기본적으로 죽지 않고 떨어진다.
- 프리팹 = 클래스라서 "씬에 놓인 서브트리를 그대로 프리팹으로" 만드는 워크플로가 약하다. Child Actor 는 제약이 많고 Level Instance 는 무겁다. 중첩·변형이 Unity/Godot 보다 어색하다.
- CDO/델타 직렬화의 함정 — 기본값을 바꾸면 "명시적으로 같은 값으로 설정" 한 인스턴스와 구별이 안 되어 예상 밖 전파가 나고, 부모 Blueprint 의 컴포넌트 변경이 자식에 반영되지 않는 SCS 문제가 있다.
- 트레이싱 GC 라 스파이크가 있고(증분화로 완화), 원시 포인터 규약 위반이 곧 크래시다.
- UHT/매크로/모듈 규약이 빌드를 복잡하게 한다. JGEngine 도 같은 길을 이미 택했다.

**JGEngine 교훈.** 가장 가까운 기반이다. JGHeaderTool ≈ UHT, `JGObject` ≈ UObject, `JGCLASS`/`JGPROPERTY` ≈ UCLASS/UPROPERTY, `StaticClass<T>()`/`Cast<>`/`NewObject` 도 같은 어휘(`Source/Runtime/Core/Object/ObjectGlobalSystem.h`). 차이는 GC — UE 는 도달성 트레이싱, JGEngine 은 **참조 카운트 + 지연 파괴 큐**(`Memory.h:749` `garbageCollection`). 참조 카운트는 순환을 못 끊으므로 Actor↔Component, Actor↔World 의 역참조는 `PWeakPtr` 규약이 필수다. 또 JGEngine 에는 CDO 가 없다 — UE 식 "클래스 = 프리팹" 을 그대로 옮기려면 클래스별 기본값 인스턴스를 새로 만들어야 한다.

### 2-3. Godot — Node + SceneTree + PackedScene

**구조**

```
SceneTree (프로세스당 하나)
 └ root : Window
     └ (현재 씬) Node 서브트리
          Node ─ Node3D / Node2D / Control / …   (상속 트리. 노드 종류 = 클래스)
                   └ 자식 노드들                  (조합 = 자식 노드 추가)
```

- **모든 것이 노드다.** 노드 종류는 상속으로 나뉘고(Node3D → VisualInstance3D → MeshInstance3D), 기능 조합은 **자식 노드**로 한다. 캐릭터 = `CharacterBody3D` ⊃ `MeshInstance3D`, `CollisionShape3D`, `AnimationPlayer`, `Camera3D`.
- 스크립트는 **노드당 하나**. 스크립트는 노드 클래스를 `extends` 하는 클래스라서, 여러 행동을 한 노드에 붙이려면 스크립트 상속 또는 자식 노드로 분리한다.
- **씬(PackedScene, `.tscn`)** = 노드 서브트리를 저장한 리소스. 씬을 다른 씬에 **인스턴스**하면 프리팹이 되고, 인스턴스에서 바꾼 프로퍼티만 부모 씬 파일에 저장된다. **상속 씬(Inherited Scene)** 은 다른 씬을 베이스로 하는 씬(= 프리팹 변형). 레벨도 씬, 프리팹도 씬, 게임 전체도 씬 — **하나의 재귀적 포맷**.
- **시그널** 노드가 선언하는 관찰자 이벤트. 에디터에서 연결 가능. 그룹(태그), NodePath 로 참조.
- **수명** `Node` 는 트리가 소유 — 부모를 `free()` 하면 서브트리가 전부 죽는다. `queue_free()` 는 프레임 끝 지연 파괴. `RefCounted`(대부분의 `Resource`)는 참조 카운트. 즉 **트리 소유 + RC 하이브리드**. 트리에서 뗀 노드(`remove_child`)는 호출자가 책임진다(누수가 흔한 지점).
- **서버(Servers)** RenderingServer / PhysicsServer3D / AudioServer 등. **RID(불투명 핸들)** 로 다루는 데이터 지향 백엔드. 노드는 서버 리소스의 프런트엔드(MeshInstance3D 는 RenderingServer 의 instance RID 를 들고 있다). 노드가 병목이면 서버를 직접 써서 노드를 우회한다.
- **ECS 를 채택하지 않은 이유(2021, Juan Linietsky)** 사용성·확장성이 우선이고, 성능이 필요한 곳은 서버 계층에서 데이터 지향으로 처리한다는 입장. 노드 상속이 "여러 기능을 동시에 갖는 노드" 를 엔진이 미리 제공하는 데 유리하다고 주장.
- **처리 순서** `_process`/`_physics_process` 는 `process_priority` 가 같으면 트리 순서. `_ready` 는 자식이 먼저(bottom-up). 4.1 부터 `process_thread_group` 으로 서브트리를 다른 스레드에서 처리 가능.

**장점**
- 개념이 하나(노드)라 학습·에디터·직렬화가 극도로 단순하다. 씬 파일이 텍스트라 diff/merge 가 쉽다.
- "씬 = 프리팹 = 레벨" 의 재귀 조립. 인스턴스 오버라이드가 자연스럽고 상속 씬으로 변형까지 된다.
- 트리 소유로 수명이 직관적(부모가 죽으면 자식도). UI(Control) 처럼 트리 자체가 의미인 영역에 특히 잘 맞는다.
- 시그널이 느슨한 결합을 언어 차원에서 지원한다.
- 서버 계층으로 성능 탈출구가 있다.

**단점**
- 행동 조합이 어색하다. 컴포넌트가 없어서 "이 노드에 A 행동과 B 행동을 붙인다" 가 스크립트 상속(단일) 또는 자식 노드 + 부모 참조로 우회된다. Unity 사용자가 가장 많이 겪는 불편.
- 논리 계층과 트랜스폼 계층이 같은 트리다. 트랜스폼 부모-자식이 필요 없는 논리 그룹도 트리에 넣어야 하고, 트랜스폼은 공유하되 논리적으로는 형제인 경우를 표현하기 어렵다.
- 노드 수 = 오브젝트 수 × 부속 노드 수. 대량 인스턴스에서 노드 오버헤드가 크고, 수만 개 이상은 서버 직접 사용 = 두 개의 API 세계.
- "두 종류 기능을 동시에 갖는 노드" 는 엔진이 미리 만들어 둔 조합이 있어야 한다.
- 트리에서 뗀 노드는 수동 관리라 누수/댕글링이 생긴다(`queue_free` 규약 학습 필요).

**JGEngine 교훈.** Devkit 의 `JGDevScene` 이 렌더 커맨드를 직접 기록하는 지금 구조는 "노드가 서버의 프런트엔드" 모델과 같다. 렌더 오브젝트(`IJGGraphicsObject`, `PScene`)를 RID 같은 핸들로 두고 게임 오브젝트가 그것을 참조하는 분리는 Godot 의 서버 모델 그대로다(§4-6).

## 3. 상용 엔진 밖의 방법론

### 3-1. 상속 계층 (Classic OOP)

- `Actor → Pawn → Character → …` 처럼 깊은 클래스 트리로 종류와 기능을 함께 표현. Quake 의 `edict_t`(함수 포인터 `think`/`touch`/`use`), Doom 의 `mobj_t` + 상태 테이블은 "거대 구조체 + 함수 포인터" 변형.
- **장점** 직관적. 가상 함수 한 번으로 다형성. 콜스택이 곧 구조라 디버깅이 쉽다. 도구 없이 시작할 수 있다.
- **단점** 조합 폭발("날 수 있고 + 수영 가능하고 + …"). 다이아몬드 상속. 기반 클래스 비대화("모든 것을 아는 Actor"). 런타임 조합 변경 불가. Mick West(2007), Scott Bilas(2002) 가 이 문제에서 컴포넌트로 이행한 사례를 기록했다.
- **현재 위치** 순수 형태로는 소멸. UE 와 Godot 이 "종류는 상속, 기능은 조합" 으로 잔존.

### 3-2. 컴포넌트 기반 (Aggregation) — 세 변종

| 변종 | 컴포넌트의 정체 | 대표 | 특징 |
|---|---|---|---|
| (a) 객체 컴포넌트 | 데이터 + 행동을 가진 객체. 오브젝트가 목록으로 소유 | Unity MonoBehaviour, UE ActorComponent, Dungeon Siege GoComponent | 직관·툴링 쉬움. 오브젝트당 비용, 순서·참조 문제 |
| (b) 컴포넌트 매니저 | 타입별 매니저가 데이터(SoA)를 소유. 오브젝트는 ID | Bitsquid(2014), Insomniac(2010) | 캐시·배치 처리·스폰 빠름. 매니저마다 코드 필요 |
| (c) 순수 데이터 + 시스템 | 컴포넌트는 데이터만, 행동은 시스템 | ECS(§3-4) | 아래 절 |

- **Bitsquid(Niklas Gray, 2014)** Entity = 인덱스 + 세대 카운터. ComponentManager 가 컴포넌트 데이터를 소유하고 엔티티 ↔ 컴포넌트 매핑을 관리. Transform 컴포넌트는 **부모가 자식보다 앞에 오도록 배열을 정렬**해 한 번의 선형 순회로 월드 행렬을 갱신. Entity Resource 를 컴파일 시점에 만들어 스폰 비용을 줄임.
- **Radical(Marcin Chady, GDC 2009)** 컴포넌트 간 의존·업데이트 순서·참조 문제를 "컴포넌트 타입별 업데이트 페이즈" 로 해결. **Insomniac(Terrance Cohen, GDC 2010)** 컴포넌트를 타입별 연속 배열에 두고 타입별 배치 업데이트 — (a) 에서 (b) 로 가는 중간.
- (a) 의 장단은 §2-1·§2-2 와 같다. (b) 는 "이 오브젝트가 무엇인지 한눈에" 보기 어렵고 행동을 어디에 두는지 규약이 필요하지만, 핫패스에서는 가장 실용적이다.

### 3-3. 프로퍼티 / 데이터 모델 중심

- **Dark Engine(Thief, System Shock 2)** 오브젝트 = ID. **프로퍼티**(타입별 테이블에 ID→값), **링크**(오브젝트 간 관계. 타입 있음), **아키타입** 계층(추상 오브젝트에서 프로퍼티 상속) + **메타프로퍼티**(믹스인). 디자이너가 새 종류를 코드 없이 정의. Doug Church(GDC 2002), Alex Duran(GDC 2003) 이 정리.
- **Dungeon Siege(Scott Bilas, GDC 2002)** 텍스트 템플릿(상속) → Go 인스턴스. 데이터 주도 게임 오브젝트 시스템의 고전.
- **Our Machinery — The Truth(2017~2022)** 에디터 쪽 **중앙 데이터 모델**. 모든 에디터 데이터가 "타입 + 프로퍼티 집합" 오브젝트이고, **프로토타입**(다른 오브젝트를 원형으로 삼아 바뀐 프로퍼티만 저장)으로 프리팹·변형을 일반화. undo/redo, 협업 병합, 직렬화, 프로퍼티 에디터가 데이터 모델 차원에서 공짜. 런타임은 별도 엔티티 컨텍스트로 컴파일(저작/런타임 분리).
- **장점** 도구·직렬화·undo 를 한 번에 얻는다. 디자이너 확장성. 프로토타입 상속이 일반적이다. 데이터가 곧 문서라 diff/merge 가 쉽다.
- **단점** 모든 접근이 간접(키 조회). 타입 안전성이 약해 런타임 검증에 의존. 런타임용 표현을 따로 컴파일해야 성능이 나온다. 구현 규모가 크다(사실상 미니 DB).
- **JGEngine 관점** JGHeaderTool 리플렉션이 이미 "타입 + 프로퍼티 집합" 메타(`JGClass`/`JGProperty`)를 제공한다. 인스펙터·undo·프로토타입 델타는 리플렉션 위에서 The Truth 의 절반을 얻을 수 있다.

### 3-4. 데이터 지향 ECS

**정의.** Entity = ID. Component = 순수 데이터. System = 컴포넌트 조합에 대한 쿼리 + 함수. **행동이 오브젝트 밖(시스템)에 있다** 는 점이 컴포넌트 기반(a)과의 본질적 차이다.

**저장 방식 3종**

| 방식 | 대표 | 순회 | 컴포넌트 추가/제거 | 비고 |
|---|---|---|---|---|
| Archetype / Chunk | Unity Entities, UE Mass, flecs, Bevy | 최고(같은 구성끼리 SoA 청크) | 아키타입 이동 비용 | 구성 변경이 잦으면 불리. 청크 단편화 |
| Sparse Set | EnTT | 다중 컴포넌트 쿼리는 가장 작은 집합 기준. 그룹(group)으로 최적화 | O(1) | 단순. 소규모에 적합 |
| 컴포넌트 매니저 | Bitsquid | 매니저별 수제 | 매니저별 | 제네릭 쿼리 없음. 유연 |

**사례 — Overwatch(Timothy Ford, GDC 2017)** 컴포넌트는 데이터만, 시스템은 상태 없음, 전역 상태는 싱글턴 컴포넌트, 시스템 간 결합은 유틸리티 함수와 지연 실행(deferral)로 처리. 결정론적 시뮬레이션 → 예측/롤백 네트코드에 유리. 다만 "행동을 어디에 두나" 는 여전히 규약 문제였다고 술회.

**관계(Relationships).** 순수 ECS 의 약점이던 계층·소유·참조를 1급으로 — flecs 의 `ChildOf`, `IsA`(프리팹 상속), 임의 (관계, 대상) 쌍. Bevy 0.16 의 `ChildOf`/`Children`(일대다). flecs 프리팹은 `IsA` 로 컴포넌트를 공유하고 인스턴스가 오버라이드하면 복사한다(프로토타입 기반).

**옵저버/리액티브.** 컴포넌트 추가·제거·변경 훅(flecs observers, Bevy hooks/observers, EnTT signals) — "ECS 에서 이벤트는 어떻게" 의 답.

**저작.** Unity 는 GameObject 로 저작하고 Baking, Mass 는 Trait 로 저작, flecs 는 Flecs Script(DSL). 순수 ECS 에디터를 처음부터 만드는 것은 상당한 작업이다.

**장점**
- 캐시 친화. 시스템의 읽기/쓰기 집합으로 자동 병렬 스케줄.
- 구성이 런타임에 자유롭게 바뀐다(상태 = 컴포넌트 유무).
- 직렬화·네트워크 스냅샷이 단순하다(POD 배열). 결정론적 시뮬레이션에 유리.
- 테스트 용이(시스템 = 순수 함수).

**단점**
- 소규모 게임플레이에서 보일러플레이트가 크다(컴포넌트/시스템 분리 강제).
- 계층·이벤트·"이 오브젝트가 무엇인지 한눈에" 가 어렵다(관계·옵저버로 완화 중).
- 시스템 순서 관리 — 수십 개를 넘으면 스케줄 그래프가 곧 아키텍처.
- 아키타입 이동 비용, 청크 단편화.
- 디자이너 저작 모델과 리플렉션 기반 툴링을 다시 만들어야 한다.
- 디버깅(엔티티 ID 뿐). OOP 다형성 부재(태그 + 시스템 분기 또는 함수 포인터 컴포넌트).

**흔한 오해.** "ECS = 빠르다" 가 아니라 "메모리 배치를 통제할 수 있다" 다. 오브젝트가 수백 개면 이득이 없다(Godot 글의 요지).

### 3-5. 노드 트리 / 씬 그래프 (Composite)

- Godot, Roblox, Flax Actor 트리, OGRE·three.js 씬 그래프.
- **렌더 씬 그래프를 게임 오브젝트 모델로 겸용하는 것의 함정**(Tom Forsyth, "Scene Graphs – just say no") — 렌더에 필요한 순회(재질별·가시성별)와 논리 계층 순회는 다르다. 렌더는 평탄한 리스트/배치가 낫다. 현대 엔진은 논리 트리(노드)와 렌더 컨테이너(서버, 씬 프록시)를 분리한다.
- **장점** 소유·수명·트랜스폼·직렬화가 한 구조. UI 에 최적.
- **단점** §2-3 Godot 단점 + 트리 순회 비용, 트리 위치가 논리를 강제.

### 3-6. 메시지 패싱 / 액터 모델

- Defold(`msg.post(url, id, table)`), Unity `SendMessage`, O3DE EBus, Source Entity I/O, Dark Engine 의 링크 기반 메시지. 이론적 배경은 Hewitt 액터 모델(Erlang, Akka, Orleans) — 온라인 게임 서버(Orleans 는 Halo 4 서비스에서 출발)에서 주류. **UE 의 "Actor" 는 이 액터 모델과 무관**하다(배치 단위의 이름일 뿐).
- **장점** 송신자가 수신자 타입을 몰라도 된다(느슨한 결합). 지연·큐잉·스레드 경계 넘기기가 자연스럽다. 디자이너가 데이터로 연결(Source I/O). 네트워크 투명성.
- **단점** 타입 안전성 상실(문자열/테이블). 흐름 추적 어려움(누가 보냈나). 즉시 응답이 필요한 질의에 부적합. 디스패치·복사 비용.
- **현실적 위치** 컴포넌트 모델의 통신 수단 중 하나로 흡수(이벤트/델리게이트 + 필요 시 메시지 큐).

### 3-7. 이벤트 / 시그널 / 데이터 바인딩 (Reactive)

- Godot 시그널, UE 델리게이트/이벤트 디스패처, Unity UnityEvent, Qt 시그널-슬롯, 반응형 프로퍼티. JGEngine 의 `HDelegate`/`HMulticastDelegate`(`Core/Misc/Delegate.h`)와 `HAttribute<T>`(`Core/Misc/Attribute.h`)가 이 계열.
- **장점** 관찰자 결합 해제. 에디터에서 연결 가능.
- **단점** 수명 — 구독자가 죽은 뒤 호출. 약참조 바인딩(`PSPDelegate`)이 필요한 이유. 순서 비결정. 디버깅.

### 3-8. 컴파일 타임 조합 (Mixin / CRTP / Policy-based)

- `class Player : public WithTransform<WithHealth<Entity>>` 류.
- **장점** 제로 오버헤드. 타입 안전.
- **단점** 런타임 조합 불가. 컴파일 시간·에러 메시지. 에디터 저작 불가. 도구·프로토타입용 소형 엔진에 한정.

### 3-9. 저작 모델 ≠ 런타임 모델 (Baking / 컴파일)

- Unity SubScene Baking, Bitsquid Entity Resource, The Machinery(The Truth → 엔티티 컨텍스트), UE Packed Level Actor / Mass Trait.
- **장점** 저작은 사람 친화, 런타임은 기계 친화. 런타임 표현을 자유롭게 바꿀 수 있다.
- **단점** 두 표현 사이 동기화·디버깅("런타임에서 본 것이 저작의 어디에서 왔나"). 라이브 편집이 어렵다. 구현이 두 배.
- **JGEngine** 지금 단계에서는 저작 = 런타임(`JGObject` 그대로 저장/로드)으로 시작하고, 필요 시 렌더 쪽만 컴파일된 표현(핸들 기반 컨테이너)을 두는 것이 현실적이다.

## 4. 횡단 관심사 비교

### 4-1. 조립 단위(프리팹) 표현

| | 표현 | 인스턴스가 저장하는 것 | 중첩 | 변형 | 원본 변경 전파 |
|---|---|---|---|---|---|
| Unity Prefab | 인스턴스 서브트리 에셋(프로토타입 기반) | 원본 참조 + 오버라이드 목록 | Nested | Variant | 즉시(오버라이드 제외) |
| UE Blueprint | 클래스(CDO) | CDO 와의 델타 | Child Actor(제약) | 자식 클래스 | 즉시(델타 제외) |
| UE Level Instance | 레벨 파일 | 레벨 참조 + 트랜스폼 | 가능 | 없음(오버라이드 실험적) | 즉시 |
| Godot PackedScene | 노드 서브트리 리소스 | 씬 참조 + 바뀐 프로퍼티 | 인스턴스 안 인스턴스 | 상속 씬 | 즉시 |
| O3DE Prefab | JSON 템플릿 | 상위 템플릿 DOM 에 패치 | 중첩 | (패치로 대체) | 전파 |
| flecs Prefab | 엔티티 + `IsA` | 오버라이드한 컴포넌트만 복사 | 프리팹 자식 복사 | 프리팹의 프리팹 | 공유 컴포넌트는 즉시 |
| Dark Engine Archetype | 추상 오브젝트 계층 | 프로퍼티 오버라이드 | — | 메타프로퍼티 | 즉시 |
| The Truth Prototype | 오브젝트 프로토타입 | 바뀐 프로퍼티만 | 서브오브젝트 | 프로토타입 체인 | 즉시 |

**핵심 분기: 클래스 기반(UE, GameMaker) vs 프로토타입 기반(Unity, Godot, flecs, Dark, Truth).** 프로토타입 기반은 "씬에 놓인 것을 그대로 템플릿화" 와 "인스턴스 오버라이드" 가 자연스럽고, 클래스 기반은 코드(행동)를 템플릿에 포함하기 쉽다. 리플렉션이 있으면 둘 다 결국 **"프로퍼티 델타 저장"** 으로 구현된다. JGEngine 은 `JGPROPERTY` 단위 JSON 직렬화가 있으므로 "프리팹 JSON vs 인스턴스 JSON 의 차이" 가 곧 오버라이드다. 오브젝트 간 참조(Actor→Actor)의 직렬화에는 안정적 ID(GUID 또는 서브트리 내 경로)가 필요하다 — Unity fileID, UE 오브젝트 경로, Godot NodePath.

### 4-2. 수명 관리

| 방식 | 대표 | 순환 참조 | 파괴 시점 | 댕글링 감지 | 비용 | 스레드 |
|---|---|---|---|---|---|---|
| 트레이싱 GC | UE UObject, Unity C# | 문제 없음 | 비결정(GC 시점) | GC 가 참조를 null 로(`TObjectPtr`, 약참조) | 스파이크, 마킹 비용 | 마킹 병렬 가능 |
| 참조 카운트 | Godot RefCounted, **JGEngine PSharedPtr** | **끊어야 함**(약참조) | 결정적(0 되는 순간) 또는 지연 | 약참조로 | 원자 증감 | 락 프리 카운터 |
| 트리 소유 | Godot Node, Roblox Instance | 없음(단일 소유) | 부모 파괴 시 | 없음(외부 참조는 약참조 필요) | 없음 | 트리 단위 |
| 핸들 + 세대 | ECS Entity, Bitsquid, Godot RID, floooh | 없음(소유 개념 없음) | 명시적 destroy | **O(1) 검증**(세대 비교) | 최소 | 인덱스라 공유 쉬움 |
| 고유 소유 + 원시 관찰 | `unique_ptr` + raw | 없음 | 결정적 | 없음 | 최소 | — |

JGEngine 은 참조 카운트 + 지연 파괴(GC 큐)다. 메모리 분석(`Document/Memory_현황분석_2026-09-21.md` §2-4·§4)에서 **파괴 순서 = 할당 순서(FIFO), WeakCount 무시, `= nullptr` 대입 no-op, 풀 고갈 무음**이 확인됐다. 트리 소유 모델을 얹으려면 "부모가 자식보다 먼저 죽지 않는다" 가 GC 순서에 의존하지 않고 **명시적 `Destroy()` 전파**로 보장되어야 하고, GC 는 메모리 회수만 맡아야 한다. 렌더/물리 리소스는 세대 핸들이 적합하다 — GPU 수명과 게임 오브젝트 수명이 다르다(Phase 5 전송 관리자·종료 크래시와 같은 축. `AssetDatabase.h` `releaseAssets` 주석의 크래시 사례).

### 4-3. 업데이트 순서

| | 단위 | 순서 결정 | 병렬 |
|---|---|---|---|
| Unity | 컴포넌트 메서드 | 암묵적 + Script Execution Order(타입별) | 잡 시스템은 별도 |
| UE | Actor/Component TickFunction | TickGroup + Prerequisite | 그룹 내 옵션(제한적) |
| Godot | 노드 `_process` | `process_priority` + 트리 순서. 4.1+ `process_thread_group` | 서브트리 단위 |
| ECS | 시스템 | 명시적 스케줄(의존 그래프, 읽기/쓰기 집합) | 자동 |
| **JGEngine 현재** | 스케줄 태스크 | 6 버킷(`EMainThreadExecutionOrder`: GraphicsBegin / Begin / Update / End / GraphicsEnd / UpdateWindow) + Priority | 없음 |

교훈. 컴포넌트마다 가상 `Update` 를 호출하는 (a) 형은 "틱 등록/해제" 가 곧 성능·수명 이슈다. GUI 분석에서 **스케줄러에 Unschedule API 가 없음**이 확인됐으므로(`GUI_현황분석_2026-09-21.md` 3-B), Actor/Component 틱을 스케줄 태스크로 개별 등록하는 방식은 피하고 **World 가 틱 목록을 직접 관리**(등록 시 그룹 배정, 비활성은 목록에서 제외, 프레임 중 추가/제거는 지연 적용)하는 UE 식이 안전하다. 6 버킷은 TickGroup 의 씨앗으로 쓸 수 있다.

### 4-4. 통신

| 수단 | 대표 | 결합 | 타입 안전 | 지연/큐 | 적합 |
|---|---|---|---|---|---|
| 직접 참조 | `GetComponent`, 포인터 | 강 | ◎ | × | 같은 오브젝트 안 |
| 이벤트/델리게이트 | UE 델리게이트, Godot 시그널, `HDelegate` | 약 | ◎ | ○ | 1:N 통지 |
| 메시지 | Defold, EBus, Source I/O | 최약 | △ | ◎ | 스레드·네트워크 경계, 데이터 연결 |
| 쿼리 | ECS 시스템 | 없음 | ◎ | — | 집합 처리 |
| 태그/그룹 | Gameplay Tag, Godot 그룹 | 약 | ○ | — | 분류·조회 |

JGEngine 은 `HDelegate`/`HMulticastDelegate`/`PSPDelegate`(약참조 바인딩)가 있으므로 이벤트 축은 준비됐다. 단 `Delegate.h:253` `GetOwner()` 조건 반전이 GUI 분석에 기록되어 있다.

### 4-5. 계층(트랜스폼)의 소유자

| | 트랜스폼을 갖는 것 | 부모-자식 단위 | 트랜스폼 없는 오브젝트 |
|---|---|---|---|
| Unity | Transform 컴포넌트(필수) | GameObject(= Transform) | 불가 |
| UE | USceneComponent | 컴포넌트(Actor 어태치 = 루트 컴포넌트 어태치) | 가능(AInfo 류. 루트 없는 Actor) |
| Godot | Node3D/Node2D(노드 종류) | 노드 | 가능(`Node` 자체) |
| Flax | Actor | Actor | 불가(Actor 는 항상 트랜스폼) |
| ECS | Transform 컴포넌트 | `ChildOf`/`Parent` 컴포넌트 + 전파 시스템 | 가능 |
| Bitsquid | Transform 컴포넌트 매니저 | 정렬된 배열(부모가 앞) | 가능 |

세 가지 선택지 — (i) 오브젝트가 트랜스폼을 갖는다(Godot/Flax. 단순, 컴포넌트에 트랜스폼 없음), (ii) 컴포넌트가 갖는다(UE. 한 Actor 안에 여러 트랜스폼, 복잡), (iii) 필수 컴포넌트(Unity. (i)의 변형). 렌더 프리미티브 하나가 오브젝트당 하나라면 (i)가 충분하고, 한 Actor 가 여러 메시를 각기 다른 오프셋으로 가지려면 (ii)나 "컴포넌트가 로컬 오프셋만 갖는" 절충이 필요하다.

### 4-6. 렌더/물리 미러링

| | 게임 측 | 렌더 측 | 동기화 |
|---|---|---|---|
| UE | UPrimitiveComponent(게임 스레드) | FPrimitiveSceneProxy(렌더 스레드) | 변경을 렌더 커맨드로 전송. 프록시 재생성 |
| Godot | 노드 | 서버 RID | 노드가 서버 API 호출 |
| Unity | Renderer 컴포넌트 | 내부 렌더 월드 | 내부 |
| ECS | Transform/Mesh 컴포넌트 | 렌더 시스템이 컴포넌트를 직접 읽음 | 없음(같은 데이터) |
| **JGEngine 현재** | (없음. `JGDevScene` 이 직접 기록) | `PScene::_graphicsObjectPool`(`HList<PSharedPtr<IJGGraphicsObject>>`, 초안), `PCamera` 빈 클래스 | — |

게임 오브젝트가 렌더 객체를 `PSharedPtr` 로 소유하면 GC 파괴 순서 문제(Graphics 모듈 종료 전에 해제되어야 함. `AssetDatabase::releaseAssets` 주석의 종료 크래시 사례)가 다시 생긴다. **Graphics 가 렌더 프리미티브/카메라/라이트를 핸들로 발급하고 게임 오브젝트는 핸들만 들고 트랜스폼·가시성 변경을 넘기는** Godot 서버 방식이 현재 모듈 경계(Graphics ↔ GameFrameWorks)와 GC 특성에 맞다.

### 4-7. 직렬화 · 에디터

리플렉션 유무가 결정적이다. UE·JGEngine 은 헤더 툴, Unity 는 C# 리플렉션 + `SerializeField`, Godot 은 ClassDB + `_get_property_list`, ECS 는 컴포넌트가 POD 라 직렬화는 단순하지만 엔티티 참조 재매핑이 필요하다. JGEngine 은 `JGPROPERTY` 로 JSON 직렬화가 되고 `LoadObject` 가 타입명으로 객체를 만든다(`ObjectGlobalSystem.h` `SaveObject`/`LoadObject`). 없는 것은 **오브젝트 간 참조의 직렬화 규약**(GUID/경로)과 **델타(오버라이드) 저장**이다.

### 4-8. 네트워크 (짧게)

UE 는 Actor 단위 복제(권한 모델), Unity NGO 는 NetworkObject, Godot 은 MultiplayerSynchronizer(노드 단위), ECS 는 컴포넌트 스냅샷(Overwatch). 오브젝트/컴포넌트 모델은 복제 단위가 명확하다는 장점이 있다. 지금 결정하지 않아도 되지만 "오브젝트에 안정적 네트워크 ID 를 둘 자리" 는 남겨둘 것.

### 5-2. 후보 3안과 제안

| | A. UE형 World/Actor/Component | B. Godot형 Node 트리 | C. ECS + 저작 레이어 |
|---|---|---|---|
| 뼈대 | 리플렉션 오브젝트. World ⊃ Actor ⊃ Component | 리플렉션 노드 트리. 조합 = 자식 노드 | Entity ID + 컴포넌트 저장소 + 시스템 |
| 기존 자산 활용 | ◎ 리플렉션·직렬화·모듈·GC 그대로 | ◎ 같음 | △ 리플렉션은 메타만, GC 미사용, 툴링 신규 |
| 조합 | ◎ 컴포넌트 | ○ 자식 노드(행동 조합 어색) | ◎ |
| 대량 오브젝트 | △(Actor 무거움. 핫패스 별도 필요) | △ | ◎ |
| 프리팹 | 클래스(CDO) 또는 서브트리 에셋 — 선택 필요 | 씬 = 프리팹 재귀 | `IsA` 관계 또는 별도 |
| 수명 | RC + 약참조 규약 + 명시적 Destroy | 트리 소유(가장 단순) | 세대 핸들 |
| 1인 구현 비용 | 낮음~중간 | 낮음~중간 | 높음(저작·디버깅 도구 포함) |
| 위험 | GC 취약점 위에 첫 대량 소비자 | 트랜스폼 = 논리 트리 강제 | 게임플레이 보일러플레이트, 에디터 부재 |

**제안 — A 를 뼈대로, B 의 계층·프리팹, ④' 의 핫패스를 빌린다.** 정리하면 Flax Engine 과 매우 흡사한 구성이다.

1. **오브젝트 모델** `World ⊃ Actor ⊃ Component`. Actor 가 트랜스폼과 부모-자식 트리를 직접 갖고(Godot/Flax), Component 는 트랜스폼이 없다(UE 의 ActorComponent 만 있고 SceneComponent 트리는 없음). 한 Actor 에 메시가 여럿 필요하면 자식 Actor 로 표현한다. → 트랜스폼 계층이 하나(Actor 트리)라 직렬화·에디터·수명이 단순하고, 컴포넌트는 순수 행동/데이터로 남는다.
2. **수명** World 가 Actor 를, Actor 가 Component 와 자식 Actor 를 소유(`PSharedPtr`). 역참조(Component→Actor, Actor→World, 자식→부모)는 전부 `PWeakPtr`. 파괴는 `Destroy()` 가 서브트리로 명시 전파하고 GC 는 메모리 회수만. 렌더/물리는 Graphics 가 발급한 세대 핸들로 참조.
3. **프리팹** `JGAsset` 파생 에셋 = Actor 서브트리 JSON(프로토타입 기반). 씬/레벨도 같은 포맷(Godot 식 재귀). 인스턴스는 "프리팹 GUID + 프로퍼티 델타 + 추가/제거 목록" 을 저장(Unity 식). 변형(Variant)은 "프리팹을 원본으로 하는 프리팹". CDO 를 새로 만들지 않아도 되고, `IJsonable` 델타 비교로 구현 가능.
4. **틱** World 가 그룹별 틱 목록을 관리(현재 6 버킷을 PrePhysics/Update/PostUpdate/Late 정도의 그룹으로 세분). 스케줄러 태스크 등록은 쓰지 않는다.
5. **통신** `HDelegate`(약참조 바인딩) 기본. 메시지 버스는 필요해질 때.
6. **핫패스** Graphics 의 프리미티브/카메라/라이트, 나중의 물리·파티클·군중은 Bitsquid 식 컴포넌트 매니저(SoA + 세대 핸들)로 Graphics/각 모듈에 둔다. 게임플레이 계층은 이 컨테이너를 핸들로만 만진다.
7. **저작 = 런타임** 으로 시작. 베이킹은 필요해질 때(§3-9).

**A 를 고른 이유(B·C 대비).** B 는 행동 조합이 스크립트 상속/자식 노드에 갇히는데 JGEngine 은 스크립팅 언어가 없어 C++ 클래스 상속만 남는다 — 컴포넌트가 있어야 조합이 된다. C 는 리플렉션·GC·모듈이라는 이미 지불한 비용을 대부분 버리고 저작 도구를 새로 세워야 하며, 1인 개발에서 "게임플레이 계층까지 ECS" 는 Overwatch 규모의 규약 투자를 요구한다. 대량 오브젝트 성능은 ④' 를 핫패스에만 적용해 얻을 수 있다(Godot 의 서버 논리).

**각 엔진에서 빌릴 것**

| 출처 | 빌릴 것 |
|---|---|
| Unity | 프로토타입 기반 프리팹 + 오버라이드 시각화, `RequireComponent` 류 의존 선언, 컴포넌트 재사용 |
| UE | 리플렉션 관통(직렬화·에디터·참조 추적 한 체계), TickGroup + Prerequisite, World/Level 구분, 트랜스폼 없는 컴포넌트 구분, 게임플레이 프레임워크 어휘(GameMode 등은 나중) |
| Godot | 씬 = 프리팹 재귀, 트리 소유 수명(명시적 Destroy 전파), 시그널, 서버/RID 분리 |
| ECS · Bitsquid | 핫패스 컴포넌트 매니저(SoA + 세대 핸들), 트랜스폼 갱신을 정렬된 배열 순회로 |

### 5-3. 제안안(A)을 JGEngine 관용구로 옮기면

설계 확정이 아니라 **"이 방향이 기존 코드와 맞물리는지 눈으로 검토하기 위한 스케치"** 다. 실제 착수 전에 §6 의 결정 항목을 먼저 정한다.

```cpp
// Source/Runtime/GameFrameWorks/Actor.h
#pragma once
#include "Core.h"
#include "GameFrameWorksDefines.h"
#include "Actor.generation.h"

class PWorld;
class JGActorComponent;

JGCLASS()
class GAMEFRAMEWORKS_API JGActor : public JGObject
{
    JG_GENERATED_CLASS_BODY

    friend class PWorld;

private:
    JGPROPERTY()
    HGuid Guid;                 // 인스턴스 고유 ID. 참조 직렬화·네트워크 ID 겸용 (§6-10)

    JGPROPERTY()
    HTransform LocalTransform;  // 트랜스폼은 Actor 가 직접 갖는다 (§6-2. Flax·Godot 식)

    JGPROPERTY()
    HList<PSharedPtr<JGActorComponent>> Components;   // 소유

    JGPROPERTY()
    HList<PSharedPtr<JGActor>> Children;              // 소유 (트리)

    PWeakPtr<JGActor> Parent;   // 역참조는 약참조. 순환 카운트 방지 (§5-4-3)
    PWeakPtr<PWorld>  World;    // 역참조

    // 캐시. 더티 플래그로 지연 계산
    mutable HMatrix WorldMatrix;
    mutable bool    bWorldMatrixDirty;

public:
    // 수명: Destroy 가 서브트리로 명시 전파한다. GC 순서에 기대지 않는다 (§5-4-2)
    void Destroy();

    template<class T>
    PSharedPtr<T> AddComponent()
    {
        PSharedPtr<T> component = Allocate<T>();
        registerComponent(component);
        return component;
    }

    template<class T>
    PSharedPtr<T> FindComponent() const
    {
        return Cast<T>(findComponent(JGTYPE(T)));
    }

protected:
    virtual void OnBeginPlay() {}
    virtual void OnTick(float32 deltaSeconds) {}
    virtual void OnEndPlay() {}

private:
    void registerComponent(PSharedPtr<JGActorComponent> component);
    PSharedPtr<JGActorComponent> findComponent(const JGType& type) const;
};
```

맞물림 지점 네 가지 — 이번 조사에서 코드로 확인한 결과를 붙였다.

1. **`GameFrameWorks` 가 현재 StaticLib** 이다(`GameFrameWorks.module.json`). 게임 모듈(SharedLib)이 `JGActor` 를 파생하고 리플렉션에 등록하려면 **SharedLib 로 바꾸고 `GAMEFRAMEWORKS_API` 를 도입해야** 한다. `module_system_info.json` 의 코드젠 대상에도 들어가야 리플렉션이 생성된다(`ObjectGlobalSystem.cpp` `codeGen()`).
2. **`HTransform` 은 없다.** `Core/Math` 에 `HMatrix`(`Matrix.h:10`), `HVector*`, `HQuaternion`, `HBBox`, `HFrustum`, `HPlane`, `HRay`, `HRect`, `HColor` 는 있으나 **위치·회전·스케일을 묶은 트랜스폼 타입이 없다.** 먼저 만들어야 하고, `JGPROPERTY` 직렬화를 위해 `IJsonable` 파생 구조체(`HStaticSubMesh` 가 선례)로 둔다.
3. **`HList<PSharedPtr<T>>` 프로퍼티는 이미 동작한다 — 프리팹의 핵심이 이미 있다.**
   - 선례: `Source/Runtime/GUI/Widget.h:44` 의 `JGPROPERTY() HList<PSharedPtr<JGWidgetComponent>> WidgetComponents`. 생성 코드(`Temp/CodeGen/GUI/Widget.generation.h:19,40`)가 `AddMember`/`GetData` 를 뽑는다.
   - **다형 보존 확인.** `PJsonData::makeJsonValue(const PSharedPtr<T>&)`(`Json.h:695`)가 `[JGType, 객체데이터]` **2원소 배열로 타입을 함께 저장**하고, 읽을 때 `readJsonValue(PSharedPtr<T>*)`(`Json.h:1416`)가 저장된 타입으로 `getJGObject(classType)` → `StaticClass` → `AllocateByClass` 하여 **구체 파생 클래스를 복원**한다. `HList` 는 원소마다 이 경로로 위임한다(`Json.h:650`, `1316`).
   - 결론: **"Actor 서브트리 = 컴포넌트·자식 목록을 가진 `JGObject` 트리" 의 JSON 왕복은 새 직렬화기를 만들지 않아도 된다.** §6-3 의 프로토타입 프리팹이 현 자산 위에서 바로 성립한다. 남는 것은 **델타(오버라이드) 비교**와 **오브젝트 간 참조(GUID 해석)** 두 가지뿐이다.
   - **단, 리팩터링 중 상시로 밟게 될 크래시 경로가 하나 있다**(§5-4-9). 컴포넌트 타입을 지우거나 이름을 바꾼 프리팹을 로드할 때다.
4. **`HPrimitiveHandle` 은 아직 없다.** Graphics 에 핸들 발급 API(`PScene` 또는 `PJGGraphicsAPI`)를 추가하는 것이 게임 프레임워크의 선행 작업이 된다.

### 5-4. JGEngine 이 특히 밟기 쉬운 함정

1. **렌더 씬 그래프를 게임 오브젝트 트리로 겸용**(Forsyth). Graphics `PScene` 과 게임 `World` 를 같은 것으로 만들지 말 것. `PScene` 은 평탄한 렌더 컨테이너로 남긴다.
2. **GC 순서에 수명을 의존.** 현재 GC 는 FIFO 라 부모가 자식보다 먼저 파괴될 수 있다. 명시적 Destroy 전파 없이는 트리 모델이 종료 크래시를 재현한다.
3. **컴포넌트 간 `PSharedPtr` 상호 참조 → 순환 누수.** 참조 카운트 모델의 근본 제약. 역참조는 항상 `PWeakPtr`.
4. **오브젝트마다 스케줄 태스크 등록.** Unschedule 부재로 누수(GUI 분석 2-1 사례).
5. **UE 식 CDO 프리팹을 그대로 이식.** JGEngine 에 CDO 가 없다. 프로토타입(에셋 서브트리) 방식이 현 자산과 맞다.
6. **`Scene` 명명 충돌.** Graphics `PScene`, Devkit `JGDevScene` 이 이미 있다. 게임 측은 `World`/`Level` 을 쓰고 GUI 의 `JGWidgetComponent` 와도 이름을 구분한다.
7. **클래스별 고정 개수 풀.** 오브젝트 수가 늘면 무음 크래시(메모리 분석 P0). 성장형 풀(단계 C) 전에는 오브젝트 수 상한을 의식해야 한다.
8. **`Source/Runtime/Game` 이름 충돌.** 유저 게임 모듈 이름이 `Game` 이면 엔진 `Game.dll` 과 충돌(엔진·게임 분리 분석 I 항목). 프레임워크 착수 시 함께 정리.
9. **미등록 타입 프리팹 로드 — 확정 크래시 경로(신규 발견).** 프리팹 JSON 이 참조하는 컴포넌트 클래스를 **삭제·개명하거나 그 모듈이 로드되지 않았을 때** 다음이 연쇄한다.

   | 단계 | 코드 | 동작 |
   |---|---|---|
   | ① | `Json.cpp:43` `getJGObject` | 클래스 미등록이면 **실패가 아니라** `Allocate<JGObject>()`(기반 객체)를 반환 |
   | ② | `Json.h:1449` `*value = Cast<T>(...)` | 기반 객체 → 파생 `T` 캐스트 실패로 **빈** `PSharedPtr` |
   | ③ | 대입 자체가 무효 | 메모리 분석 §4-2 의 확정 버그 — **빈 rhs 대입은 no-op**. `*value` 는 갱신되지 않고 빈 상태로 남는다 |
   | ④ | `Json.h:1450` `value->GetRawPointer()` | `_ptr`(널)을 그대로 넘겨 역참조 |

   즉 **"컴포넌트 클래스를 리팩터링하면 기존 프리팹 로드가 널 역참조로 죽는다."** 프레임워크를 만드는 동안 클래스 개명·삭제는 상시로 일어나므로 이 경로를 가장 자주 밟게 된다. `getJGObject` 가 실패를 실패로 반환하고 호출부가 해당 원소를 건너뛰도록 고치는 것이 근본 수정이며, **메모리 단계 A-2(`PSharedPtr` 대입 수정)가 선행되어야** ②~③이 정상화된다. 부수로 `Json.h:1425` 의 `if (value == nullptr && _value.IsArray() == false)` 는 `&&` 가 `||` 자리에 있어(널 `value` + 유효 배열이면 통과) 같은 함수 안의 두 번째 널 경로다.
