Rules (design 4-10):
  1 .jgasset parses as JSON (error has line/column), JGObjectType, JGObject, JGAsset._guid present
  2 GUID unique across both mounts (the asset database keeps the first and drops the copy)
    _guid is parsed by the checker itself: 11 decimal parts, data1 != 0, 16-bit/8-bit ranges.
    (HGuid::FromString uses std::stoull and throws on non-numeric text - see 5.)
  3 every string inside an asset that starts with a mount token (/JGEngine/ · /JGGame/) names a file in the cook set.
    Same normalization as HAssetPath (backslash, leading '/', no extension -> .jgasset), case-sensitive like the runtime lookup,
    case-only mismatch gets a hint. The asset's own JGAsset.AssetPath field is not a reference (the database uses the file location).
    One line per missing target: first JSON place + "and N more place(s)".
  4 data tables: load issues + ValidateDataTableContent. Errors fail the cook, warnings are reported (cook continues).
    RowRef "Table" lookups resolve inside the cook set; AssetRef existence is left to rule 3 (no duplicate warning).
  + files outside every mount -> error. Paths come only from the given mounts (not from the cooking process' Content dirs).

== 5. Found while doing this (not changed) ==
Asset loading reads _guid through PJsonData::GetData(HGuid*) (Core/FileIO/Json.h:1302) -> HGuid::FromString (Core/Misc/Guid.cpp).
FromString splits on '-': fewer than 11 parts -> silently an invalid (zero) GUID; 11+ parts -> each part goes through
PString::ToUint64/ToUint32 = std::stoull/stoul, which throw std::invalid_argument on a non-numeric part (e.g. a typo in a
hand-edited .jgasset) and silently truncate out-of-range 16/8-bit parts. The cook check catches all of these before packaging;
the runtime parse itself is Core's (reported to 엔진 총괄 as a possible 보류 item).
