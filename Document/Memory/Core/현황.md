## 3. 구현 현황 상세

### 3-1. 완료

**풀 (Phase 2, `MemoryPool.h/.cpp` 전면 교체, 설계 `Files/Memory_풀재설계_설계_2026-09-28.md` §3 · 구현 차이 §3-15)**

| 구조 | 역할 |
|---|---|
| `HMemoryPool` | 청크 테이블 `Chunks[256]`(atomic 포인터, 인덱스 = 헤더 `OwnerChunkID`, 생성 뒤 불변), 스레드 → 인덱스 맵(`CreateMutex` 아래에서만), 풀 전체 대형 캐시(`LargeCacheMutex`), `Tick()` |
| `HMemoryChunk` (스레드마다 1개, TLS 캐시) | `HPagePool Classes[18]`, lock-free MPSC 원격 반납 스택(소유 스레드가 다음 할당 때 pop-all, 대기 256 이상이면 즉시), `PageListMutex`(Empty · All 페이지 목록 전용) |
| `HPagePool` (2026-10-18 전 이름 `HSizeClass`) | 같은 크기 페이지 풀 — Partial/Empty 페이지 목록, 빈 블록 intrusive 목록, atomic 카운터(Live · Peak · Pages · EmptyCount · Growths · Releases · AllocCount), 디버그 격리 링 32 |
| `HPage` (64B 헤더) | 64KB `VirtualAlloc` 페이지(블록 주소 마스크로 페이지 조회). 32KB 이상 클래스는 블록 하나짜리 `malloc` 페이지. `EmptySince` 로 유휴 회수 |
| `HMemoryHeader` (16B) | 모든 블록 payload 앞. `MemorySize`(클래스 또는 `Large`) · `MemeoryState` · `OwnerChunkID`. 재설계 전과 같은 레이아웃 |
| `HLargeHeader` (32B) | 1MB 초과 또는 정렬 16 초과 요청. 요청 크기 그대로 잡고, 놓으면 대형 캐시(용량 × 4 ≤ 요청 × 5, 예산 64MB, 유휴 10초) |
| `HMemoryPoolConfig` | 클래스 8B~1MB 18개, 페이지 64KB, 페이지 헤더 64B, 청크 최대 256, 대형 캐시 64MB, 유휴 10초, 원격 반납 임계 256 |

- 고갈이 없다: 클래스가 비면 페이지를 추가한다(Info 1줄, 청크 커밋 16 · 32 · 64 · 128MB 문턱마다 Warning). 남은 실패는 시스템 힙 실패 하나이며 `poolFatal` 이 Critical 로그 뒤 `std::abort()` 한다. `nullptr` 반환 경로 없음(`Allocate<T>` · `HAllocator::allocate` 는 `JG_CHECK`).
- 빈 페이지는 같은 클래스가 LIFO 로 재사용하고 10초 유휴면 `Tick`(메인 스레드, `GMemoryGlobalSystem::Update`)이 시스템에 돌려준다(틱마다 클래스당 최대 32페이지, `free` 는 락 밖).
- 디버그 빌드(`_DEBUG`): 할당 0xCD · 해제 0xDD 채움(블록당 1MB 상한), 4KB 이하 클래스는 최근 해제 32개 격리. 릴리스 경로에는 코드가 없다.
- 트레이스: `MemoryPool.cpp` 맨 위 `#define JG_MEMORY_TRACE 0` (1-1). 1 로 바꾸면 할당 · 해제마다 `[ID: n] Allocated/Deallocated N byte, address : hex` Info 줄. 풀 안 로그는 `JG_POOL_LOG`(재진입 가드 `tlsInPoolLog`)로만, 청크 생성 · 성장 · 실패 · 종료에서만 부른다.

**안전장치 (Phase 1, `Memory.h`)**: `PSharedPtr`/`PWeakPtr` 의 `assign()` 헬퍼(새 참조 먼저 잡고 옛 참조 놓기, 같은 객체면 변화 없음), `operator=(nullptr_t)`, 자기 이동 가드 — `std::shared_ptr` 과 같은 의미론. `Allocate<T>`/`Wrap<T>` 의 `IMemoryObject` 파생 검사는 `static_assert`. `enable_if_t` 12곳.

**GC 제어 블록 (4-1 축소판, `Memory.h/.cpp`)**: 강 · 약 참조 수를 CRT 힙의 `PMemoryPrivate::HMemoryControlBlock { RefCount, WeakCount }` 하나로(`WeakCount` = 약참조 수 + 객체 생존 몫 1). GC 는 강참조 0 인 객체를 파괴한 뒤 생존 몫만 놓고, 마지막 몫을 놓는 쪽이 블록을 해제한다(`ReleaseWeakReference`). `PWeakPtr` 소멸자는 죽은 객체라도 몫을 놓고, `Pin()` 은 주소 조회 없이 "강참조 > 0 이면 +1" CAS, `Wrap()` 은 약참조 카운터도 채운다. 종료 강제 파괴에서 강참조가 남은 객체의 블록은 의도된 누수(이번 실행 0개).

**`HAllocator` (2-4, `Allocator.h`)**: `operator==`/`!=`, `is_always_equal`, `alignof(T)` 를 풀에 전달(16 초과는 대형 정렬 경로), `JG_CHECK(Result != nullptr)`, 메모리 시스템 종료 뒤 `deallocate` 는 무시 + 디버그 1회 `OutputDebugString`.

**통계 위젯 (2-2 → UI-1, `MemoryStatistics.cpp`)**: `GetStatInfo` 는 relaxed 카운터 읽기만(락 · 청크 워크 없음). 2026-09-30 UI-1 로 화면을 새로 짰다.

## 5. 알려진 함정 · 주의사항

설계 규칙(코드에 박혀 있거나 사용자가 정한 것):
- **풀 `Allocate`/`Deallocate` 정상 경로에서 `JG_LOG` 금지.** `AddLog` 가 `PString::Format` 으로 문자열을 만들므로 문자열 · 로깅이 풀을 쓰는 날 무한 재귀다. 풀 안 로그는 `JG_POOL_LOG`(재진입 가드)로 청크 생성 · 성장 · 실패 · 종료에서만. 로그 싱크(`Log.cpp` 의 `PRecentLogSink`)도 같은 이유로 std 컨테이너만 쓴다.
- **모든 블록은 청크 안에 있다**(헤더 16B, `OwnerChunkID` = 청크 테이블 인덱스, 0 = 메인). 외부 블록 · malloc 폴백을 만들지 않는다(사용자 결정). 대형 블록도 청크가 소유하는 블록 하나짜리 페이지다.
- **엔진 컨테이너를 static 저장소에 두지 않는다**(전역 · 함수 지역 · 클래스 static). 메모리 시스템이 내려간 뒤 DLL 언로드의 atexit 소멸자가 죽은 풀(디버그 이터레이터 프록시)을 읽어 0xC0000005. 잔존 위반: `DirectX12API.cpp:450-470` 폴백 함수 지역 `static HHashMap` 4개(폴백 경로가 돌 때만 생성, Graphics 5-17).
- `PSharedPtr` 를 든 글로벌 시스템은 모듈 `ShutdownModule` 에서 놓는다. `DisconnectModule` 직후 GC `Flush` 가 돈다.
- `IMemoryObject` 뿌리는 정확히 하나(오프셋 0). 다중 상속 시 `Allocate<T>` 의 `IMemoryObject*` 변환이 모호해진다(GameFrameWorks 는 `GameMasterActor.cpp:5` 처럼 관찰자를 분리해 우회).

종료 · GC:
- 종료 순서: `GCoreSystem::Destroy` → 모듈 `ShutdownModule` 역순 + `Flush` → `UnRegister` StringTable · ConsoleCommand · Object · Module · Schedule · Timer → **Memory**(소멸자 `forceFlush`: 강참조가 남아도 FIFO 로 강제 파괴) → Log → DLL 언로드. 강제 파괴된 객체의 제어 블록은 남기므로(4-1) 늦은 `PSharedPtr` 해제가 해제 메모리를 쓰진 않지만 **객체는 이미 없다**.
- GC 는 `GCoreSystem::Update` 2번째(그래픽 펜스 대기 전)에 돈다. 프레임 N 에 놓은 GC 객체는 N+1 시작에 파괴된다. GPU 리소스 자체는 Graphics 5-5 이후 `DestroyCommittedResource`(프레임 시리얼 지연)로 놓는다.
- 종료 코드 판독: `0xC0000005` = 종료 순서 버그, `3` = 예외 · assert · `abort`(풀 `poolFatal` 도 abort 이므로 Critical 로그를 먼저 본다), `4` = crashwalk 가 종료 행을 끊음.
- **JGConsole 은 `GCoreSystem::Update()` 를 부르지 않는다** → GC · 스케줄러 · 풀 `Tick` 이 돌지 않아 `Allocate<>` 객체가 `Destroy` 까지 남는다. 헤드리스 시나리오를 한 프로세스에 여러 개 쌓지 말고, 사이에 `GMemoryGlobalSystem::GetInstance().Flush()` 를 부르거나 프로세스를 나눈다.
- 디버그 풀 격리(4KB 이하 클래스 최근 해제 32개) 때문에 "해제 직후 재할당 = 같은 주소" 가 안 나온다. 주소 재사용(ABA) 재현은 DevelopEngine 에서 불가.
- 새 풀은 놓은 블록을 LIFO 로 바로 재배포하고 0xDD 로 채운다. 재설계 뒤 갑자기 드러난 손상은 대부분 **원래 있던 use-after-free** 다(0xDD 바이트 확인). 대표 패턴: 맵을 `const HPair<Key, Value>&`(키 non-const)로 순회하면 원소가 **복사**된다 → 그 안의 `HList::data()` 를 잡으면 dangling. 남은 복사 전용 사이트: `Json.h:723/749`, `ObjectGlobalSystem.cpp:286`, `ObjectGlobals.cpp:10`, `Scheduler.cpp:218`, `AssetDatabase.cpp:31/37`, `DX12Shader.cpp:11`, GameFrameWorks 6곳, JGBuildTool/JGHeaderTool. 새 코드는 `const auto&` 또는 `const HPair<const K, V>&`.

대리자(Core 공용, 2026-10-11 수정 뒤의 규칙 — §3-4):
- **방송 중 해제는 핸들만 무효로 하고, 칸은 가장 바깥 방송이 끝날 때 지운다.** 그래서 방송 중(콜백 안)의 `GetSize()` 는 뺀 구독을 아직 센다. 방송 밖에서는 바로 지워진다.
- `GetOwner` 는 **살아 있는 주인만** 돌려준다. 주인이 죽은 SP 구독은 nullptr 이라 `RemoveObject(옛 주소)` 로 못 뺀다 — `RemoveAll` 이나 핸들 `Remove` 로만 빠진다(보류). 같은 주소에 새 객체가 들어와도 옛 구독이 맞지 않는 것이 의도다.
- 방송 중 추가한 구독은 맨 뒤에 붙어 **같은 방송의 뒤 순서에서도 불린다**(`BroadCast` 가 칸마다 `size()` 를 다시 본다 — 코드 확인, 검사는 다음 방송에 불리는지만 본다). 그 추가로 목록이 다시 잡히면 실행 중인 32B 이하 콜백이 있던 메모리가 반납된다 → 콜백 안에서 `Add` 한 뒤에는 캡처를 읽지 않는다(보류).
- 옛 코드에서 방송 중 해제는 Debug 에서 `Assertion failed: _allocator.HasAllocation()`(`HDelegate::Execute` — 빈 대리자 실행)으로 멈췄다(종료 코드 없음). 같은 assert 를 다시 보면 어떤 해제 경로가 핸들을 남긴 채 콜백만 비운 것이다.
- `Compress()` 는 부르지 않는다(논리 오류, 보류).
- 람다는 늘 값으로 갖는다(ER-023, 10-11): 왼값은 복사, 오른값은 이동. 그래서 **복사할 수 없는 람다(`std::unique_ptr` 를 잡은 람다 등)는 걸 수 없다** — 오른값도 델리게이트 사본(Clone)이 복사를 요구한다. 걸고 난 뒤 원래 변수를 바꿔도 구독은 따라가지 않는다(따라가게 하려면 람다가 그 변수를 참조로 잡는다).
