## 1. 목표

1. **고갈이 없다.** 크기 클래스가 비면 그 클래스에 페이지를 하나 더 붙인다. `nullptr`을 돌려주는 경로가 사라진다(현황분석 P0-1, 0-2 재현 (a)).
2. **1MB 한도가 없다.** 최대 클래스를 넘는 요청은 풀 API 안의 대형 블록 경로가 요청 크기 그대로 잡고, 놓은 블록은 캐시에 두어 비슷한 크기의 반복 요청에 재사용한다(낭비 25%·총량 64MB·유휴 10초 상한. 0-2 재현 (b), `Graphics_TODO.md` 5-23).
3. **모든 블록은 청크 안에 있다.** 헤더 16바이트·`OwnerChunkID`로 소유 청크를 찾는 규칙이 그대로 성립한다. 대형 블록도 청크가 소유하는 "블록 하나짜리 페이지"라 예외가 아니다. 다른 점은 빈 목록에 넣지 않고 놓는 즉시 시스템 힙에 돌려준다는 것뿐이며, 풀 API 밖에서는 구분할 필요가 없다.
4. **상주 메모리를 실측에 맞춘다.** 스레드마다 100.69MB(30,768블록)를 미리 잡는 대신 페이지를 필요할 때 만든다. 기준선의 메인 스레드 정상 상태는 약 1MB, 워커는 0.5MB 안팎이다.
5. **스레드 간 해제가 안전하다.** 소유 스레드만 자기 청크의 목록을 만지고, 다른 스레드의 반납은 lock-free 스택으로 받는다(P0-5). `shared_lock`을 풀고 쓰던 iterator(P0-6)와 `hash<thread::id>` 충돌도 없앤다.
6. **통계가 O(1)이다.** 클래스별 live·피크·페이지 수·성장 횟수를 카운터로 들고, 청크 전체를 걷는 `GetStatInfo`를 없앤다(P1-14). 위젯이 클래스별 표를 보인다.
7. **`HAllocator`가 완성된다.** `operator==`, `is_always_equal`, 정렬 인자(P1-12).

**바꾸지 않는 것.** 풀 바깥의 API 모양(`HMemoryPool::Allocate/Deallocate`, `GetMemoryPool()`, `GetMemoryHeader()`, `HAllocator<T>`, `GMemoryGlobalSystem::Allocate<T>`/`Wrap`), 헤더 16바이트 레이아웃, GC·등록 테이블(`AllocatedMemoryBlocks`)은 그대로다(Phase 4에서 따로 다룬다). 컨테이너 사용 코드는 한 줄도 바뀌지 않는다.

## 3. 새 구조

### 3-1. 상수

| 이름 | 값 | 비고 |
|---|---|---|
| `kHeaderSize` | 16 | `HMemoryHeader` 그대로 |
| `kMinClass` | 8 B | 빈 블록 안에 next 포인터(8B)를 두므로 4B 클래스는 없앤다. 4B 요청은 8B 블록(기준선 4B 피크 3개) |

| `kIdleSeconds` | **10 (확정)** | 빈 페이지(클래스)와 캐시 블록(대형) 공통. 이 시간 다시 쓰이지 않으면 프레임 틱이 시스템에 돌려준다 |

### 3-2. 헤더

`HMemoryHeader`(16B: `EMemorySize MemorySize`, `EMemoryState State`, `uint64 OwnerChunkID`)는 위치·크기·필드가 그대로다. `GetMemoryHeader(ptr) = ptr - 16`도 그대로. 대형 블록은 그 앞에 16B를 더 둔다.

```
풀 블록:        [HMemoryHeader 16B][payload = 클래스 크기]           OwnerChunkID = 청크 인덱스
대형 블록:  [Raw 8B][Capacity 8B][HMemoryHeader 16B][payload = 요청 크기]  OwnerChunkID = 청크 인덱스, MemorySize = Large
                                ↑ ptr-16 은 두 종류 모두 HMemoryHeader
```

`Deallocate(ptr)`는 `ptr-16`을 읽어 `MemorySize`가 `Large`면 대형 경로, 아니면 클래스 경로로 간다. 두 종류 모두 `OwnerChunkID`로 소유 청크를 찾는다. 표식 검사 한 번이 두 종류를 가르는 전부다.

### 3-3. 크기 클래스와 페이지

stride = 크기 + 16. 페이지 = `malloc(블록 수 × stride)` 한 덩어리(16B 정렬). 만들 때 모든 블록 헤더에 `MemorySize`·`OwnerChunkID`를 쓰고 블록을 클래스 빈 목록에 잇는다.

| 클래스 | stride | 64KB 페이지의 블록 수 (헤더 48B 제외) | 기준선 메인 피크 | 정상 상태 페이지 |
|---:|---:|---:|---:|---:|
| 8 B | 24 | 2,728 | 6 | 1 |
| 16 B | 32 | 2,046 | 854 | 1 |
| 32 B | 48 | 1,364 | 123 | 1 |
| 64 B | 80 | 818 | 157 | 1 |
| 128 B | 144 | 454 | 616 | 2 |
| 256 B | 272 | 240 | 493 | 3 |
| 512 B | 528 | 124 | 13 | 1 |
| 1 KB | 1,040 | 62 | 42 | 1 |
| 2 KB | 2,064 | 31 | 4 | 1 |
| 4 KB | 4,112 | 15 | 3 | 1 |
| 8 KB | 8,208 | 7 | 2 | 1 |
| 16 KB | 16,400 | 3 | 1 | 1 |
| 32 KB | 32,784 | 1 (블록 하나짜리 페이지, 32,832 B) | 1 | 1 |
| 64 KB | 65,552 | 1 (블록 하나짜리 페이지, 65,600 B) | 0 | 0 |
| 128 KB~1 MB | | 1 (블록 하나짜리 페이지, 크기 + 64 B) | 워커만 | |

메인 스레드 정상 상태 = 페이지 16개 ≈ **1.0 MB**(지금 100.69 MB). 워커(에셋 로드)는 8·16·64·128·256·512 B·1 KB 각 1페이지 ≈ 0.4 MB, 1 MB급 버퍼 4개는 1 MB 클래스(블록 하나짜리 페이지)이며 로드가 끝나 놓이면 빈 페이지로 남아 있다가 10초 안에 다시 쓰이지 않으면 회수된다(§3-8b).

페이지 규칙:
- **lazy.** 청크 생성 때 아무것도 예약하지 않고 클래스의 첫 요청에서 첫 페이지를 만든다(첫 페이지는 성장으로 세지 않는다).
- **64KB 정렬.** 페이지는 `_aligned_malloc(64KB, 64KB)`로 잡아 시작 주소가 64KB의 배수다. 그래서 블록 주소에서 `& ~(64KB-1)` 한 번으로 페이지를 찾는다(헤더에 페이지 포인터를 넣지 않아도 된다).
- **페이지 헤더 48B.** 페이지 맨 앞에 `HPage`(클래스, 살아 있는 블록 수, 이 페이지의 빈 목록, 목록 링크)를 두고 첫 블록은 48B 뒤에서 시작한다(16B 정렬 유지).
- **블록 하나짜리 페이지.** stride 두 개가 64KB에 안 들어가는 클래스(32KB 이상)는 페이지 = 블록 하나. 페이지 크기는 `48 + stride`이고 페이지 주소는 `블록 - 64`로 찾는다. 이 클래스들은 놓으면 페이지째 회수되므로 "2블록 페이지의 나머지 절반"이 노는 일이 없다.
- **회수.** 페이지의 블록이 전부 돌아오면 그 페이지는 클래스의 Empty 목록으로 가고, 같은 클래스 요청이 오면 새 페이지 대신 그것을 쓴다. 10초 동안 쓰이지 않으면 프레임 틱이 시스템에 돌려준다(§3-8b, 대형 캐시와 같은 규칙). 돌려준 메모리는 어느 클래스든 다음 성장 때 다시 받는다.

### 3-4. 청크 (스레드마다 하나)

```cpp
struct HPage                            // 페이지 맨 앞 48B. 64KB 정렬이라 블록 주소를 마스크하면 나온다
{
	uint32 ClassIndex;
	uint32 Live;                        // 이 페이지에서 나가 있는 블록 수. 0 이면 Empty 목록으로
	uint32 BlockCount;
	uint32 _pad;
	void*  FreeHead;                    // 이 페이지의 빈 블록 목록 (intrusive, payload 첫 8B = next)
	HPage* NextPartial;                 // Partial 목록(빈 블록이 남은 페이지) 또는 Empty 목록 링크. 한 페이지는 둘 중 한 곳에만 있다
	HPage* NextAll;                     // 클래스의 모든 페이지 목록 링크 (종료·통계용)
	double EmptySince;                  // Empty 목록에 들어간 시각 (steady_clock 초). 10초 지나면 회수
};                                      // = 48B

struct HSizeClass                       // 소유 스레드만 만진다 (통계 필드는 atomic relaxed 로 다른 스레드가 읽기만)
{
	uint32 BlockSize;                   // 8 .. kMaxClass
	uint32 Stride;                      // BlockSize + 16
	uint32 BlocksPerPage;               // 1 이면 블록 하나짜리 페이지 (stride 가 32KB 이상)
	HPage* PartialHead = nullptr;       // 빈 블록이 남은 페이지들. 할당은 항상 이 목록의 첫 페이지에서. 소유 스레드만
	HPage* EmptyHead   = nullptr;       // 완전히 빈 페이지들. head = 가장 오래 비어 있던 것, tail = 최근. PageListMutex 아래에서만
	HPage* EmptyTail   = nullptr;
	HPage* AllHead     = nullptr;       // 모든 페이지. PageListMutex 아래에서만
	uint32 PageCount = 0;                   // PageListMutex 아래에서만 갱신
	std::atomic<uint32> EmptyCount = 0;     // 갱신은 PageListMutex 아래에서, 읽기는 Tick 이 락 없이 (0 이면 락을 잡지 않고 건너뛴다)
	std::atomic<uint32> Live = 0;       // 통계
	std::atomic<uint32> Peak = 0;
	std::atomic<uint32> Total = 0;      // 페이지 수 × BlocksPerPage
	std::atomic<uint32> Growths = 0;    // 첫 페이지 이후 추가된 페이지 수
	std::atomic<uint32> Releases = 0;   // 회수해 시스템에 돌려준 페이지 수
	std::atomic<uint64> AllocCount = 0; // 누적 (델타 감지·리플레이 대조용)
};

class HMemoryChunk
{
	uint64          Index;              // 청크 테이블 인덱스 = 헤더 OwnerChunkID
	std::thread::id OwnerThread;
	HSizeClass      Classes[kClassCount];           // 8B..kMaxClass, 인덱스 = log2(size) - 3
	std::atomic<void*>  RemoteFreeHead = nullptr;   // 타 스레드 반납 스택 (lock-free push / 소유자 pop-all)
	std::atomic<uint32> RemoteFreePending = 0;      // 통계: 아직 회수 안 된 원격 반납
	std::atomic<uint64> RemoteFreeTotal   = 0;      // 통계: 누적 (지금의 Dismatch 경고를 대신함)
	std::atomic<uint64> CommittedBytes    = 0;      // 페이지 합계
	std::mutex          PageListMutex;              // Empty·All 목록과 PageCount. 페이지가 생기고·비고·회수될 때만 잡는다(드문 이벤트).
	                                                // Tick(메인 스레드)이 다른 청크의 빈 페이지를 회수할 수 있게 하기 위한 것. Partial 목록과 블록 경로는 무락
	std::atomic<uint32> LargeLive         = 0;      // 대형 블록(블록 하나짜리 페이지) 통계. 어느 스레드에서든 free 되므로 atomic
	std::atomic<uint64> LargeBytes = 0, LargePeakBytes = 0, LargeTotal = 0;
};
```

### 3-5. 풀

```cpp
class HMemoryPool
{
	std::atomic<HMemoryChunk*> Chunks[kMaxChunks];  // 인덱스 = OwnerChunkID. 읽기는 락 없음
	std::atomic<uint32>        ChunkCount;
	std::mutex                 CreateMutex;         // 청크 생성 때만
	std::unordered_map<std::thread::id, uint32> ChunkIndexByThread;   // CreateMutex 아래에서만

	// 대형 블록 캐시 (§3-9). 드문 경로라 뮤텍스 하나. 노드는 빈 payload 안에 둔다
	std::mutex          LargeCacheMutex;
	HLargeCacheNode*    LargeCacheHead = nullptr;   // 최근 해제 순 (head = 최신, tail = 최고참)
	HLargeCacheNode*    LargeCacheTail = nullptr;
	uint64              LargeCachedBytes = 0;
	uint32              LargeCachedCount = 0;
	std::atomic<uint64> LargeReuseCount = 0, LargeReuseWasteBytes = 0, LargeEvictCount = 0, LargeIdleReleaseCount = 0;
};

// TLS 캐시. Core 는 정적 라이브러리라 DLL 마다 사본이 있지만, 각 사본이 같은 풀 객체에서 같은 청크 포인터를 얻으므로 문제없다.
thread_local struct { HMemoryPool* Pool; HMemoryChunk* Chunk; } tlsChunk;

HMemoryChunk& HMemoryPool::thisThreadChunk()
{
	if (tlsChunk.Pool == this && tlsChunk.Chunk != nullptr) return *tlsChunk.Chunk;     // 실제 코드는 중괄호 규칙 준수
	lock_guard lock(CreateMutex);
	auto iter = ChunkIndexByThread.find(std::this_thread::get_id());
	uint32 index = (iter != end) ? iter->second : createChunk();   // ChunkCount >= kMaxChunks 이면 Critical 로그 + 중단
	tlsChunk = { this, Chunks[index] };
	return *Chunks[index];
}
```

키가 `std::thread::id` 자체이므로 해시 충돌은 map 이 비교로 해결한다. 헤더에 들어가는 `OwnerChunkID`는 순번 인덱스라 `Deallocate`가 해시 없이 배열 한 번으로 청크를 찾는다.

### 3-6. 할당

```cpp
void* HMemoryPool::Allocate(uint64 size, uint64 alignment = 16)
{
	if (size > kMaxClass || alignment > 16) return allocateLarge(thisThreadChunk(), size, alignment);   // §3-9, §3-10. 이 스레드 청크가 소유하는 블록 하나짜리 페이지

	HMemoryChunk& chunk = thisThreadChunk();
	uint32 idx = classIndex(size);                    // 올림 2의 제곱 (uint64, _BitScanReverse64), 최소 8B → log2 - 3
	HSizeClass& cls = chunk.Classes[idx];

	HPage* page = cls.PartialHead;                    // 빈 블록이 남은 페이지 중 첫 번째
	if (page == nullptr)
	{
		drainRemoteFrees(chunk);                      // §3-7. 원격 반납을 페이지 목록에 되돌린다
		page = cls.PartialHead;
		if (page == nullptr)
		{
			page = takeEmptyOrGrow(chunk, cls);       // §3-8b. 10초 안에 비워진 빈 페이지가 있으면 그것, 없으면 새 페이지. 실패는 시스템 힙 실패뿐
			if (page == nullptr)
			{
				fatal("memory pool: page allocation failed", size, idx);   // Critical 로그 + 중단 (nullptr 을 돌려주지 않는다)
			}
		}
	}

	void* block = page->FreeHead;
	page->FreeHead = nextOf(block);
	++page->Live;
	if (page->FreeHead == nullptr)                    // 가득 찬 페이지는 partial 목록에서 뺀다
	{
		cls.PartialHead = page->NextPartial;
	}
	HMemoryHeader* header = GetMemoryHeader(block);   // MemorySize / OwnerChunkID 는 페이지 생성 때 써 둔 값
	header->MemeoryState = EMemoryState::Allocated;
	uint32 live = ++cls.Live;  if (live > cls.Peak) cls.Peak = live;  ++cls.AllocCount;
	debugFillAlloc(block, cls.BlockSize);             // §3-12 (디버그 빌드)
	return block;
}
```

정상 경로에 락·map 조회·CRT 호출·로그가 없다. 지금은 `shared_lock` + `unordered_map::find` + `std::map::find` + deque pop + (트레이스 시) 로그 두 줄이 붙는다.

`AlignPowerOfTwo`는 `1 << Log2()`가 `int` 시프트라 이 파일 안에 `uint64` 전용 `roundUpPow2`를 따로 둔다.

### 3-7. 해제

```cpp
void HMemoryPool::Deallocate(void* ptr)
{
	if (ptr == nullptr) return;
	HMemoryHeader* header = GetMemoryHeader(ptr);
	if (header->MemorySize == EMemorySize::Large) return deallocateLarge(ptr);           // §3-9. 어느 스레드에서든 즉시 free

	check(header->MemeoryState == EMemoryState::Allocated, "double free or foreign pointer");   // 디버그 assert, 릴리스 Critical 로그
	header->MemeoryState = EMemoryState::None;

	HMemoryChunk& owner = *Chunks[header->OwnerChunkID];
	if (&owner == tlsChunk.Chunk)                       // 소유 스레드: 자기 목록에 되돌림
	{
		HSizeClass& cls = owner.Classes[classIndex(header->MemorySize)];
		HPage* page = pageOf(ptr, cls);                 // 64KB 마스크. 블록 하나짜리 페이지는 ptr - 64
		debugFillFree(ptr, cls.BlockSize);
		bool wasFull = (page->FreeHead == nullptr);
		nextOf(ptr) = page->FreeHead;  page->FreeHead = ptr;  --page->Live;  --cls.Live;
		if (wasFull) { page->NextPartial = cls.PartialHead;  cls.PartialHead = page; }   // 다시 partial 목록으로
		if (page->Live == 0) { moveToEmpty(chunk, cls, page); }                         // §3-8b. Partial 에서 빼 Empty 목록으로 (비워진 시각 기록)
	}
	else                                                // 타 스레드: 소유 청크의 원격 스택에 lock-free push
	{
		void* head = owner.RemoteFreeHead.load();
		do { nextOf(ptr) = head; } while (!owner.RemoteFreeHead.compare_exchange_weak(head, ptr));
		++owner.RemoteFreePending;  ++owner.RemoteFreeTotal;
	}
}

void HMemoryPool::drainRemoteFrees(HMemoryChunk& chunk)      // 소유 스레드만 호출
{
	void* list = chunk.RemoteFreeHead.exchange(nullptr);     // 한 번에 전부 가져온다 (단일 소비자라 ABA 없음)
	for (; list != nullptr; list = next) { next = nextOf(list); (위 소유 스레드 경로와 같은 절차로 해당 페이지에 되돌린다); --RemoteFreePending; }
}
```

- 원격 반납은 소유 스레드의 다음 `Allocate`(빈 목록일 때) 또는 `RemoteFreePending`이 임계(예: 256)를 넘을 때 회수한다. 소유 스레드가 영원히 할당하지 않으면 그 블록은 그 청크 안에 묶여 있지만 새지는 않는다(종료 때 페이지 통째로 해제).
- 지금의 `Dismatch` Warning 로그(실행당 55줄)는 사라지고 `RemoteFreeTotal` 카운터가 대신한다.
- 소유 스레드 판정은 `std::this_thread::get_id()`가 아니라 TLS 캐시의 청크 포인터 비교라 비용이 없다.

### 3-8. 성장

```cpp
bool HMemoryPool::growClass(HMemoryChunk& chunk, HSizeClass& cls)
{
	uint64 pageBytes = (cls.BlocksPerPage > 1) ? kPageBytes : (sizeof(HPage) + cls.Stride);
	HPage* page = (HPage*)_aligned_malloc(pageBytes, kPageBytes);   // 64KB 정렬. 블록 주소 & ~(64KB-1) = 페이지
	if (page == nullptr) return false;
	page->ClassIndex = idx;  page->Live = 0;  page->BlockCount = cls.BlocksPerPage;  page->FreeHead = nullptr;
	for (int32 i = cls.BlocksPerPage - 1; i >= 0; --i)    // 헤더 초기화 + 페이지 빈 목록에 잇기 (주소 오름차순 배포)
	{
		HMemoryHeader* h = (HMemoryHeader*)((char*)page + sizeof(HPage) + i * cls.Stride);
		h->MemorySize = (EMemorySize)cls.BlockSize;  h->MemeoryState = None;  h->OwnerChunkID = chunk.Index;
		nextOf(h + 1) = page->FreeHead;  page->FreeHead = h + 1;
	}
	page->NextPartial = cls.PartialHead;  cls.PartialHead = page;
	{
		lock_guard lock(chunk.PageListMutex);         // All 목록·PageCount 는 Tick 도 만진다
		page->NextAll = cls.AllHead;  cls.AllHead = page;  ++cls.PageCount;
	}
	cls.Total += cls.BlocksPerPage;  chunk.CommittedBytes += pageBytes;
	if (cls.PageCount + cls.Releases > 1) { ++cls.Growths;  logGrowth(chunk, cls); }   // 첫 페이지는 성장이 아니다
	return true;
}
```

**성장 로그(결정 3).** 권장: 페이지 추가마다 **Info** 한 줄(`[Memory] chunk 0 class 32 B grew to 2 pages (2,730 blocks, committed 1.3 MB)`)과, 청크 `CommittedBytes`가 16·32·64·128 MB 문턱을 처음 넘을 때 **Warning** 한 줄. 이번 PSO 누수(프레임당 32B 3개)는 약 455프레임마다 Info 한 줄, 이후 문턱 Warning으로 드러나고, 자동 감지는 Phase 6-1(프레임별 델타)이 맡는다. 대안: 첫 페이지 이후 모든 성장을 Warning으로(128 B·256 B는 정상 상태에서도 2~3페이지라 매 실행 3줄이 경고로 찍힌다).

로그 호출은 재진입 가드 아래에서만 한다: `thread_local bool s_inPoolLog`가 참이면 로그를 건너뛴다. 로깅이 풀을 쓰게 되는 날에도 재귀하지 않는다.

### 3-8b. 페이지 회수 (남은 메모리 재활용)

크기 클래스 방식에서 페이지 안의 빈 블록은 **같은 클래스만** 다시 쓴다. 32B 페이지의 남은 자리를 1KB 요청이 쪼개 쓰게 하려면 가변 크기 분할·병합(버디 또는 범용 힙)이 필요한데, 그러면 O(1)이 아니고 외부 단편화와 병합 비용이 생긴다. 이 엔진의 할당 분포(작은 블록 수천 개 + 큰 버퍼 소수)에는 맞지 않아 택하지 않는다.

대신 **페이지 단위**로 재활용한다. 규칙은 대형 캐시(§3-9)와 같다(2026-09-28 사용자 결정으로 "보관 1개" 규칙을 없애고 통일).
- 페이지의 블록이 전부 돌아오면(`page->Live == 0`) 그 페이지를 Partial 목록에서 빼 클래스의 **Empty 목록** 끝에 넣고 비워진 시각을 적는다. 시스템에 바로 돌려주지 않는다.
- 같은 클래스에 요청이 와서 Partial 목록이 비어 있으면 새 페이지를 만들기 전에 Empty 목록에서 꺼내 쓴다(`malloc` 없음, 페이지 폴트 없음).
- **10초** 동안 다시 쓰이지 않은 빈 페이지는 프레임 틱이 시스템에 돌려주고, 그 메모리는 어느 클래스든 다음 성장 때 다시 받는다. 보관 개수 제한은 두지 않는다.
- 결과적으로 클래스에 잠기는 메모리는 "살아 있는 블록이 든 페이지 + 최근 10초 안에 비워진 페이지"다. 방금 쓰던 양을 넘지 않고 10초 뒤에는 실제 사용량으로 내려온다.

```cpp
void HMemoryPool::moveToEmpty(HMemoryChunk& chunk, HSizeClass& cls, HPage* page)   // 소유 스레드. page->Live == 0
{
	unlinkPartial(cls, page);                          // Partial 은 소유 스레드 전용이라 락 없음
	page->EmptySince = nowSeconds();
	lock_guard lock(chunk.PageListMutex);              // Empty 목록은 Tick(메인 스레드)도 만진다
	appendTail(cls.EmptyHead, cls.EmptyTail, page);  ++cls.EmptyCount;
}

HPage* HMemoryPool::takeEmptyOrGrow(HMemoryChunk& chunk, HSizeClass& cls)          // 소유 스레드
{
	{
		lock_guard lock(chunk.PageListMutex);
		if (cls.EmptyHead != nullptr)
		{
			HPage* p = popHead(cls.EmptyHead, cls.EmptyTail);  --cls.EmptyCount;
			p->NextPartial = cls.PartialHead;  cls.PartialHead = p;
			return p;
		}
	}
	return growClass(chunk, cls) ? cls.PartialHead : nullptr;
}

void HMemoryPool::releaseIdlePages(double now)                                     // Tick 에서, 메인 스레드
{
	for (each chunk) for (each cls)
	{
		if (cls.EmptyCount.load(std::memory_order_relaxed) == 0) continue;   // 빈 페이지가 없으면 락을 잡지 않는다 (정상 상태의 거의 모든 프레임)
		lock_guard lock(chunk.PageListMutex);
		while (cls.EmptyHead != nullptr && now - cls.EmptyHead->EmptySince > kIdleSeconds)   // head = 가장 오래 비어 있던 것
		{
			HPage* p = popHead(cls.EmptyHead, cls.EmptyTail);  --cls.EmptyCount;  unlinkAll(cls, p);
			--cls.PageCount;  cls.Total -= p->BlockCount;  chunk.CommittedBytes -= pageBytesOf(cls);  ++cls.Releases;
			_aligned_free(p);
		}
	}
}
```

- Partial 목록은 소유 스레드만 만지므로 무락이다. Empty·All 목록과 `PageCount`만 `PageListMutex`로 지키며, 이 락은 페이지가 생기고·비고·회수되는 드문 이벤트에만 잡힌다. 블록 할당·해제의 정상 경로에는 락이 없다.
- **성능 영향.** 락이 잡히는 곳은 (1) 페이지 생성, (2) 페이지가 완전히 빔, (3) Empty 페이지 재사용, (4) Tick의 회수 검사다. (1)~(3)은 기준선에서 실행 전체에 수십 번 수준이고(정상 상태 메인 청크 페이지 16개), 정상 상태의 블록 연산 345회/프레임에는 락이 하나도 없다. (4)는 `EmptyCount == 0`이면 락 없이 건너뛰므로 빈 페이지가 있는 프레임에만 청크×클래스당 한 번 잡는다(비경합 `std::mutex` 잠금·해제는 수십 ns). 경합은 소유 스레드가 페이지 이벤트를 일으키는 바로 그 순간에 Tick이 같은 클래스를 볼 때만 생기고, 기다려도 회수 루프(`_aligned_free` 몇 번) 길이다. 지금 코드가 **모든** 할당에 `shared_lock` + `unordered_map` 조회를 하는 것과 비교하면 락 횟수가 수만 분의 일이다.
- **락을 완전히 없애는 대안(소유 스레드 회수).** 회수를 Tick이 아니라 각 소유 스레드가 자기 할당·해제 경로에서 간헐적으로(예: 64번에 한 번 또는 1초에 한 번) 하게 하면 뮤텍스가 필요 없고 모든 페이지 목록이 스레드 소유가 된다. 대가는 셋이다. (1) 한동안 풀을 안 쓰는 스레드(대기 중인 로드 스레드)의 빈 페이지는 그 스레드가 다시 움직일 때까지 남는다(직전 버스트 이하로 묶이고 다음 버스트에 재사용됨). 유휴 진입 훅으로 즉시 놓게 하면 재사용을 잃고, 메인이 대신 회수하게 하면 "쉬는 중" 핸드셰이크가 필요해 결국 락과 같다. (2) 정상 경로에 카운터 증가·분기 하나와 N번마다 시계 읽기(수십 ns)가 들어간다. 무시할 크기지만 0은 아니다. (3) 회수 작업이 임의의 할당 호출 안에서 일어나 그 호출이 수십 µs 길어질 수 있다(Tick은 프레임 시작의 정해진 자리에서 한다). 그래서 기본은 Tick + 뮤텍스이고, 2-6 스트레스 테스트에서 락 대기가 측정되면 이 방식으로 바꾼다. 구조는 같고 회수 호출 위치만 옮기면 된다.
- `unlinkPartial`·`unlinkAll`은 단일 연결 목록에서 O(페이지 수)다. 클래스의 페이지는 보통 몇 개라 문제없고, 커지면 이중 연결로 바꾼다.
- 블록 하나짜리 페이지(32KB 이상 클래스)는 놓는 순간 `Live == 0`이라 Empty 목록으로 간다. 1MB 버퍼 4개를 쓰고 놓으면 4개가 10초까지 남아 있다가 회수되고, 그 사이 로드가 이어지면 그대로 재사용된다.
- 디버그 격리(§3-12)에 들어 있는 블록은 아직 페이지에 돌아오지 않은 것이므로 그만큼 비워지는 시점이 늦어진다. 의도된 동작이다.
- 통계에 `EmptyCount`(현재 빈 페이지 수)와 `Releases`(회수 횟수)가 추가된다. 같은 클래스에서 성장과 회수가 번갈아 많이 일어나면 유휴 시간을 늘릴 신호다.

### 3-9. 대형 블록 (결정 2 · 확정: 1MB 초과 → 정확한 크기 + 대형 캐시)

크기 클래스는 2의 제곱이라 큰 요청을 클래스로 받으면 낭비가 큰 크기에서 가장 커진다(1.2MB 요청 → 2MB 블록, 9MB → 16MB). 그리고 클래스에는 상한이 있어야 한다. 그래서 **1MB(최대 클래스)를 넘는 요청은 요청 크기 그대로 잡는 블록 하나짜리 페이지**로 처리한다. 청크가 소유하고 같은 헤더 자리를 쓰므로 "모든 블록은 청크 안" 규칙이 유지된다.

놓을 때는 바로 `free`하지 않고 **대형 캐시**에 넣는다. 스트리밍·로딩처럼 비슷한 크기의 큰 버퍼가 반복되면 시스템 힙 호출과 페이지 폴트 없이 재사용되고, 세 규칙이 캐시가 메모리를 붙들고 있는 것을 막는다.
- **크기 맞춤.** 캐시 블록 용량이 `요청 ≤ 용량 ≤ 요청 × 1.25`일 때만 재사용한다(낭비 상한 25%. 같은 크기가 반복되면 0). 범위 안에서 가장 작은 것을 고른다.
- **총량 예산.** 캐시 합계가 64MB를 넘으면 가장 오래된 것부터 시스템에 돌려준다. 예산보다 큰 블록은 캐시하지 않고 바로 돌려준다.
- **유휴 해제.** 10초 동안 쓰이지 않은 캐시 블록은 매 프레임 틱(`GMemoryGlobalSystem::Update` → `HMemoryPool::Tick`)에서 돌려준다(빈 페이지 회수 §3-8b와 같은 시간). 로딩이 끝나면 캐시는 자연히 비고 상주 메모리가 내려온다.

같은 시나리오를 따라가면 이렇게 된다(1.6MB × 1.25 = 2.0MB가 경계값. 구현은 정수 비교 `용량 × 4 ≤ 요청 × 5`로 경계를 정확히 본다. 1.6MiB는 1,677,721.6B라 검증 코드는 1,677,722B로 올려 쓴다).

| 순서 | 동작 | 캐시 상태 |
|---|---|---|
| 2MB 할당 | `malloc`, 정확히 2MB | 비어 있음 |
| 2MB 해제 | 캐시에 넣음 | 2MB 1개 |
| 1.6MB 할당 | 2.0MB ≤ 1.6 × 1.25 → **재사용** (낭비 0.4MB 누적 카운터) | 비어 있음 |
| 1.6MB 해제 | 캐시에 넣음 (용량은 2MB) | 2MB 1개 |
| 1.2MB 할당 | 2.0MB > 1.2 × 1.25 = 1.5MB → 새로 `malloc` 1.2MB | 2MB 1개 |
| 10초 경과 | 틱이 2MB를 `free` | 비어 있음 |

```cpp
struct HLargeHeader    { void* Raw; uint64 Capacity; HMemoryHeader Header; };        // 32B. Header 가 payload 바로 앞 = 일반 블록과 같은 자리
struct HLargeCacheNode { HLargeCacheNode* Prev; HLargeCacheNode* Next; double FreedSeconds; };   // 캐시에 있는 동안 빈 payload 첫 24B 에 둔다

void* HMemoryPool::allocateLarge(HMemoryChunk& chunk, uint64 size, uint64 alignment)
{
	uint64 align = max(alignment, 16);
	char* payload = (align == 16) ? tryReuseLarge(size) : nullptr;      // 정렬 16 초과 요청은 캐시를 쓰지 않는다 (§3-10)
	if (payload == nullptr)
	{
		char* raw = (char*)malloc(size + kLargeHeaderSize + (align - 1));    // 헤더 32B + 정렬 여유
		if (raw == nullptr) fatal("memory pool: large allocation failed", size);   // 유일하게 남는 실패 경로. Critical 로그 + 중단
		payload = alignUp(raw + kLargeHeaderSize, align);
		HLargeHeader* fresh = (HLargeHeader*)(payload - kLargeHeaderSize);
		fresh->Raw = raw;  fresh->Capacity = size;
	}
	HLargeHeader* lh = (HLargeHeader*)(payload - kLargeHeaderSize);
	lh->Header = { EMemorySize::Large, EMemoryState::Allocated, chunk.Index };   // 소유 청크 = 이번에 할당(재사용)한 스레드
	uint64 bytes = (chunk.LargeBytes += lh->Capacity);  if (bytes > chunk.LargePeakBytes) chunk.LargePeakBytes = bytes;
	++chunk.LargeLive;  ++chunk.LargeTotal;
	debugFillAlloc(payload, size);
	return payload;
}

char* HMemoryPool::tryReuseLarge(uint64 size)                             // 캐시에서 [size, size×1.25] 중 가장 작은 것
{
	lock_guard lock(LargeCacheMutex);
	HLargeCacheNode* best = nullptr;
	for (HLargeCacheNode* n = LargeCacheHead; n != nullptr; n = n->Next) // 캐시는 수십 개 이하 (예산 64MB / MB 단위)
	{
		uint64 cap = headerOf(n)->Capacity;
		if (cap >= size && cap * 4 <= size * 5 && (best == nullptr || cap < headerOf(best)->Capacity)) best = n;   // 정수 비교로 1.25배 경계를 정확히
	}
	if (best == nullptr) return nullptr;
	unlink(best);  LargeCachedBytes -= headerOf(best)->Capacity;  --LargeCachedCount;
	++LargeReuseCount;  LargeReuseWasteBytes += headerOf(best)->Capacity - size;
	return (char*)best;                                                   // 노드 위치 = payload
}

void HMemoryPool::deallocateLarge(void* ptr)                              // 어느 스레드에서든 호출 가능
{
	HLargeHeader* lh = (HLargeHeader*)((char*)ptr - kLargeHeaderSize);
	check(lh->Header.MemeoryState == EMemoryState::Allocated, "double free");
	HMemoryChunk& chunk = *Chunks[lh->Header.OwnerChunkID];               // 통계 갱신용
	chunk.LargeBytes -= lh->Capacity;  --chunk.LargeLive;
	lh->Header.MemeoryState = EMemoryState::None;
	debugFillFree(ptr, lh->Capacity);
	if (lh->Capacity > kLargeCacheBudget) { free(lh->Raw); return; }     // 예산보다 큰 것은 캐시하지 않는다
	lock_guard lock(LargeCacheMutex);
	pushHead((HLargeCacheNode*)ptr, /*FreedSeconds=*/nowSeconds());  LargeCachedBytes += lh->Capacity;  ++LargeCachedCount;
	while (LargeCachedBytes > kLargeCacheBudget) { evictTail();  ++LargeEvictCount; }   // 오래된 것부터 free
}

void HMemoryPool::Tick()                                                  // GMemoryGlobalSystem::Update 에서 매 프레임
{
	double now = nowSeconds();                                            // std::chrono::steady_clock. 엔진 타이머에 의존하지 않는다
	releaseIdlePages(now);                                                // §3-8b 빈 페이지 회수
	lock_guard lock(LargeCacheMutex);
	while (LargeCacheTail != nullptr && now - LargeCacheTail->FreedSeconds > kIdleSeconds) { evictTail();  ++LargeIdleReleaseCount; }
}
```

- 이 경로는 **풀 API 안**에 있다. 호출자(`HAllocator`, `Allocate<T>`)는 모른다. 표식 검사는 `Deallocate` 첫 줄 한 번.
- 해제와 재사용은 소유 스레드를 거치지 않는다. 캐시는 풀 전체에 하나이고 뮤텍스 하나로 지킨다(드문 경로). 재사용된 블록의 소유 청크는 이번에 받은 스레드의 청크로 바뀐다(헤더 `OwnerChunkID` 갱신). 큰 버퍼가 원격 스택에 묶여 있는 일이 없다.
- 캐시 노드(Prev·Next·해제 시각 24B)는 빈 payload 안에 둔다. 헤더(`Raw`·`Capacity`)는 캐시에 있는 동안 그대로라 재사용 때 다시 쓴다.
- 정렬 16 초과로 잡은 블록도 캐시에 들어가되(16 정렬은 만족하므로 일반 요청에 재사용 가능), 정렬 16 초과 **요청**은 캐시를 보지 않고 새로 잡는다.
- 헤더를 32B로 늘리는 것은 대형 블록만이다. 모든 블록의 헤더를 32B로 키우면 32B 클래스에서 50%가 헤더가 된다.
- 로그는 없다(1080p 리드백처럼 매 프레임 올 수 있다). 카운터가 위젯에 나온다: 청크별 live 개수·바이트·피크·누적, 풀 전체 캐시 개수·바이트, 재사용 횟수, 재사용 누적 낭비, 예산 초과 해제, 유휴 해제. 트레이스 빌드에서는 일반 블록과 같은 줄이 찍혀 `memlog_stats.sh`가 그대로 읽는다.
- 종료 때 `LargeLive > 0`이면 누수로 보고 개수·바이트를 Warning으로 남기고(살아 있는 대형 블록은 목록에 없으므로 풀이 대신 해제하지 않는다), 캐시에 있는 블록은 모두 `free`한다.
- 매 프레임 같은 큰 버퍼를 잡고 놓는 코드는 장기적으로 그 시스템이 버퍼를 유지하는 게 맞다. 캐시는 그런 코드가 들어와도 풀이 버티게 하는 안전망이다.
- 지금 `std::vector`로 우회한 12곳(`HTexturePixels::Data`, DevScene RGBA 버퍼, `JGTexture` 압축 버퍼 등)은 이 경로가 들어오면 `HList`로 되돌릴 수 있다(2-6 뒤, 별도 항목).

**결정 2 — 확정(2026-09-28, 사용자).** 상한 1MB(클래스 8B~1MB 18개, 32KB 이상은 블록 하나짜리 페이지). 1MB 초과는 정확한 크기 + 대형 캐시(낭비 1.25배 상한·예산 64MB·유휴 10초). 검토했던 다른 길과 그 이유:
- (B) 64KB 초과 → 정확한 크기, 캐시 없음: 지금 기준선(1MB 초과 할당은 에셋 로드 때 6회)에는 충분하지만 스트리밍·로딩이 반복되는 미래에 매번 시스템 힙을 부른다.
- (A′) 1MB 위도 2의 제곱 클래스로 연장: 같은 클래스 반복은 재사용되지만 큰 크기에서 낭비가 최대 50%이고(9MB → 16MB) 보관 페이지가 큰 덩어리로 논다. 범용 할당자들이 큰 크기에 2의 제곱을 쓰지 않는 이유.
- (C) 대형 경로 없이 Critical + 중단: `std::vector` 우회 유지. 권하지 않았다.

### 3-10. 정렬

- 페이지 시작은 `malloc` 16B 정렬. stride가 8B 클래스는 24(8의 배수), 16B 이상은 16의 배수 → payload 정렬은 8B 클래스 8, 그 위는 16. 지금은 개수 표에 기대던 것을 stride 규칙으로 보장한다.
- `alignment > 16` 요청(`alignas(32)` 등)은 크기와 무관하게 대형 경로로 보내 `alignUp`으로 맞춘다. 드문 경우라 클래스마다 정렬 변형을 두지 않는다.
- `HAllocator<T>::allocate`는 `Allocate(count * sizeof(T), alignof(T))`를 부른다. `GMemoryGlobalSystem::Allocate<T>`도 `alignof(T)`를 넘긴다.

### 3-11. 통계와 위젯 (2-2)

`HMemoryChunkStatInfo`는 위젯이 쓰는 `ChunkID`, `TotalMemorySize`(= CommittedBytes), `AllocatedMemorySize`(= Σ Live × BlockSize), `HeaderMemorySize`(= Σ Total × 16)를 유지하고, 블록 단위 벡터(`AllocatedMemories`/`EmptyMemories`)를 없앤다. 대신 `Classes[]{BlockSize, BlocksPerPage, Pages, Total, Live, Peak, Growths, AllocCount}`, `RemoteFreePending/Total`, `OwnerThreadID`를 넣고, 청크 항목에 `LargeLive/Bytes/PeakBytes/Total`을, `HMemoryPoolStatInfo`에 그 합계와 `ChunkCount`, 대형 캐시 상태(`CachedCount/Bytes`, `ReuseCount`, `ReuseWasteBytes`, `EvictCount`, `IdleReleaseCount`)를 넣는다. `GetStatInfo`는 카운터를 relaxed로 읽기만 한다(다른 스레드 청크 값은 한 프레임 늦을 수 있다. 통계 용도라 허용).

위젯(`MemoryStatistics.cpp`): 루프 안 `[0]`을 `ChunkStatInfo`로. 스레드별 막대(커밋 vs live) 아래에 클래스별 표(크기 · live/total · 페이지 · 성장 · 사용률), 원격 반납 대기 수, 대형 블록 행. 사용률 90% 이상(다음 할당이 성장을 일으킴)과 성장 횟수 > 0 을 강조.

### 3-12. 디버그 채움과 격리 (결정 4)

빈 목록이 LIFO 스택이 되면 **방금 놓은 블록이 바로 다음 요청에 재배포**된다. 지금은 큐(FIFO)와 클래스당 수천 개 여유가 사실상 "격리 구역" 노릇을 해서, 해제된 컨테이너 버퍼를 가리키는 댕글링 포인터 같은 잠재 버그가 드러나지 않았을 수 있다. 재설계 뒤 그런 버그는 즉시 손상으로 나타난다. 그래서 디버그 빌드에 두 장치를 둔다.

- **채움**: 할당 시 payload를 `0xCD`, 해제 시 `0xDD`로 채운다(MSVC 디버그 힙과 같은 값. 대형 블록도). 해제 뒤 읽으면 `DDDDDDDD`가 보여 원인이 바로 잡힌다.
- **격리**: 클래스마다 최근 해제 N개(권장 32)를 링에 잡아 두고 그 뒤에 빈 목록에 넣는다. 재사용을 N번 늦춰 UAF가 값 손상으로 드러날 시간을 준다. 메모리 비용은 클래스당 N블록.

둘 다 `_DEBUG`에서만 켜고 릴리스 경로에는 코드가 없다(`#if`). 권장: 채움 켬, 격리 32.

### 3-13. 종료

`HMemoryPool::Shutdown`: 청크마다 클래스의 `AllHead` 목록(Empty 페이지 포함)을 따라 페이지 전부 `_aligned_free`, 원격 스택은 버림(페이지에 속하므로 따로 해제 없음), 대형 캐시의 블록은 모두 `free`. 대형 블록이 남아 있으면(어느 청크든 `LargeLive > 0`) 개수·바이트를 Warning으로 남긴다(누수 리포트. Phase 4-3의 GC 생존 객체 리포트와 짝). TLS 캐시는 `Pool != this`로 무효화되므로 따로 지울 것이 없다. `HAllocator::deallocate`가 시스템 해제 뒤 불리면 지금처럼 무시하되 디버그에서 1회 `OutputDebugString`(정적 컨테이너 규칙 위반 감지).

### 3-14. 호출자 쪽 변경

- `Allocator.h`: `allocate(count)` → `Allocate(count * sizeof(T), alignof(T))`(현재 `int32 MemSize` 캐스트 제거), `operator==`/`!=`(항상 같음), `using is_always_equal = std::true_type`. 이후 `HList::swap`·이동 대입이 컴파일되므로 "복사 후 clear" 우회를 되돌린다.
- `Memory.h` `GMemoryGlobalSystem::Allocate<T>`: `MemoryPool.Allocate(sizeof(T), alignof(T))` + `JG_CHECK(MemPtr != nullptr)`(성장 뒤에는 도달하지 않지만 계약을 코드로 남긴다).
- `EMemorySize`: `_4_Byte`·`_1_GB`(실제 2MB)는 더 쓰지 않는다. 열거형은 헤더 필드 타입이라 남기고, 대형 블록 표식은 새 열거자 `Large = 1`이다(`Unknown = 0`은 초기화되지 않은 헤더와 구분하기 위해 그대로 둔다).

## 7. 검증 (Memory_TODO 2-6)

1. **빌드**: 전체 오류 0, 경고 기준선(C4244 4·LNK4098 1) 유지.
2. **0-2 재현 (a) `exhaust32`**: 32B 클래스에 페이지가 추가되며(Info 로그, `Growths` 증가) 4,097번째 이후도 계속 할당, `HList<uint8>(32)` 정상, 종료 코드 0. 임시 코드의 "survived" 로그가 찍히고 반납까지 끝난다.
3. **0-2 재현 (b) `oversize`**: 2MB `HList`가 대형 경로로 성공(`LargeLive` 1), 해제 뒤 캐시에 들어감(`CachedBytes` 2MB), 종료 코드 0.
3-b. **대형 캐시 (`JG_MEMTEST=largecache`)**: §3-9 표의 시나리오 그대로 — 2MB 할당·해제 → 1.6MB 할당이 재사용(`ReuseCount` 1, `ReuseWasteBytes` 0.4MB) → 해제 → 1.2MB 할당은 새 블록(`ReuseCount` 그대로, `CachedCount` 1) → 11초 대기 뒤 `CachedBytes` 0(`IdleReleaseCount` 1). 이어서 1MB+1 크기를 70회 할당·해제해 예산 64MB 초과 시 오래된 것부터 해제(`EvictCount` > 0, `CachedBytes` ≤ 64MB). 정렬 32 요청은 캐시를 지나치는지(`ReuseCount` 불변) 확인.
3-c. **빈 페이지 회수 (`JG_MEMTEST=emptypages`)**: 32B 블록 3,000개 할당(페이지 3개, `Growths` 2) → 전부 해제 → 즉시 `EmptyCount` 3·`PageCount` 3 → 5초 뒤 32B 1개 할당하면 빈 페이지 재사용(`Growths` 불변, `EmptyCount` 2) → 11초 뒤 나머지 2개 회수(`Releases` 2, `PageCount` 1, `CommittedBytes` 감소). 1MB 4개 할당·해제도 같은 방식으로 4개가 남았다가 11초 뒤 0.
4. **상주 메모리**: 정상 상태에서 `Get-Process JGLauncher | % WorkingSet64` 또는 Private Bytes를 기준선(청크 2개 ≈ 201MB 커밋)과 비교. **150MB 이상 감소**가 합격.
5. **교차 스레드 스트레스** (`JG_MEMTEST=stress`): 로드 스레드에서 `HList` 10만 개 할당 → 메인에서 해제, 반대 방향도, 디버그 빌드 10회. 손상·assert 0, 끝나면 `RemoteFreePending` 0, 모든 클래스 `Live` 0.

| TLS가 DLL마다 사본 | 사본마다 같은 청크 포인터를 캐시하므로 정합. `Pool != this` 검사로 재생성 대비. 8모듈 런타임에서 스트레스 테스트로 확인 |

## 9. 이후 단계와의 연결

- **Phase 3(흡수 1차)**: 델리게이트·모듈 객체·문자열 참조 카운트가 들어와도 페이지 성장으로 흡수된다. 위젯 클래스별 표로 증가량을 본다.
- **Phase 4-1(GC 제어 블록)**: 제어 블록을 객체 앞 고정 오프셋에 둘 때 `Allocate<T>`가 `sizeof(T) + 제어블록`을 요청하면 되고, 헤더 16B는 그대로다. 헤더 확장을 택하면 이 문서의 stride 표만 다시 계산한다.
- **Phase 5(ImGui·rapidjson)**: 대형 경로가 있으므로 1MB 초과 요청이 안전하다. rapidjson `Realloc`은 할당·복사·해제로 구현.
- **Phase 6-1**: `AllocCount`·`Live` 카운터가 프레임별 델타 감지의 입력이 된다.
- **Phase 7-4(`PString` 풀 이전 재검토)**: 재진입 가드가 있어 문자열이 풀을 써도 성장 로그가 재귀하지 않는다.
