## 0. Core 모듈

Core는 엔진의 가장 하위 계층에 위치한 기반 모듈이다. 엔진의 모든 모듈은 Core에 의존하며, Core는 Graphics, GUI 등 상위 시스템이 공통으로 사용하는 기본 기능을 제공한다.

![Core 모듈 — Core.lib 안의 관리자 GCoreSystem, 전역 시스템 기반 클래스를 상속한 베이스 시스템 8개, 공용 도구, Core에 의존하는 모듈 DLL의 기반 클래스 IModuleInterface와 모듈이 등록한 전역 시스템](그림/Core_00_Core모듈.svg)

## 1. 엔진 내 Core의 위치

Core는 정적 라이브러리(`Core.lib`)이며, 실행 파일과 모든 모듈 DLL에 링크된다. 따라서 바이너리마다 Core 코드의 사본이 포함되고, 모듈 DLL은 로드될 때 실행 파일의 관리자 인스턴스에 연결된다.

### 1-1. Core 의존 관계

![Core 의존 관계 — Asset · Audio · Graphics · GUI · GameFrameWorks · GameHost · JGEditor 모듈과 실행 프로그램은 모두 Core를 링크하여 사용하며, Core는 다른 모듈에 의존하지 않음](그림/Core_01_누가기대나.svg)

- 화살표는 링크 의존을 나타낸다. JGGameBootstrap을 제외한 엔진 프로젝트 17개가 모두 Core를 링크한다([[JGEngine 구조도]] 2번).
- 각 상자에는 해당 모듈이 Core에서 주로 사용하는 기능을 적었다.
- Core는 다른 엔진 모듈에 의존하지 않으며, 외부 라이브러리로 spdlog와 rapidjson만 사용한다.

### 1-2. 바이너리별 Core 사본

![바이너리별 Core 사본 — Graphics.dll · GameFrameWorks.dll · 게임 모듈 DLL에 포함된 Core 사본이 Link_Module을 통해 JGLauncher.exe의 실제 GCoreSystem에 연결됨](그림/Core_02_Core사본.svg)

- 모듈 DLL이 로드되면 엔진이 해당 DLL의 `Link_Module`을 호출해 실행 파일의 관리자 주소를 전달한다. 이후 그 DLL에서 호출하는 전역 시스템(`GetInstance()`)은 모두 실행 파일의 인스턴스를 가리킨다.
- 엔진 경로, 프로젝트 경로 같은 전역 값도 관리자 내부(`HCoreSystemGlobalValues`)에 두어 모든 DLL이 같은 값을 참조한다.
- 반면 `static` 변수는 바이너리마다 따로 존재한다. 콘솔 명령 목록의 헤드(`HAutoConsoleCommand::Head`)가 그 예다. 따라서 여러 DLL이 공유해야 하는 상태는 관리자를 통해 관리한다.

## 2. 엔진 생명 주기

엔진은 초기화, 프레임 갱신, 종료의 세 단계로 동작한다. 초기화 단계에서 관리자가 베이스 시스템을 생성하고 실행 모듈(Launch Module)을 연결하며, 실행 모듈이 나머지 필요한 모듈을 연결한다. 이후 창이 닫힐 때까지 매 프레임 시스템을 갱신하고, 종료 단계에서 초기화의 역순으로 해제한다.

### 2-1. 초기화

![초기화 — 런처, Core 관리자, 베이스 시스템, 모듈 시스템, 실행 모듈 사이의 초기화 호출 순서](그림/Core_03_켜질때.svg)

- 런처는 JGLauncher 또는 패키지 실행 파일이고, Core 관리자는 `GCoreSystem`이다. 실행 모듈은 에디터 실행 시 JGEditor, 게임 단독 실행 시 GameHost다. 실행 모듈이 연결하는 모듈은 Graphics, GUI, Asset, GameFrameWorks, 게임 모듈 등이다.
- 관리자는 `Create`에서 베이스 시스템 8개를 등록한 뒤 엔진 루트와 프로젝트 루트를 결정하고(10번), 리플렉션 정보를 등록한다(5번). 그다음 실행 모듈을 연결하고, 마지막으로 모든 시스템의 `Start`를 호출한다.
- 창은 Core가 아니라 실행 모듈이 `StartupModule`에서 생성한다(9번). 따라서 실행 모듈의 `StartupModule`은 시스템 `Start`보다 먼저 호출된다.
- 패키지 빌드에서 `Bin/JGPackage.json`을 읽지 못하면 리플렉션 등록과 실행 모듈 연결을 건너뛰고 종료 코드 2로 끝난다.

### 2-2. 프레임 갱신

![프레임 갱신 — GCoreSystem::Update가 1 메모리 GC, 2 타이머, 3 스케줄(프레임 단계 Graphics Begin → Begin → Update → End → Graphics End → Update Window), 4 문자열 테이블, 5 콘솔 명령, 6~8을 순서대로 호출하고, 창이 닫히면 종료 단계로 진행](그림/Core_04_프레임한바퀴.svg)

| 프레임 단계 | 처리 내용 | 등록 위치(코드 확인) |
|---|---|---|
| GraphicsBegin | 프레임 시작. 재사용할 프레임 자원의 GPU 작업 완료 대기(펜스 대기), ImGui 새 프레임 시작 | Graphics `BeginFrame`, GUI `NewFrame` |
| Begin | 현재 사용처 없음 | — |
| Update | 게임 로직, 월드, 게임 UI 갱신, 에디터 위젯 갱신 | GameFrameWorks `tick`, GUI `UpdateWidgets` |
| End | 게임 화면 렌더링 명령 기록(게임 단독 실행 시) | GameHost `renderFrame` |
| GraphicsEnd | GPU 제출, Present | Graphics `EndFrame` |
| UpdateWindow | 윈도우 메시지 처리(`WM_QUIT` 수신 시 루프 종료) | 창 `Update`(메시지 펌프) |

- 관리자의 `Update`는 등록된 시스템을 등록 순서대로 한 번씩 갱신한다. 게임 로직과 렌더링은 스케줄 시스템(그림의 3)이 프레임 단계별로 등록된 작업을 실행하면서 처리된다(`ScheduleByFrame(단계, 작업)`, 단계 열거형 `EMainThreadExecutionOrder`).
- 프레임 N에서 참조가 모두 해제된 객체는 프레임 N+1의 메모리 시스템 갱신(그림의 1)에서 파괴된다(4번).
- JGConsole 같은 헤드리스 도구는 프레임 루프를 실행하지 않으므로 GC와 스케줄 작업이 동작하지 않는다.

### 2-3. 종료

![종료 — 창 닫힘 → GCoreSystem::Destroy → 창 콜백 해제 → 시스템 Destroy(등록 역순: 모듈이 등록한 시스템 → 모듈 ShutdownModule) → GC Flush → 베이스 시스템 해제 → DLL 언로드](그림/Core_05_꺼질때.svg)

- 종료는 초기화의 역순으로 진행한다. 나중에 등록된 시스템과 모듈이 먼저 등록된 것에 의존하기 때문이다.
- 메모리 시스템은 로그 시스템 다음으로 늦게 해제된다. 모든 시스템이 메모리 시스템을 사용하기 때문이다.
- 창 콜백은 가장 먼저 해제된다. 따라서 모듈은 종료 시 구독을 해제하기 전에 창 콜백이 아직 유효한지 확인해야 한다.

## 3. 모듈 시스템

모듈 시스템(`GModuleGlobalSystem`)은 기능 단위 DLL을 로드하고 수명을 관리한다. 에디터 실행 시 JGEditor 모듈이 Graphics, GUI, Asset 등을 차례로 연결하며, 모듈 하나를 연결할 때마다 DLL 로드, Core 인스턴스 연결, 모듈 객체 생성, `StartupModule` 호출, 콘솔 명령 등록을 수행한다.

### 3-1. 모듈 연결 과정

![모듈 연결 과정 — ConnectModule 호출 시 이미 연결된 모듈이면 즉시 성공, 아니면 DLL 로드 → Link_Module → 모듈 객체 생성 → StartupModule → 콘솔 명령 등록 → 연결 순서 목록 끝에 추가](그림/Core_06_모듈연결.svg)

- 모듈 DLL은 `JG_MODULE_IMPL(모듈 클래스, API)` 매크로로 진입 함수 두 개(`Link_Module`, `_Create_Module_Interface_`)를 내보낸다.
- 연결된 모듈은 이름 또는 타입으로 조회한다(`FindModule`).
- 이미 연결된 모듈을 다시 연결하면 아무 작업 없이 성공을 반환한다. 참조 카운트는 관리하지 않는다.

### 3-2. 연결 순서와 종료 순서

![모듈 연결 순서와 종료 순서 — 시작 시 Graphics · GUI · Asset · GameFrameWorks · 게임 모듈 · JGEditor 순으로 목록에 추가되고, 종료 시 역순으로 JGEditor부터 ShutdownModule 호출](그림/Core_07_연결순서.svg)

- 모듈은 `StartupModule`이 끝난 뒤 연결 목록에 추가된다. 따라서 JGEditor가 `StartupModule` 안에서 연결한 모듈이 JGEditor보다 앞에 놓이고, 종료 시에는 목록의 역순으로 JGEditor가 먼저 `ShutdownModule`을 호출받는다. 즉 의존하는 모듈이 먼저 종료된다.
- 참조 카운트가 없으므로 모듈은 `ShutdownModule`에서 다른 모듈의 연결을 해제하지 않는다. 종료 순서는 엔진이 관리한다.
- 개별 모듈 해제(`DisconnectModule`)는 콘솔 명령 해제, `ShutdownModule`, GC 순으로 진행한다. DLL은 엔진 종료 시 일괄 언로드한다.

## 4. 메모리 시스템

메모리 시스템(`GMemoryGlobalSystem`)은 엔진의 CPU 메모리 할당과 객체 수명을 관리한다. 객체는 `Allocate<T>()`로 생성하고 스마트 포인터(`PSharedPtr`)로 참조한다. 참조가 모두 해제된 객체는 즉시 파괴되지 않고 다음 프레임 시작 시 GC가 파괴한다.

### 4-1. 메모리 풀 할당 구조

![메모리 풀 할당 구조 — 할당 요청은 크기와 정렬에 따라 스레드 청크(크기 클래스 → 페이지 → 블록) 또는 대형 블록으로 분기하며, 다른 스레드의 반납과 메인 스레드 Tick이 이를 보조함](그림/Core_08_풀칸받기.svg)

- 1MB 이하이고 정렬이 16바이트 이하인 요청은 호출한 스레드의 청크(`HMemoryChunk`)에서 처리한다. 청크는 크기 클래스 18개(8B~1MB)로 나뉘며, 빈 블록이 없으면 64KB 페이지를 추가하므로 고갈되지 않는다(32KB 이상 클래스는 블록 하나짜리 페이지를 추가한다).
- 1MB를 넘거나 정렬이 16바이트를 넘는 요청은 대형 블록으로 할당하며, 해제된 대형 블록은 대형 캐시에 잠시 보관해 재사용한다.
- 모든 블록은 특정 청크에 속한다(블록 앞 16B 헤더에 청크 번호를 기록). 풀을 거치지 않는 할당 경로(malloc 폴백)는 두지 않는다(사용자 결정, 2026-09-28).
- 다른 스레드가 해제한 블록은 lock-free 반납 스택을 통해 원래 청크로 돌아가고, 10초 이상 사용하지 않은 빈 페이지는 메인 스레드의 `Tick`이 시스템에 반환한다.
- 엔진 컨테이너(`HList`, `HHashMap`, `HMap`, `HSet` 등)도 이 풀을 사용하는 STL 별칭이다(`HAllocator`).
- 2026-09-28 재설계로 상주 메모리가 428MB에서 230MB로 줄었다. 스레드별, 크기 클래스별 사용량은 메모리 통계 창(DevStatistics)에서 확인한다.

### 4-2. 객체 수명 주기

![객체 수명 주기 — 게임 코드, 메모리 시스템, 메모리 풀, 객체 사이의 할당, 강참조 · 약참조, 다음 프레임 GC에 의한 파괴, 블록 반납 순서](그림/Core_09_오브젝트생애.svg)

- 강참조(`PSharedPtr`)는 객체를 유지하고, 약참조(`PWeakPtr`)는 객체 수명에 관여하지 않는다. 약참조로 객체를 사용하려면 `Pin()`으로 강참조를 얻는다.
- 참조 카운트는 객체 외부의 제어 블록(`HMemoryControlBlock`, 강참조 수와 약참조 수)에 저장한다. 객체가 파괴되어도 약참조가 남아 있으면 제어 블록이 유지되므로, 이후의 `Pin()`은 안전하게 실패한다(2026-09-29 4-1).
- 엔진 종료 시에는 강참조가 남은 객체도 할당 순서대로 강제 파괴한다(`forceFlush`).

### 4-3. IMemoryObject 단일 루트 규칙

![IMemoryObject 단일 루트 규칙 — IMemoryObject 아래에 문자열 · 스마트 포인터, JGObject(하위에 액터 · 위젯 · 게임 클래스), 창 · 스케줄 작업 · 콜백이 위치하며, 두 부모가 모두 IMemoryObject를 상속한 클래스는 금지](그림/Core_10_뿌리규칙.svg)

- 스마트 포인터로 관리하는 타입은 `IMemoryObject`를 정확히 하나의 루트로 상속해야 한다.
- 다중 상속으로 `IMemoryObject` 상속 경로가 둘이 되면 `Allocate<T>`가 `IMemoryObject*`로 변환할 때 모호성이 생긴다.
- 관찰자 같은 인터페이스를 추가할 때는 그 인터페이스가 `IMemoryObject`를 상속하지 않도록 분리한다(예: GameFrameWorks `GameMasterActor`).

## 5. 리플렉션과 코드 생성

리플렉션은 클래스의 타입, 속성, 함수 정보를 실행 중에 조회하는 기능이다. 헤더에 `JGCLASS()` 등의 마커를 붙이면 빌드 전에 JGHeaderTool이 헤더를 분석해 등록 코드를 생성한다. 엔진 초기화 시 이 코드가 오브젝트 시스템(`GObjectGlobalSystem`)에 클래스를 등록하며, 이를 바탕으로 타입 이름으로 객체를 생성하거나 JSON으로 직렬화할 수 있다. 에셋 파일(`.jgasset`)도 이 직렬화를 기반으로 한다.

### 5-1. 코드 생성과 등록 과정

![코드 생성과 등록 과정 — 헤더의 마커 매크로, 빌드 전 JGHeaderTool 실행, 코드 생성, 모듈 DLL 컴파일, 초기화 시 모듈 목록의 DLL 로드, 오브젝트 시스템 등록, 사용의 7단계](그림/Core_11_리플렉션흐름.svg)

- 마커 매크로(`JGCLASS`, `JGPROPERTY`, `JGFUNCTION`, `JGENUM`, `JGENUMMETA`)는 빈 매크로다. 컴파일러는 무시하고 JGHeaderTool만 텍스트로 분석한다. 헤더는 `JGCLASS()` 바로 앞에 `#include "파일.generation.h"`를 둔다.
- 생성 코드는 클래스마다 세 함수를 포함한다. 클래스 정보(속성, 함수, 부모 목록)를 생성하는 함수, 속성을 실제 객체에 바인딩하는 함수, 객체를 생성하는 함수(`Allocate<C>()`)다.
- 모듈 목록 파일은 `PreBuild.bat`에서 JGHeaderTool 다음에 실행되는 JGBuildTool이 생성한다.
- 리플렉션용 DLL 로드는 모듈 연결(3번)보다 먼저 일어난다. 초기화 시 목록의 DLL을 모두 로드해 클래스를 먼저 등록한다.
- 생성 파일은 내용이 바뀐 경우에만 다시 기록한다. 헤더를 수정하면 `PreBuild.bat`(게임 프로젝트는 `GenerateGameProjectFiles.bat`)을 다시 실행한다.
- 등록된 정보는 `StaticClass<T>()`(클래스 정보 조회), `AllocateByClass`(타입으로 객체 생성), `SaveObject`와 `LoadObject`(JSON 직렬화), `Cast`(상속 관계의 타입 변환)로 사용한다.

### 5-2. 직렬화 구조

![직렬화 구조 — SaveObject는 객체를 JSON 필드 2개(타입 이름 · 내용)로 저장하고 내용은 상속 계층마다 항목 하나를 두며, LoadObject는 타입 이름으로 등록된 타입을 찾아 생성 함수로 새 객체를 생성한 뒤 계층마다 ReadJson을 호출한다](그림/Core_12_저장불러오기.svg)

- `JGPROPERTY`가 붙은 속성은 생성 코드가 JSON으로 자동 직렬화한다. 객체를 가리키는 속성은 `[타입, 값]` 형식으로 저장한다.
- JSON은 `JGObjectType`(타입 이름)과 `JGObject`(내용) 두 항목으로 구성되며, 내용은 상속 계층마다 하나의 하위 항목을 가진다. `LoadObject`는 타입 이름으로 등록된 타입을 찾아 객체를 생성한 뒤, 상속 계층별로 `ReadJson`을 호출해 속성을 채운다.
- 제약: JGHeaderTool이 처리하는 마커는 `JGCLASS`, `JGPROPERTY`, `JGFUNCTION`, `JGENUM`, `JGENUMMETA`다. `JGSTRUCT`, `JGINTERFACE`는 매크로만 정의되어 있고 처리하지 않는다.
- 제약: 헤더 하나에 리플렉션 클래스는 하나만 둘 수 있다. 속성 선언은 한 줄(`타입 이름;`)로 작성해야 분석된다.
- 제약: `Cast`는 두 타입이 상속 관계인지만 검사하고, 실제 객체의 타입은 실행 중에 검사하지 않는다(보류 항목 7-3).

## 6. 대리자(Delegate)

대리자는 호출할 함수를 객체로 저장해 두었다가 나중에 실행하는 기능이며, 이벤트 구독에 사용된다. 예를 들어 창 크기가 바뀌면 창은 크기 변경 이벤트를 한 번 브로드캐스트하고, 이 이벤트를 구독한 Graphics와 GameHost의 함수가 모두 호출된다.

### 6-1. 클래스 구조

![대리자 클래스 구조 — HMulticastDelegate는 구독마다 HDelegate를 하나씩 포함하고 Add 계열 함수는 HDelegateHandle을 반환하며, HDelegate는 IDelegateInstance(정적 · 원시 포인터 · 람다 · 약참조 대리자)를 포함한다](그림/Core_13_대리자짜임.svg)

| 클래스 | 역할 |
|---|---|
| `HMulticastDelegate` | 여러 구독을 보관하고 한 번에 브로드캐스트하는 이벤트 |
| `HDelegate` | 함수 하나를 보관하는 단일 대리자(구독 하나 또는 단일 콜백) |
| `HDelegateHandle` | 구독 식별자. 특정 구독을 해제할 때 사용한다(`Remove`) |
| `PStaticDelegate` | 전역 함수, 정적 함수 바인딩 |
| `PRawDelegate` | 객체 포인터와 멤버 함수 바인딩. 객체를 파괴하기 전에 구독을 해제해야 한다(`RemoveObject` 등) |
| `PLambdaDelegate` | 람다 바인딩. 람다는 항상 복사본으로 저장한다(2026-10-11 ER-023) |
| `PSPDelegate` | 약참조 객체와 멤버 함수 바인딩. 객체가 이미 파괴되었으면 호출해도 실행되지 않는다 |

- 32B 이하의 콜백은 대리자 내부 버퍼에 저장하고, 그보다 큰 콜백만 힙에 할당한다(`HInlineAllocator`).
- 선언 매크로는 `JG_DECLARE_DELEGATE`, `JG_DECLARE_MULTICAST_DELEGATE`, `JG_DECLARE_EVENT`다. 창 이벤트 3종(9번)도 이 매크로로 선언되어 있다.

### 6-2. 브로드캐스트 중 구독 해제

![브로드캐스트 중 구독 해제 — BroadCast 시작 시 잠금 카운트가 1 증가하고, 구독 1이 구독 3을 Remove하면 핸들만 무효로 표시되어 구독 3은 건너뛰며, BroadCast 종료(잠금 카운트 0) 후 가장 바깥 브로드캐스트가 끝날 때 무효 항목을 일괄 제거한다](그림/Core_14_방송중구독빼기.svg)

- 브로드캐스트 도중에 목록에서 항목을 즉시 삭제하면 순회 순서가 어긋나거나 실행 중인 콜백의 저장소가 해제될 수 있다.
- 따라서 브로드캐스트 중의 해제는 핸들만 무효화하고, 가장 바깥 브로드캐스트가 끝날 때 무효 항목을 일괄 삭제한다(2026-10-11 수정).
- 이 때문에 콜백 안에서 `GetSize()`를 호출하면 해제된 구독도 개수에 포함된다.

## 7. 콘솔 명령

콘솔 명령 시스템(`GConsoleCommandGlobalSystem`)은 이름으로 등록된 명령을 찾아 실행한다. 에디터의 DevConsole 창과 명령줄 도구 JGConsole이 같은 레지스트리를 사용한다. 명령은 각 모듈의 `.cpp` 파일에 정적 객체로 선언하며, 모듈이 연결될 때 자동으로 등록된다.

### 7-1. 명령 등록 과정

![명령 등록 과정 — 모듈 .cpp의 static HAutoConsoleCommand는 DLL 로드 시 자기 바이너리의 목록에 연결되고, ConnectModule 후 RegisterAll로 레지스트리에 등록되며, 모듈 종료 시 UnregisterAll로 해당 DLL의 명령만 제거되고, 실행 파일의 명령과 기본 help는 레지스트리 생성 시 등록된다](그림/Core_15_명령등록길.svg)

- 정적 초기화 시점에는 DLL의 Core 사본이 아직 관리자에 연결되지 않은 상태다(1-2). 따라서 선언 객체(`HAutoConsoleCommand`)는 레지스트리, 메모리 풀, 로그를 사용하지 않고 해당 바이너리의 목록에 자신을 추가하기만 한다. 실제 등록은 모듈 연결 후에 이루어진다.
- 모듈 연결 시 `StartupModule` 직후 `RegisterAll`로 등록하고, 모듈 종료 시 `ShutdownModule` 직전 `UnregisterAll`로 해당 DLL의 명령만 해제한다. 실행 파일의 명령과 기본 `help` 명령은 레지스트리 생성 시 등록한다.
- 이름이 중복되어 등록에 실패한 명령은 해제 대상에서도 제외한다. 다른 바이너리의 명령을 해제하지 않기 위해서다.
- 명령 이름은 소문자 `영역.동작` 형식이다(예: `audio.selftest`). Core 내부에는 명령을 선언하지 않는다. 정적 라이브러리이므로 링크 시 누락되거나 중복 등록될 수 있기 때문이다. Core 자체 검사 명령은 JGConsole에 있다.

### 7-2. 명령 실행 과정

![명령 실행 과정 — DevConsole 창은 Submit으로 명령을 대기열에 넣어 다음 프레임 5단계에서 실행하고 결과 줄을 로그 · 최근 로그로 표시하며, JGConsole은 Execute로 즉시 호출하여 종료 코드 0 · 1을 받는다](그림/Core_16_명령실행길.svg)

- 실행 방식은 두 가지다. `Execute`는 메인 스레드에서 즉시 실행하고, `Submit`은 대기열에 넣어 다음 프레임의 콘솔 명령 시스템 갱신 때 실행한다.
- DevConsole은 GUI 갱신 도중에 명령을 받으므로 `Submit`을 사용한다. JGConsole은 프레임 루프가 없으므로 `Execute`로 즉시 실행하고, 결과를 종료 코드(성공 0, 실패 1)로 반환한다.
- 인자 형식은 `이름 위치인자 -flag -key=value "공백이 있는 값"`이다. 이름과 키는 소문자로 정규화하고 값은 그대로 둔다. `-key value`처럼 공백으로 구분한 값은 지원하지 않는다.
- `help`는 전체 명령을 이름순으로 출력하고, `help 이름`은 해당 명령의 사용법을 출력한다.

## 8. 로그

로그 시스템(`GLogGlobalSystem`)은 spdlog를 감싼 전역 시스템이다. 모든 모듈은 `JG_LOG(분류, 레벨, 형식 문자열, 인자...)` 매크로로 로그를 남기며, 한 번의 호출이 로그 파일, 콘솔 창, 최근 로그 버퍼에 동시에 기록된다.

![로그 흐름 — 모든 모듈의 JG_LOG는 로그 시스템(spdlog 로거 1개)을 거쳐 파일 · 콘솔 창 · 최근 로그로 출력되고, 최근 로그는 DevConsole 창과 JGConsole 모듈 명령이 읽는다](그림/Core_17_로그흐름.svg)

- 로그 레벨은 Debug, Trace, Info, Warning, Error, Critical이다. Warning 이상은 즉시 파일에 기록(flush)하고, Info 이하는 버퍼에 모았다가 기록한다. 따라서 비정상 종료 시 마지막 Info 로그 일부가 누락될 수 있다.
- 형식 문자열은 printf 방식(`%s`, `%d`)을 사용한다. `{0}` 같은 자리 표시자는 치환되지 않고 그대로 출력된다.
- 로그 파일은 툴과 에디터는 작업 폴더의 `jg_log.txt`, 패키지는 `Saved/Logs/<이름>.log`이며, 시작 시 내용을 비운다. 패키지에서 같은 이름의 파일을 다른 프로세스가 사용 중이면 `<이름>_2.log` 등으로 대체하며, `-logfile=`로 경로를 지정할 수 있다.
- 최근 로그 버퍼는 Info 이상 최근 1024줄을 일련번호와 함께 보관하며, DevConsole 창과 JGConsole 모듈 명령이 읽는다. 이 버퍼는 메모리 풀과 `JG_LOG`를 사용하지 않는다. 로그와 메모리 풀이 서로를 호출하는 재귀를 막기 위해서다.
- 로그 시스템은 가장 먼저 초기화되고 가장 마지막에 해제된다(2번).

## 9. 창, 입력, 플랫폼

Core는 창 생성, 윈도우 메시지 처리, 입력 변환, 플랫폼 기능을 제공한다. Windows가 보낸 메시지는 Core의 창 프로시저(`WndProc`)가 받아 세 가지 창 이벤트(원본 메시지, 크기 변경, 엔진 입력)로 브로드캐스트하고, 필요한 모듈이 각 이벤트를 구독한다.

### 9-1. 창 생성

![창 생성 — 실행 모듈(JGEditor 또는 GameHost)의 StartupModule이 HPlatform::CreateJWindow로 Windows 창(PWindowsJWindow)을 생성하고, 관리자 전역 값 MainWindow와 프레임 단계 UpdateWindow의 메시지 펌프에 등록한다](그림/Core_18_창만들기.svg)

- Core는 창 생성 기능만 제공하며, 실제 창은 실행 모듈이 `StartupModule`에서 생성한다(`HPlatform::CreateJWindow`). 생성된 창은 관리자의 `MainWindow`에 등록되고, 메시지 펌프는 프레임 단계 `UpdateWindow`에 등록된다.
- 에디터는 DPI 배율을 적용한 크기(100% 기준 1936x1119)로, GameHost는 게임 창 설정 크기(기본 클라이언트 영역 1920x1080 또는 테두리 없는 전체 화면)로 창을 생성한다.
- 두 실행 모듈 모두 창을 먼저 생성한 뒤 다른 모듈을 연결한다. Graphics가 초기화될 때 이 창의 크기로 스왑체인을 생성하기 때문이다.
- GameHost가 창 생성에 실패하면 종료 코드 3으로 종료한다. 창이 없는 실행(JGConsole)에서는 `MainWindow`가 null이다.

### 9-2. 윈도우 메시지 처리

![윈도우 메시지 처리 — Windows 메시지는 Core 창 프로시저 WndProc을 거쳐 WndProc 이벤트(GUI · Audio), OnResize 이벤트(Graphics · GameHost), 입력 변환기 → OnInput 이벤트(GameHost, 구독자가 있을 때만), WM_QUIT(프레임 루프 종료)로 분기된다](그림/Core_19_창메시지길.svg)

- 창 이벤트 3종(`HWindowCallBacks`의 `WndProc`, `OnResize`, `OnInput`)은 모두 6번의 멀티캐스트 대리자다. 관리자가 하나의 인스턴스를 보유하며, 필요한 모듈이 구독한다.
- `WndProc` 이벤트는 모든 메시지를 전달한다. GUI는 이를 ImGui에 전달하고, Audio는 `WM_ACTIVATEAPP`를 받아 창이 비활성화되면 설정에 따라 음량을 줄이거나 음소거한다.
- `OnResize` 이벤트는 `WM_SIZE`에서 발생한다. Graphics는 스왑체인 크기를, GameHost는 뷰포트 크기를 변경한다.
- 엔진 입력 변환은 `OnInput` 구독자가 있을 때만 수행한다. GameHost는 구독하고 에디터는 구독하지 않으므로, 에디터에서는 ImGui가 원본 메시지를 직접 처리한다. Audio가 `OnInput` 대신 `WndProc`을 구독하는 것도 에디터에서 입력 변환이 활성화되지 않게 하기 위해서다.
- 엔진 입력 이벤트(`HInputEvent`)의 종류는 포인터 이동, 누름, 뗌, 휠, 이탈, 키 누름, 키 뗌, 문자 입력(UTF-32), 포커스 획득, 포커스 상실이다. 버튼은 왼쪽, 오른쪽, 가운데, X1, X2이고, 보조 키는 Shift, Ctrl, Alt다.
- 입력 변환기(`HWindowsInputTranslator`)는 운영체제 호출이 없는 로직으로 분리되어 있어 창 없이 검사할 수 있다(`input.selftest`).
- `WM_QUIT`를 받으면 프레임 루프가 종료된다.

### 9-3. 플랫폼 유틸리티(`HPlatform`)

| 분류 | 기능 |
|---|---|
| DLL | 로드, 언로드, 함수 조회(`LoadDll`, `UnLoadDll`, `LoadFuncInDll`). 모듈 시스템(3번)과 리플렉션(5번)이 사용한다 |
| 창 | 창 생성(`CreateJWindow`) |
| DPI | DPI 인식 활성화(Per-Monitor V2), 창 배율 조회(`GetDpiScale`). 현재 DPI 인식은 JGLauncher만 활성화하며, 패키지 실행 파일은 활성화하지 않는다 |
| 텍스트 입력 | 클립보드 읽기와 쓰기(UTF-8), IME 조합 창 위치 지정(`SetImeCompositionRect`, GameHost가 사용) |
| 기타 | 실행 파일 경로 조회, GUID 생성, 엔진 키 코드와 Windows 가상 키 코드 변환 |

## 10. 파일과 경로

파일 도우미(`HFileHelper`)는 파일 읽기와 쓰기, 엔진과 프로젝트의 디렉터리 경로를 제공한다. 엔진 루트와 프로젝트 루트는 초기화 시 한 번 결정되어 관리자에 저장되며, 모든 DLL이 같은 값을 참조한다. 따라서 같은 토큰 경로(`/JGGame/Sounds/Draw.wav`)도 에디터 빌드에서는 프로젝트의 `Content` 폴더를, 패키지에서는 패키지의 `Content/JGGame` 폴더를 가리킨다.

### 10-1. 루트 디렉터리 결정

![루트 디렉터리 결정 — 에디터 빌드는 -project= 인자(툴)와 ../../의 .jgproject 유무로 프로젝트 모드와 엔진 단독 모드를 구분하고, 패키지는 Bin/JGPackage.json을 읽어 엔진 · 프로젝트 디렉터리를 모두 패키지 디렉터리로 지정하며, 읽기에 실패하면 종료 코드 2로 시작을 중단한다](그림/Core_20_폴더정하기.svg)

- `../../`는 작업 폴더가 아니라 실행 파일 위치를 기준으로 한다(`Bin/DevelopEngine/`에서 두 단계 상위 폴더가 엔진 루트 또는 프로젝트 루트).
- 툴(JGBuildTool, JGHeaderTool)이 `-project=`로 받은 프로젝트가 다른 엔진에 연결되어 있으면 Critical 로그를 남기고 프로젝트 모드로 전환하지 않는다.
- 프로젝트 모드의 엔진 루트는 `.jgproject`의 `EngineRoot`를 먼저 사용하고, 없으면 환경 변수 `JGENGINE_ROOT`를 사용한다.
- 패키지는 실행 모듈과 런타임 모듈 목록도 `JGPackage.json`에서 읽는다.

### 10-2. 디렉터리와 토큰 경로

![디렉터리와 토큰 경로 — /JGEngine/…은 EngineContentDirectory를 통해 에디터 빌드의 엔진 디렉터리/Content와 패키지/Content/JGEngine에, /JGGame/…은 GameContentDirectory를 통해 프로젝트 디렉터리/Content와 패키지/Content/JGGame에 대응하고, 저장 디렉터리(SavedDirectory)는 프로젝트 디렉터리/Saved와 패키지/Saved에 대응한다](그림/Core_21_폴더와토큰.svg)

- Core는 디렉터리 경로만 제공한다(`EngineContentDirectory`, `GameContentDirectory`, `SavedDirectory`, `EngineShaderDirectory` 등). 토큰(`/JGEngine/`, `/JGGame/`)을 실제 경로로 변환하는 일은 사용하는 모듈이 담당한다. 에셋은 Asset 모듈(`HAssetPath`, 확장자가 없으면 `.jgasset` 추가), 사운드는 Audio 모듈(11번)이 변환한다.
- 엔진 단독 실행(프로젝트 없음)에서는 게임 Content 경로가 비어 있으므로 `/JGGame/` 경로는 오류가 된다.
- 패키지에서 `Content`, `Saved`, `Bin` 밖의 파일을 읽으면 디렉터리마다 한 번 경고를 남긴다(`Package reads outside Content/Saved/Bin`). 쿠킹의 스모크 실행이 이 경고를 검사한다. 패키지에서 개발 전용 경로(Source, Temp, Config 등)를 조회하면 한 번 오류를 남긴다.
- 파일 함수는 텍스트 전체 읽기(`ReadAllText`), 바이너리 전체 읽기(`ReadAllBytes`), 원자적 쓰기(`WriteAllTextAtomic`)다. 원자적 쓰기는 `.tmp` 파일에 쓴 뒤 이름을 바꾸며, 데이터 테이블 저장에 사용한다. JSON은 rapidjson 래퍼(`PJson`)로 처리한다.
- 경로는 ASCII만 지원한다(D-26).

## 11. Audio 모듈과 Core

Audio 모듈은 Core에만 의존하는 런타임 모듈로, 효과음과 배경음 재생 기능을 제공한다. Core의 모듈 시스템, 전역 시스템 등록, 창 이벤트, 파일 기능을 사용하며, 재생은 외부 라이브러리 miniaudio가 처리한다.

![Audio 모듈과 Core — 사운드를 사용하는 게임 모듈이 1 모듈 연결, 2 Play 호출 순으로 Audio를 사용하고, GAudioGlobalSystem은 Core 관리자에 등록되어 창 이벤트 WndProc의 WM_ACTIVATEAPP와 로그 · 콘솔 명령을 사용하며, HAudio는 HFileHelper로 파일을 읽어 miniaudio 0.11.25에 전달한다](그림/Core_22_Audio와Core.svg)

- 게임 모듈이 Audio 모듈을 연결하면(`ConnectModule("Audio")`) Audio 모듈은 `StartupModule`에서 자체 전역 시스템(`GAudioGlobalSystem`)을 관리자에 등록한다. 이 시스템은 매 프레임 `Update`에서 재생이 끝난 사운드를 정리하고, `WndProc` 이벤트로 `WM_ACTIVATEAPP`를 받아 창이 비활성화되면 설정에 따라 음량을 줄이거나 음소거한다.
- 게임이 `HAudio::Play`를 호출하면 Audio 모듈은 토큰 경로를 Content 경로로 변환하고 Core의 파일 함수로 파일 전체를 읽은 뒤, 내부 엔진(`HAudioEngine`)을 통해 miniaudio로 재생한다.
- 사운드를 사용하는 게임 모듈만 Audio를 연결한다(`module.json` 의존성 추가와 `ConnectModule("Audio")`). 에디터와 GameHost는 기본으로 연결하지 않는다.
- 사용하는 Core 기능은 모듈 연결(3번), 전역 시스템 등록(2번), 창 이벤트(9번), 파일과 경로(10번), 로그와 콘솔 명령(7번, 8번)이다. 자체 검사 명령 `audio.selftest`도 Audio 모듈에 있다.
- 창이 없는 실행(JGConsole)이나 `-nosound` 인자를 사용하면 null 출력 장치(무음)를 사용한다. 자세한 내용은 [[Audio]]를 참고한다.

## 기타 구성 요소

문자열(`PString`, 인턴 문자열 `PName`, 문자열 테이블), 수학(`HVector3`, `HMatrix` 등), 타이머, 비동기 작업 스레드(`ScheduleAsync`), GUID, 시간은 이 문서의 그림에 포함하지 않았다. [[Core]]의 폴더 표와 핵심 클래스 항목을 참고한다.
