## 1. 우리가 만드는 것 (최우선 원칙)

**우리는 게임 엔진(JGEngine)을 만든다. 이 엔진을 기반으로 보드 & 카드 게임을 만들 것이다.**
**지금의 초점은 기반(엔진)이다. 게임 구현이 아니다.**

| 하지 않는 것 | 대신 하는 것 |
|---|---|
| 특정 게임(아컴호러 LCG, 반지의 제왕 LCG 등)의 규칙·카드·시나리오를 엔진 코드에 넣기 | 어떤 보드/카드 게임에도 쓰이는 범용 기반(턴/페이즈 진행, 액터/컴포넌트, 데이터 로딩, 네트워크 세션 등)을 만들기 |
| 엔진 설계·코드를 특정 게임 기준으로 평가하기 ("아컴호러를 하려면 X가 필요하다") | 엔진 시스템 자체의 완성도·검증·안정성으로 평가하기 |
| 보고서·현황에서 게임 구현 진척을 엔진 진척처럼 다루기 | 엔진 시스템(Core, Graphics, GameFrameWorks, DevOps, Server, GUI, JGEditor) 단위로 진척을 보고하기 |
| 게임 고유 코드를 엔진 모듈 안에 두기 | 게임 코드는 엔진 밖 GameProject(Source/<Name>, Source/<Name>Editor)에 두기 |

- 레퍼런스 게임 자료(Document/아컴호러 등)는 "이런 종류의 게임이 돌아가야 한다"는 **요구사항 확인용 참고 자료**다. 언급은 요구사항 예시 수준에서 그친다.
- 판단 기준 한 줄: **"이 작업 결과가 다른 보드/카드 게임에도 그대로 쓰이는가?"** 아니라면 엔진 작업이 아니다. 게임 프로젝트 영역으로 분류해 해당 분야 TODO의 "게임 프로젝트 영역(엔진 범위 외)" 표에 둔다.

## 2. 문서 구조와 인수인계

| 위치 | 내용 |
|---|---|
| Document/Memory/README.md | 전체 요약과 인덱스. 새 에이전트는 여기서 시작한다 |
| Document/Memory/진행현황.md | 분야별 진행 상태, 다음 할 일, 결정 대기 항목을 한곳에서 관리 |
| Document/Memory/<분야>/현황.md | 그 분야의 역할, 구현 상태, 마지막 세션 상태, 함정, 검증 방법 |
| Document/Memory/<분야>/TODO.md | 다음 할 일 Top N, 미완료 항목 표, 완료 이력 |
| Document/Memory/<분야>/Files/ | 설계·분석 문서, 검증 증적(캡처·로그), 도구 스크립트 |
| Document/ (루트) | 사용자 보고서(HTML 등) |

분야: Core(Core 모듈 — 메모리 시스템 · 콘솔 명령 시스템 · Core 공용. 2026-10-11 `Memory/` 에서 이름 변경), GameFrameWorks(게임 UI · 데이터 테이블 포함), Graphics, DevOps(빌드 시스템 · 툴 · 게임 프로젝트 환경 · 빌드 성능, 2026-10-02 GameModule 에서 이름 변경), Server, Etc(GUI · JGEditor(DevConsole 창 포함) · 참고자료). 세션 ↔ 분야 표는 README 5절, 옛 위치 → 새 위치는 README 6절.

작업 규칙:
1. 시작: README.md → 해당 분야 현황.md → TODO.md 순으로 읽는다.
2. 진행: TODO의 항목 식별자(예: Phase 5-26, R5)를 유지하고 문서 간 참조를 깨지 않는다.
3. 종료·중단 전: 현황.md의 "세션 마지막 상태", TODO.md, 진행현황.md를 갱신한다. 대화에만 있는 결정은 사라진다.
4. 증적: 빌드 로그·캡처·결과 txt는 Files/에 두고 문서에서 경로로 참조한다.
5. **커밋 · 푸시는 엔진 총괄이 묶어서 한다**(전체 필수 지침 8, 사용자 결정 2026-10-17 보고함 H-001 — 그 전에는 "커밋은 사용자가 한다"). 분야 세션은 커밋 · 푸시하지 않는다. 일이 끝나면 커밋에 함께 들어가야 할 파일(재빌드된 exe, 템플릿 등)을 TODO 의 커밋 체크리스트에 적고 엔진 총괄에 알린다.
   - 엔진 총괄은 그 일의 빌드 · 자체 테스트가 통과한 것을 보고, **그 일에서 고친 파일만 골라**(`git add -A` 금지 — 다른 세션이 고치는 중인 파일이 섞이지 않게) 커밋하고 푸시한 뒤 보고함에 "보고"로 남긴다(무엇을 · 커밋 번호).
   - 커밋 전 검사기(`.git/hooks/pre-commit`)가 사용자 메모 · 아컴호러 자료(`Document/아컴호러`) · 로그 · 50MB 넘는 파일을 막는다. 걸리거나 푸시가 막히면 억지로 하지 않고(`--force` 금지) 보고함에 보고한다.
   - 엔진 저장소(`useinternet/JGEngine`)는 **공개**다 — 푸시하면 누구나 본다. 아컴호러 자료는 새로 넣거나 고쳐 넣지 않는다(이미 올라간 것은 사용자가 다시 말할 때까지 그대로, 보고함 H-002). 바이너리(`Bin/`)는 하루 한 번만 넣는다.
6. **세션 교체**(전체 필수 지침 10): 대화가 많이 쌓이면 이어받기 메모를 남기고 같은 세션을 비운 뒤 다시 시작한다. **너무 자주 교체하지 않는다 — 이것이 먼저다.** 대화 창이 차는 것만으로는 교체하지 않고 자동 요약(대화 압축)에 맡긴다. **대화 압축 3번 뒤**에는 지금 하는 일 하나가 끝날 때, **4번 뒤**에는 지금 단계가 끝나는 대로 꼭 교체한다. 압축이 2번 이하면 대화 창 % 가 높아도 교체하지 않는다. 압축 횟수는 통합 대시보드 팀 화면 세션 줄의 “대화 압축 N번”(교체하면 0부터 다시 셈)에서 보고, 엔진 총괄이 일이 끝날 때마다 챙긴다. 교체 = **같은 세션의 대화를 비우고(clear) 시작 메시지(`C:/obsidian/ProjectJG/01. 운영/세션 구성.md`)를 다시 보내는 것** — 세션 id · 이름이 그대로라 보관 · id 표 고치기가 없다(옛 대화는 앱의 “이전 대화 다시 열기”).
   - 누가: 분야 세션은 **엔진 총괄이 알아서** 교체한다. **엔진 총괄은 스스로 교체하지 않는다** — 압축 3번이 되면 프로젝트 총괄이 교체 요청을 보내고, 받으면 ① 마무리(이어받기 메모 · 감시 끄기) 뒤 프로젝트 총괄에 “교체해도 됨 — 이제 비움”을 보내고 자기를 비운다(`clear_session "self"`, 그 차례가 끝나면 비워짐) → 1분쯤 뒤 프로젝트 총괄이 시작 메시지를 보낸다. 사용자가 대시보드 “교체”(세션 줄 · “총괄 교체”)를 누르면 압축 횟수와 상관없이 같은 순서로 한다.
   - 안 되는 때: 빌드 · 자체 시험 · 패키징이 도는 중, 메인 트리 잠금(`Build/BatchFiles/MainTree.cmd hold`)을 쥔 중, 사용자와 한창 주고받는 중.
   - 이어받기 메모 자리: 분야 세션 = 그 분야 `현황.md` 의 "세션 마지막 상태"(+ TODO.md, 진행현황.md §7 한 줄). 엔진 총괄 = `Document/Memory/총괄_이어받기.md`.
   - 메모에 꼭: 지금 일(대시보드 명령 `c-…` · 작업 이름(번호) · 보고함 id)과 단계 · 다음 할 것 · 기다리는 상대, 잠금 · 빌드 · 시험 상태(끝났나 · 놓았나), 고친 파일 · **미커밋 파일** · 검증 결과 파일(`Files/`) 경로, 아직 지침서 · 메모리에 안 넣은 사용자 피드백. 엔진 총괄은 더해서 감시 명령(`node Document/Dashboard/tools/watch_inbox.js`, Monitor) · 답을 기다리는 보고함 항목 · 처리 중 명령 · 분야 세션 id 표.
   - 순서(분야 세션): ① 그 세션이 하던 단계를 끝내고 메모를 쓰고 메인 트리 잠금을 풀고 감시(Monitor)를 끈 뒤 엔진 총괄에 “교체해도 됨” → ② 엔진 총괄이 그 세션을 비우고(`clear_session` — 자기가 띄운 세션만 된다) 시작 메시지(“엔진 분야 세션”) + “이어받기 메모 먼저 읽기”를 보낸다 → ③ 다시 시작한 세션이 메모 · 지침을 읽고 감시를 다시 켜고 상태 줄을 고침 → ④ **교체할 때마다 보고함에 “보고”** 한 줄(누가 · 대화 압축 몇 번 · 메모 위치).

**지금 하는 일 적기**(2026-10-12~): 일을 시작할 때 · 단계가 바뀔 때 · 끝날 때 한 줄을 고쳐 쓴다 — `node C:/Develop/JGEngine/Document/Dashboard/tools/set_status.js <세션 이름> "<지금 하는 일>"`. 세션 이름 = 세션 메시지 이름(`총괄` · `Core` · `GameFrameWorks` · `GUI` · `JGEditor` · `Graphics` · `DevOps` · `Server`). 작업은 이름(번호)로 쓴다(4절). 예: `set_status.js Server "같이 하기 대기방 기능 묶음(D-38) — 방 정보 보내기 검사 중"`. 맡은 일이 없으면 `"쉬는 중 — 맡은 일 없음"`. 사용자가 대시보드 개요 맨 위 "진행 상황"에서 본다(3시간 넘게 고치지 않은 줄은 흐리게 "오래됨").

병렬 세션 주의:
- 공유 파일(예: GameMaster 관련 파일은 GameFrameWorks와 Server가 함께 수정)은 현황.md의 의존/충돌 절을 먼저 확인하고 조정한다.
- 소스 파일 이동·추가 후에는 PreBuild(프로젝트 파일 재생성)를 돌려야 다른 세션의 빌드가 깨지지 않는다.
- 동시 실행 시 jg_log.txt가 덮어써질 수 있다.
- 격리 worktree · 검증용 게임 프로젝트는 `%TEMP%`(에이전트 스크래치패드) 밖, 저장소 안 `Temp/wt/<이름>` · `Temp/Games/<이름>`(git 무시 폴더)에 둔다. `%TEMP%` 아래에서는 MSBuild 파일 추적이 꺼져(MSB8029) 헤더를 고쳐도 다시 컴파일되지 않는다 — 낡은 obj 로 엉뚱한 곳에서 죽거나, 매번 `-t:Rebuild`(전체 빌드)를 해야 한다. 다 쓰면 `git worktree remove`, 저장소 `Temp/` 를 지웠으면 `git worktree prune`.
- **메인 트리 빌드 · 메인 Bin 실행은 `Build\BatchFiles\MainTree.cmd` 로 감싼다**(DevOps MT-1, 2026-10-03). 다른 세션의 빌드 · 실행 · 잠금이 끝날 때까지 기다렸다가(기본 6분, 30초마다 무엇을 기다리는지 출력) 잠금을 잡고 실행한 뒤 놓는다. 종료 코드는 감싼 명령 그대로다. 여러 세션이 메인을 동시에 빌드하거나, 빌드 중에 메인 Bin 에디터 · 런처 · 콘솔이 떠 있어 생기던 LNK1104 · LNK1168 · PCH 잠김을 막는다.
  - 빌드: `MainTree.cmd -name=<세션> build`(JGEngine.sln · DevelopEngine x64. `-project=JGConsole` · `-config=` · `-target=Rebuild`, 그 뒤는 MSBuild 인자). 메인 Bin 에서 에디터 · 런처 · 콘솔이 떠 있으면 그것도 기다린다.
  - 실행 · 생성: `MainTree.cmd -name=<세션> exec <프로그램> [인자]`(예: `exec Bin\DevelopEngine\JGConsole.exe console.selftest`, `exec GenerateProjectFiles.bat`). 빌드만 기다린다. 게임 프로젝트 세션이 메인 Bin 의 `JGConsole -runCook` 을 쓸 때도 이것으로 감싼다.
  - 여러 단계(메인에 파일 반영 → 생성 → 빌드 → 실행): `hold -minutes=15` → 같은 `-name=` 의 build · exec 는 바로 돈다 → 끝나면 `release`. 안 풀면 시간이 지나 저절로 풀린다(최대 60분).
  - `MainTree.cmd status` = 잠금 주인 · 기다리는 세션 · 도우미 밖 빌드(MSBuild · cl · link — VS · Rider 포함) · 메인 Bin 에서 도는 프로세스. 종료 코드 90 = 기다리다 시간 초과(막는 것 목록이 나온다 — 내 프로세스면 끄고, 남의 것이면 그 세션이나 사용자에게 알린다), 91 사용법, 92 MSBuild · 프로그램 없음.
  - 도구 시간 제한은 10분으로 두고, 길게 기다릴 일은 백그라운드 실행 + `-wait=30`. Git Bash 에서는 `cmd //c`. `-name=` 은 영문. `Temp/wt` · `Temp/Games` 는 대상이 아니다(따로 빌드). 기록 `Temp\MainTree\history.log`, 검증 `DevOps/Files/2026-10-03_MainTree_도우미_검증.txt`.

- **사용자 결정 항목(진행현황 §3 · 대시보드 “결정할 것”)은 쉬운 말로 쓴다**(사용자 피드백 2026-10-02 “무슨말인지 모르겠음”): ① 지금 생기는 일을 장면으로 ② 언제 생기는지 ③ 고를 것과 각각 무엇이 달라지는지 · 대략 일수 ④ 권고 ⑤ 급한지. 함수 · 변수 이름이나 프로토콜 같은 전문 용어는 괄호 안 참고로만 덧붙인다.
  - **엔진 용어는 다른 말로 바꾸지 않고 한 가지로 통일한다**(사용자 피드백 2026-10-03 D-31 "용어통일좀해줘. 그림판은 렌더러를 말하는거야??"). 렌더러 · 렌더 텍스처 · GPU · 프레임 · D3D12 경고 같은 사용자가 쓰는 엔진 용어는 그대로 쓴다. 쉬운 말은 용어를 바꾸는 것이 아니라 원인 → 결과를 한 단계씩 문장으로 풀어 쓰는 것이다. 각 선택지는 "무엇을 하는지"를 구체적인 동작으로 쓴다(예: "① GPU 작업이 끝날 때까지 기록을 남긴다 ② 앞 프레임이 끝나길 기다린다").
  - **결정 항목에는 그림 설명 페이지를 무조건 덧붙인다**(사용자 대시보드 명령 2026-10-17 D-39 "다음부터 요런 거 올 때, 이렇게 그림설명 무조건 덧붙이라고" + 전체 필수 지침 3번(10-17 14:00) "글만으로 묻지 않고 그림을 꼭 붙인다"). 결정 항목(D-n)을 진행현황 3절에 올리는 세션이 같이 만든다. **UI · 기획 · 코드 모든 결정**에 해당한다. 목표는 최종 결정권자(사용자)가 한눈에 보고 고르는 것 — 무엇을 정하는지, 선택지마다 무엇이 달라지는지(좋은 점 · 대가), 권하는 것과 그 까닭을 짧게.
    - 파일: `Document/D-n_<주제>_그림설명_<날짜>.html` — 로컬 HTML 한 장, 그림은 인라인 SVG(밖에서 받아 오는 것 없음), 밝은 · 어두운 화면 둘 다. 본보기 `Document/D-39_되감기지점_그림설명_2026-10-17.html`(색 · 글꼴 · 상자 꼴을 그대로 가져다 쓴다).
    - 내용: 위 ① ~ ⑤ 를 그림으로 — 지금 생기는 일의 흐름 · 왜 고를 것이 생기는지 · 선택지마다 무엇이 어디로 달라지는지(나란히 비교, 좋은 점 · 대가) · 고르지 않아도 정해 둔 것. 권고와 그 까닭 · 일수 · 급한지는 표로. 맨 위에 한 줄 요약.
    - 결정 종류에 따라 그림을 고른다(전체 필수 지침 3번):
      - **UI · 화면**(에디터 창 · 게임 UI · 도구 화면): 지금 모습과 시안 2 ~ 3개를 나란히 놓은 비교 그림(실제 캡처 + 시안 그림 · 목업).
      - **기획 · 규칙 흐름**(엔진이 돌리는 턴 · 페이즈 · 같이 하기 같은 동작): 상황과 행동을 차례대로 — 누가 무엇을 하면 어떻게 되는지(D-39 그림 1 · 2 처럼).
      - **코드 · 아키텍처 설계**: 지금과 바뀐 뒤를 견준 구조도 · 흐름도(인라인 SVG, 또는 Mermaid 를 그림으로 옮겨서 — 페이지는 밖에서 받아 오는 것 없이 열려야 한다).
    - 진행현황 D-n 행 끝에 그 파일 경로를 적고, 엔진 총괄에 보고할 때 경로를 함께 알린다. 엔진 총괄은 대시보드 D-n 의 "문서" 맨 앞에 붙인다 — 통합 대시보드 "결정" 탭이 그 링크를 바로 보여 준다(세션이 못 만들었으면 총괄이 만든다).
  - **묻기 · 답하기 · 확인받기 · 보고하기는 모두 보고함에 — 예외 없음**(전체 필수 지침 7, 2026-10-17 · 10-18 넓힘). **답**: 사용자가 물어본 것(요청 · 피드백 · 위키 피드백 · 보고함 덧붙임 · 전달 사항 속 “맞나 확인해 줘” · “무슨 소리야” · “왜 …” · “… 돼?”)에는 문서를 고치는 것과 따로 반드시 보고함에 "보고"로 답한다 — 질문 원문을 짧게 옮기고, 답을 쉬운 말로, 고친 곳 연결. 요청 메모(완료 note) · 채팅 · 상태 줄 · 위키 · 결과 파일에만 남기지 않는다. **확인받기**: 사용자가 직접 해 보고 알려 줘야 하는 것도 보고함에(`kind: "check"`). **보고**: 사용자가 시킨 일 · 검토의 결과와 사용자가 꼭 알아야 할 일(문제 · 막힘 · 밖에 올라간 것 — 커밋 · 푸시 포함)은 채팅에만 남기지 않고 보고함에 "보고"로 올린다 — `data.js` 결정 항목에 `kind: "report"`(선택지가 없으면 화면이 "확인함" 하나). 무엇을 했나 · 결과 · 남은 것 · 볼 곳(문서 · 화면)을 쉬운 말로, 도움이 되면 그림도. 자잘한 진행 소식은 올리지 않는다(팀 화면 진행 상황으로 충분). 분야 세션은 지금처럼 엔진 총괄에 알리고, 엔진 총괄이 보고를 올린다.
  - **대시보드 결정 칸 · 답 흐름**(통합 대시보드 “결정 사항” 탭 · 보고함 `http://127.0.0.1:47770/#/decisions`, 사용자 결정 2026-10-17 14:2x — 엔진 결정도 게임처럼 “선택지 고르기 + 지금 구현 + 덧붙일 말”로 답한다).
    - 결정 항목을 올리는 세션은 D-n 행 · 총괄 보고에 **한 줄 질문**, **선택지**(“이름 — 무엇이 달라지는지 · 좋은 점 · 대가”, 동그라미 번호 없이), **지금 구현**(답이 없으면 그대로 가는 것)을 적는다.
    - 엔진 총괄은 `data.js` 결정 항목(`cat: "decide"`)에 `question` · `options` · `now` · `from`(물은 세션) · `date` · `kind`(`decide` / 사용자가 직접 해 보는 `check`) · 필요하면 `images` 를 채우고, 그림 설명 페이지는 `docs` 맨 앞에 둔다. `check` 는 선택지 없이 화면이 “확인함 — 문제없음 · 문제 있음 · 건너뜀”을 준다.
    - 사용자가 고르면 수신기에 `[결정 답] 제목 / 고름: … / 덧붙임: …` 명령이 오고 `Document/Dashboard/answers/<항목 id>.json` 이 생긴다. 엔진 총괄이 반영한다: 결정이면 진행현황 3절 D-n 행에 결정을 적고 담당 세션에 맡김 → 답 파일을 `answers/applied/` 로 → 항목을 decide 에서 빼고 `data.js` `decided` 에 `{ id, qid, title, decision, date, applied }` 로(화면 “정한 것”) → 명령 상태를 `완료` 로.
    - 진행 탭의 “먼저 · 급함”은 `Document/Dashboard/priority.json`(`{ "<세션 key>": { "order": [항목 id], "urgent": [항목 id] } }`)과 `(대시보드 단추) <세션>: <제목> — 먼저/급함` 명령으로 온다. 엔진 총괄은 세션에 일을 맡길 때 이 순서를 따른다. 진행 · 앞으로 항목의 `owner` 는 세션 이름(`Core` · `GameFrameWorks` · …)으로 적는다(화면이 owner 로 묶는다).
- **사용자에게 보이는 글(보고 · 진행현황 · 대시보드 · 세션 메시지)에서 작업 번호는 이름과 함께 쓴다: "이름(번호)"**(사용자 피드백 2026-10-03 "D-31, Q-8 이런식으로 작업을 이야기하는데, 이게 어떤 작업인지 내가 너무 식별하기 어려워"). 예: "콘솔 명령 안 렌더러 경고 막기(D-31)", "게임 UI 기본 글꼴(ER-016)". 번호만 쓰지 않는다. 한 글에서 같은 번호가 다시 나올 때는 번호만 써도 된다. 대시보드는 번호 옆에 이름을 자동으로 붙인다(`Dashboard/data.js` 의 `glossary`, 새 번호가 생기면 총괄이 더한다).

## 5. 설계·코드 원칙

- 과설계 금지: 지금 구체적인 문제가 있을 때만 변경을 제안한다. 작은 절약, 정리 욕구, "나중에 X면 다시 보자"는 이유가 아니다.
- 네이밍: 시스템 이름은 그 시스템을 식별하고 접두어로 자연스럽게 읽혀야 한다. Actor/Component 접미는 유지한다.
- 코딩 스타일: if 본문을 한 줄로 쓰지 않는다. 중괄호는 항상 별도 줄에 둔다.

## 7. 총괄 · 대시보드

| 항목 | 규칙 |
|---|---|
| 작업 배정 | 총괄이 세션 메시지(`[총괄] …`)로 맡긴다. 사용자 결정 번호(D-n)와 범위 · 완료 기준이 함께 온다. 범위 밖이라고 적힌 것은 하지 않는다 |
| 보고 | 맡은 작업이 끝나거나 막히면 총괄 세션에 한두 줄로 알린다(결과 · 증적 위치 · 새로 생긴 보류나 결정). 분야 문서(현황 · TODO · 진행현황)는 지금처럼 각 세션이 갱신한다 엔진 총괄은 사용자가 시킨 일의 결과 · 꼭 알아야 할 일, 그리고 사용자 질문의 답을 하나도 빠짐없이 통합 대시보드 보고함에 "보고"(`kind: "report"`)로 올린다(전체 필수 지침 7 — 묻기 · 답하기 · 확인받기 · 보고하기 예외 없음). 분야 세션이 사용자 질문에 답할 내용을 찾았으면 엔진 총괄에 알려 보고함에 올리게 한다. 커밋 · 푸시는 분야 세션이 하지 않는다 — 2절 5번 |
| 직접 받은 일 | 사용자에게서 직접 받은 일(새 요청 검토 · 새 결정 · 착수)도 시작할 때와 끝날 때 엔진 총괄에 한 줄 알린다. 엔진 총괄이 꺼져 있으면 진행현황에 남기면 된다 — 총괄 수신기가 진행현황 변경을 보고 대시보드를 따라잡는다. 결정에 "총괄이 전달"이라고 적힌 작업 지시는 총괄이 켜질 때 보낸다. 엔진 총괄이 세션 목록에 안 보이면 세션 id `local_ddfc91e6-7f3c-405e-b413-9c2df90f1fff` 로 보내면 깨어난다(다른 꺼진 세션도 `list_sessions` 의 `local_…` id 로 보내면 깨어남) |
