## --why (전후 사정)

요청하신 C++ API Reference(게임 프로젝트가 엔진 코드를 보지 않고도 쓸 수 있는 문서)를 모듈별로 쓰기 전에, 계획을 확인받으려 합니다.
무엇을 · 어디에 · 어떤 꼴로 쓸지 정했고, Core API 하나로 견본을 만들었습니다.
지금은 API Reference 문서가 없습니다. 모듈 문서는 구조 · 흐름 설명(설계 설명)뿐입니다.
계획 전문: Document/기록/Core/Engine-34_APIReference_계획_2026-10-24.md · 견본: Document/기록/Core/Engine-34_견본/

**대상** — 게임 코드가 실제로 쓰는 엔진 형 · 매크로를 세었습니다.
- Core 45개 · GameFrameWork 84개 · Graphics 2개 · GUI 2개 · GameHost 0개 · JGEditor 0개입니다. DevOps 가 모은 게임 프로젝트가 쓰는 엔진 API 목록(Engine-35, ProjectAH 231 파일 · 게임 프로젝트 틀 · 검증 게임 4개)에서 셌습니다.
- 그래서 Reference 는 대부분 Core · GameFrameWork 입니다. GameHost · JGEditor 는 게임이 쓰는 C++ API 가 없어 README 만 둡니다.
- 엔진 내부 구현 · 엔진 프로그램 전용 · 플랫폼 구현은 넣지 않습니다.

**꼴** — API 하나를 세 곳에 같은 내용으로 둡니다(그림 2). API 가 바뀌면 세 곳을 같은 작업에서 함께 고칩니다.
- 공개 헤더 문서 주석(`///`): Visual Studio 툴팁에 그대로 보입니다. 그래서 게임 개발자가 엔진 헤더를 열지 않아도 됩니다.
- 위키 API Reference 항목: 개요 · 선언 · 매개변수/반환값 · 사용 예시 · 주의사항(스레드 · 수명 · 호출 순서 · 에러 처리). 문서 아래에 변경 이력을 둡니다.
- 모듈 README.md: 역할 · 의존 모듈 · 주요 클래스 · 사용 예시.

견본 문서 주석(콘솔 명령 선언 `HAutoConsoleCommand`):

```cpp
/// 파일 범위 전역 변수로 선언하는 콘솔 명령. 선언한 모듈이 연결되면 등록되고, 모듈이 내려가면 해제된다.
///
/// 스레드: 생성은 정적 초기화(DLL 로드) 중, 등록 · 실행은 메인 스레드.
/// 수명: 정적 저장 기간이어야 한다. 지역 변수 · 동적 할당으로 만들면 안 된다.
/// 오류: 이미 등록된 이름이면 오류 로그만 남기고 등록하지 않는다.
/// @param InName     명령 이름. 소문자 "영역.동작"(예: "audio.selftest").
/// @param InHandler  명령 본문. false 를 돌려주면 사용법을 출력한다.
HAutoConsoleCommand(const char* InName, const char* InUsage, const char* InDescription, HandlerFunction InHandler);
```

**견본 확인** — 사용 예시를 떼어 둔 작업 폴더의 JGConsole 에 넣어 빌드 · 실행했습니다. 성공 · 실패 · help 다섯 경우가 모두 예상대로 나왔습니다.
- 첫 빌드에서는 예시가 컴파일되지 않았습니다. 콘솔 명령 헤더에는 로그 매크로가 없어서, `Core.h` 를 함께 include 해야 했습니다. 이 점은 Reference 선언 칸에 적었습니다.
- 예시를 실제로 빌드해 보지 않았다면 틀린 예시가 문서에 들어갔을 것입니다. 정할 것 2 에서 안 1 을 권하는 까닭입니다.

**정할 것 세 가지**

1. 위키 자리(그림 1)
   - 안 A(권고) — 모듈 문서를 같은 이름 폴더로 옮기고, 그 아래에 「Core API Reference」를 둡니다. 좋은 점: 모듈 문서를 누르면 펼쳐져 Reference 가 바로 보입니다. 다섯 모듈이 지금의 GameFrameWork 와 같은 꼴이 됩니다. 대가: 모듈 문서 4개와 그림 경로를 옮겨야 합니다(0.5일).
   - 안 B — 옮기지 않고, 모듈 문서 바로 아래에 「00. Core API Reference」를 둡니다. 좋은 점: 옮길 것이 없어 바로 쓸 수 있습니다. 대가: 맨 위 목록이 두 배로 길어지고, GameFrameWork 만 모양이 다릅니다.
2. 예시가 컴파일되는지 확인하는 방법(그림 2 아래)
   - 안 1(권고) — 예시를 시험 프로그램(JGApiSamples)으로 묶어 엔진 빌드에 넣습니다. 좋은 점: API 가 바뀌면 빌드가 깨지므로, 문서에서 고칠 곳을 놓치지 않습니다. 대가: 예시 파일이 저장소에 들어가고, 처음 만드는 데 0.5일이 듭니다.
   - 안 2 — 문서를 쓸 때만 떼어 둔 작업 폴더에서 확인합니다(이번 견본 방식). 좋은 점: 엔진 코드에 아무것도 들어가지 않습니다. 대가: API 가 바뀐 뒤 예시가 깨져도, 다음 확인 전까지 모릅니다.
3. 헤더 문서 주석 작업을 확인받는 방법 — 헤더 파일을 고치지만, 주석만 더하고 동작은 그대로입니다.
   - 안 가(권고) — 이번 계획 확인을 설계도 확인으로 봅니다. 모듈 세션이 주석을 단 뒤, 빌드와 바뀐 줄(주석만인지)로 확인합니다. 대가: 헤더마다 따로 확인받지 않아, 주석 내용은 Reference 를 확인할 때 함께 보게 됩니다.
   - 안 나 — 모듈마다 대상 헤더 목록과 주석 견본을 다시 올려 확인받습니다. 대가: 확인을 5번 받아야 하고, 1~2일 늘어납니다.

**일수** — 모두 합쳐 약 14일입니다. Core 를 먼저 하루 써서 꼴을 굳힙니다. 그 뒤 GameFrameWork · Graphics · GUI · Editor 를 나란히 하면 달력으로 약 7일입니다(GameFrameWork 가 가장 깁니다).

**급한지** — 급하지 않습니다. 답이 오면 모듈별 작성(Engine-38~42)을 시작합니다.
