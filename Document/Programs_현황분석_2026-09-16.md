## 3. 발견된 문제

### P1 — PreBuild 실행 순서가 뒤집혀 있다

`Build/BatchFiles/PreBuild.bat` 은 HeaderTool → BuildTool 순으로 돈다. 그런데 의존 방향은 정반대다:

- BuildTool `Run()` **마지막**에 `HModuleSystemInfo::Set()` 으로 `module_system_info.json` 을 쓴다 (`BuildTool.cpp:80`).
- HeaderTool `Run()` **첫 줄**에서 `HModuleSystemInfo::Get()` 으로 그 파일을 읽는다 (`HeaderTool.cpp:71`).

**결과**
- HeaderTool 은 항상 **직전 실행분(1세대 뒤진) 모듈 집합**으로 동작한다.
- 새 SharedLib 모듈을 추가하면 PreBuild 를 **두 번** 돌려야 코드가 생성된다.
- 클린 클론에서는 파일이 없으므로 **첫 PreBuild 는 코드 생성 0건**으로 끝나고, 그 상태로 빌드하면 `.generation.h` 부재로 11개 헤더가 깨진다.

**주의 — 단순히 순서만 뒤집으면 안 된다.** premake 는 `codeGenPath .. "**.cpp"` 글롭을 *생성 시점에* 전개해 `.vcxproj` 에 파일 목록을 통째로 박아 넣는다 (`Temp/ProjectFiles/Graphics.vcxproj` 에 `.generation.cpp` 5개가 명시적으로 들어 있음). 따라서 BuildTool → HeaderTool 로 뒤집으면 **HeaderTool 이 만든 파일이 프로젝트에 안 들어가** 컴파일조차 되지 않는다.

즉 이건 두 툴 사이의 **순환 의존**이다.
- HeaderTool 은 BuildTool 이 쓰는 모듈 목록(`module_system_info.json`)이 필요하고,
- BuildTool 의 premake 는 HeaderTool 이 만든 파일이 디스크에 이미 있어야 한다.

두 순서 모두 콜드 스타트에서 PreBuild 2회를 요구한다. 현재 순서가 그나마 덜 나쁘다 — 지연이 *모듈 목록*에만 걸리고, 뒤집으면 지연이 *생성 파일 자체*에 걸려 더 치명적이다.

**수정 방안**

| 안 | 내용 | 비용 | 평가 |
|---|---|---|---|
| **A** | `PreBuild.bat` 을 BuildTool → HeaderTool → BuildTool 3단으로 | 코드 수정 0, bat 한 줄 추가 | 항상 1회 PreBuild 로 정확. BuildTool 이 2번 도는 낭비 (P2 PCH 재작성 고치면 부담 작음) |
| **B** (권장) | HeaderTool 이 `module_system_info.json` 에 의존하지 말고 **직접 `*.module.json` 을 스캔**해 `ModuleFormat == "SharedLib"` 집합을 만든다 | HeaderTool 에 모듈 스캔 추가 (BuildTool `findModuleInfo` 와 동일 로직) | 순환이 사라져 현재 순서 그대로 1회에 정확 |

B 를 택해도 BuildTool 의 `HModuleSystemInfo::Set()` 은 **그대로 둬야 한다.** 이 파일은 런타임에서도 읽는다 (`Source/Runtime/Core/Object/ObjectGlobalSystem.cpp:251`).

### P1 — `headertool_arguments.json` 이 통째로 무시된다

`Source/Programs/JGHeaderTool/Class/Arguments.h:38`

```cpp
virtual void ReadJson(PJsonData& json)          // ← const 누락, override 미표기
```

베이스는 `IJsonable::ReadJson(const PJsonData&)` (`Source/Runtime/Core/FileIO/Jsonable.h:11`). 시그니처가 달라 **오버라이드가 성립하지 않는다.** 역직렬화는 `Json.h:809` 의 `static_cast<IJsonable*>(value)->ReadJson(jsonData)` 로 가상 디스패치되므로, 실제로는 **베이스의 빈 구현**이 호출된다.

**결과** — `headertool_arguments.json` 을 어떻게 고쳐도 반영되지 않고, HeaderTool 은 언제나 `PArguments` 생성자 기본값으로 돈다. 현재 json 값과 기본값이 사실상 같아서 증상이 드러나지 않을 뿐이다.

**수정** — `virtual void ReadJson(const PJsonData& json) override`. 같은 파일의 `WriteJson` 도 `const override` 표기가 빠져 있다. (JGBuildTool 쪽 `Arguments.h:95` 는 정상.)

### P2 — `PModuleInfo::WriteJson` 복붙 버그로 템플릿이 깨져 있다

`Source/Programs/JGBuildTool/Class/ModuleInfo.h:61-62`

```cpp
json.AddMember("ModuleName", ModuleFormat);        // ← ModuleName 이어야 함
json.AddMember("ModulePath", ModuleDependencies);  // ← ModulePath 이어야 함
```

읽기(`ReadJson`)는 정상이라 빌드에는 영향이 없지만, 이 템플릿을 보고 새 모듈을 만드는 사람은 반드시 틀린 스키마를 쓰게 된다. `CodeGenPath` 도 Write 대상에서 빠져 있다.
