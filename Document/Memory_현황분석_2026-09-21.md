# 메모리 시스템 현황 분석 (2026-09-21)

메모리 관리 개선 작업에 앞서 현재 메모리 시스템의 구조, 실측 데이터, 문제점을 정리한다.
근거는 2026-09-21 12:35 기준 소스(`Source/Runtime/Core/Memory/`, `Core/Object/`, `Core/CoreSystem.*`, `Core/Misc/Module.*`)와
같은 날 생성된 실행 로그 3개(`Bin/DevelopEngine/jg_log.txt`, 아래 §3)이다. 소스는 수정하지 않았다.
각 항목 끝의 표기는 확인 방법이다. `[코드]` 소스 확인, `[로그]` 실행 로그 실측, `[재현]` 별도 컴파일로 재현, `[추정]` 근거는 있으나 직접 확인은 못 함.

## 1. 요약

1. **메모리 풀은 고정 크기 클래스 × 고정 개수 구조라 한 클래스가 다 차면 `nullptr`을 돌려주고, 그 자리의 `JG_ASSERT`는 문자열 리터럴을 검사해 절대 발동하지 않는다.** 호출자는 그대로 `placement new`/`vector` 쓰기를 해서 로그 한 줄 없이 죽는다. 오늘 11:57에 끝난 실행 로그가 정확히 이 상태(32바이트 클래스 4096/4096)에서 끊겼다. `[코드][로그]`
2. **32바이트 클래스를 채운 것은 PSO 캐시 노드 누수다.** `D3D12_GRAPHICS_PIPELINE_STATE_DESC`의 패딩 바이트까지 해시해 프레임마다 새 PSO를 만들고 캐시에 넣었다(프레임당 3개). 이 원인은 병렬로 진행 중인 다른 세션이 `PipelineState.cpp`에서 내용 기반 해시로 고치는 중이며(12:30 수정, 미커밋), 수정 후 실행 로그에서 PSO 생성이 2회로 줄고 누수가 사라진 것을 확인했다. **풀 쪽 취약점(무음 크래시, 고정 한도)은 그대로 남아 있다.** `[코드][로그]`
3. **`PSharedPtr`/`PWeakPtr`의 대입 의미론이 표준과 다르다.** `p = nullptr`, `p = 빈포인터`, `p = std::move(빈포인터)`는 모두 아무 일도 하지 않고(참조가 남는다), `p = p`는 참조를 잃는다. 엔진 안에 스마트 포인터 멤버에 `= nullptr`을 대입하는 곳이 28곳 있고, 그중 `HJGGraphicsModule::ShutdownModule`의 `_graphicsAPI = nullptr`도 해제되지 않는다. `[재현][코드]`
4. **GC는 FIFO 큐를 매 프레임 두 번 순회하며 살아 있는 객체를 다시 넣는다.** 파괴 순서가 할당 순서(부모 먼저)라 2026-09-17 종료 크래시의 구조적 원인이 남아 있고, 참조 카운터가 별도 힙 객체라 WeakCount를 무시하고 해제한다(TODO 5-18). GC는 프레임 시작(펜스 대기 전)에 돌아 GPU 리소스 파괴가 GPU 완료와 무관하다. `[코드]`
5. **예약 대비 사용률이 0.5%다.** 스레드별 청크 100.69MB(모든 페이지에 헤더를 써서 전부 상주) 두 개가 잡히는데, 메인 청크의 피크 페이로드는 548KB(6,270블록), 워커 청크는 5.5MB다. 반대로 32바이트 클래스는 정상 실행에서도 275개(6.7%)를 상시 쓰고 누수가 있으면 4096개를 넘긴다. 크기 클래스 개수가 실측 분포와 맞지 않는다. `[로그]`
6. **풀 할당·해제마다 Info 로그를 쓰고 매 줄 flush한다.** 로그 469,347줄 중 469,222줄(99.97%)이 `[Memory]`이고, 한 프레임에 풀 연산 345회가 돈다(그중 16바이트 47회는 MSVC 디버그 이터레이터 프록시). 성능 측정과 로그 판독을 모두 방해한다. `[로그][코드]`

## 2. 구조

### 2-1. 계층

```
[GC 객체]  Allocate<T>()  ──▶ GMemoryGlobalSystem ──▶ HMemoryPool.Allocate(sizeof T)
                                  │  AllocatedMemoryBlocks (std::unordered_map<void*, HMemoryBlock>, CRT 힙)
                                  │  AllocatedMemoryBlockQueue (std::queue<void*>, CRT 힙)
                                  │  HMemoryBlock { RefCount, WeakCount : std::unique_ptr<atomic_int> } (CRT 힙 2개)
                                  └─ Update(): garbageCollection(1)  /  Flush(): (0)  /  ~dtor: forceFlush(-1)

[컨테이너]  HList/HHashMap/HMap/HHashSet/HSet/HQueue/HDeque/HStack
            = std::* + HAllocator<T> ──▶ HMemoryPool.Allocate / Deallocate  (GC 추적 없음)

[풀]        HMemoryPool  ──▶ 스레드 ID(hash<thread::id>) → HMemoryChunk 1개 (첫 할당 때 malloc 100.69MB)
            HMemoryChunk ──▶ 크기 클래스 19개(4B~1MB, 2의 제곱) × 고정 개수, 블록 앞 16B 헤더(HMemoryHeader)

[풀 밖]     PString(_rawString=std::string), PName(std::weak_ptr<atomic_int>), GStringTable의 RefCount(shared_ptr),
            spdlog, rapidjson, imgui/implot, HDelegate(malloc/free), GCoreSystem·시스템 인스턴스·모듈 인터페이스(new/delete),
            D3D12 객체(ComPtr), GPU 힙(PUploadAllocator 2MB 페이지, PDescriptionAllocator 1024개 페이지, 스테이징 리소스)
```

- `IMemoryObject`(가상 소멸자 + `Construct()`/`Destruction()` 훅)를 상속한 타입만 `Allocate<>`/`Wrap<>` 대상이다. 직접 상속 클래스 38개 + `JGObject` 계열 6개 = 44개. `Construct()` 오버라이드는 `JGWidgetComponent` 1곳, `Destruction()` 오버라이드는 0곳. `PMemoryObject`, `TRawPtr`, `bProcessingGarbageCollection`은 선언만 있고 쓰는 곳이 없다. `[코드]`
- 값 타입인 `PString`, `PName`, `JGType`, `PSharedPtr`, `PWeakPtr`, `PJsonData`도 `IMemoryObject`를 상속해 vptr 8바이트를 가진다. `PSharedPtr<T>`는 32바이트(vptr + 포인터 3개)다. `[코드]`
- 사용 규모(`Source/` 전체 grep): `Allocate<` 호출 약 50곳(Core 17, Graphics 31, GUI 3), `PSharedPtr<` 575회, `PWeakPtr<` 70회, `SharedWrap`/`Wrap` 12곳, `HList<` 301회, `HHashMap<` 120회, `HHashSet<` 43회, `HQueue<` 19회, `HMap<` 12회. 풀 밖 경로는 `std::vector` 12곳(대부분 5-23 우회로 주석됨), `std::shared_ptr` 6곳, `unique_ptr` 9곳, 생 `new` 3곳(`CoreSystem.cpp:32`, `CoreSystem.h:76`, `Platform.h:36`), `malloc` 2곳(풀 자체, Delegate). 리플렉션 코드젠(`Temp/CodeGen`)이 시작 시 `MakeStatic*` 78회(클래스 12, 열거형 6, 메타 53, 프로퍼티 7)를 부르고 각각 `Allocate`한다. `[코드]`

### 2-3. 할당 경로 (`MemoryPool.cpp:78-116`, `Memory.h:565-600`)

1. `HMath::AlignPowerOfTwo(size)` → 올림 2의 제곱(최소 4). `1 << Log2(value)`가 `int` 시프트라 1GB 이상에서 넘친다(현 한도 안에서는 무관).
2. `HasSpace()` → `MemoryQueues.at(class)`. `_1_GB`(실제 값 2MB) 열거자는 있지만 큐가 없어 **1MB를 넘는 요청은 전부 `std::out_of_range`**(종료 코드 3, 로그 없음). 기존 기록(5-23)의 "2MB 한도"는 정확히는 1MB다.
3. 클래스가 비었으면 `JG_ASSERT("no memory space left.")` — `assert(문자열)`이라 항상 참 — 후 `return nullptr`. `GMemoryGlobalSystem::Allocate`는 검사 없이 `new(MemPtr) T(...)`, `HAllocator::allocate`는 그대로 반환해 `std::vector`가 널에 쓴다. **크래시 위치는 풀이 아니라 호출자이며 원인을 알려주는 출력이 없다.**
4. `Deallocate`의 이중 해제 검사는 `JG_ASSERT(true)`로 역시 무효.
5. 성공하면 `JG_LOG(Memory, Info, ...)`. 포맷이 `%u`(uint64 ID), `%x`(포인터)라 ID와 주소가 32비트로 절단돼 찍힌다.

### 2-4. GC 객체 수명 (`Memory.cpp`)

- `Allocate<T>`: 풀 블록 + `HMemoryBlock`(맵 노드, atomic 2개 → CRT 힙 3회) + 큐 push. 객체 하나에 힙 할당 4번, 전역 재귀 뮤텍스 1회.
- 참조 0이 되어도 즉시 파괴하지 않는다. `Update()` → `garbageCollection(1)` → `garbageCollectionInternal(10240)` 2회. 각 회차가 큐에서 최대 10,241개를 꺼내 RefCount==0이면 `Destruction()`→`~IMemoryObject()`→풀 반납→맵 erase, 아니면 다시 push. **살아 있는 객체 전부가 매 프레임 두 번 큐를 돈다**(객체 수에 선형). 지금 객체 수(수백)에서는 싸지만 늘면 그대로 비용이 된다.
- `GMemoryGlobalSystem`은 시스템 목록 2번째라 GC가 `GCoreSystem::Update`의 맨 앞, 즉 스케줄러가 `GraphicsBegin`(`PCommandQueue::Begin`의 펜스 대기)을 돌리기 전에 실행된다. 프레임 N에 참조를 끊은 텍스처/버퍼는 N+1 프레임 시작에 `ComPtr`이 풀리는데 그 시점 GPU는 아직 N 프레임을 실행 중일 수 있다. 지금은 DevScene 리소스가 장수해서 드러나지 않는다.
- 파괴 순서 = 큐 순서 = 할당 순서. 부팅 초기 객체(API, 큐, 할당자)가 그것을 쓰는 텍스처보다 먼저 죽는다. 2026-09-17 크래시는 캐시 무효화 + null 가드로 무해화했을 뿐 구조는 그대로다(기존 P3).
- `garbageCollectionInternal`은 WeakCount를 보지 않는다. 블록 erase로 `unique_ptr<atomic>` 두 개가 해제된 뒤에도 `PWeakPtr::IsValid()`가 `_pRefCount->load()`를 읽는다(해제 메모리 읽기, TODO 5-18). 풀이 같은 주소를 재발급하면 `Wrap(ptr)`이 다른 객체를 돌려줄 수 있다(ABA).
- `Wrap<T>(ptr)`은 전역 뮤텍스 + 해시 조회다. `PWeakPtr::Pin()`, `SharedWrap(this)`, `HTaskHandle`, 델리게이트 `CreateSP` 등 15+12곳이 매번 이 경로를 탄다.
- `Allocate<T>`의 "IMemoryObject 상속" 검사는 런타임 `JG_ASSERT`라 릴리스 구성에서는 통과하고, GC가 `(IMemoryObject*)ptr`로 가상 소멸자를 부르는 순간 UB가 된다(`Wrap`은 이미 `static_assert`).

### 2-5. 종료 순서 (`CoreSystem.cpp:81-122`, `Module.cpp:228-268`)

`Destroy()`: 시스템 `Destroy()` 역순(모듈 시스템이 `_moduleOrder` 역순으로 `ShutdownModule` → `Flush`) → `Flush` → `UnRegister` StringTable → Object → Module → Schedule → Timer → **Memory(소멸자에서 `forceFlush`)** → Log → DLL 언로드.
`forceFlush`는 참조가 남아 있어도 강제 파괴한다(`bForce`). 이 시점 살아 있는 대표 객체는 `PThread` 28개(스케줄러가 삭제될 때 참조가 풀림), `PTimer`, `PSequentialIDGenerator`, `PWindowsJWindow`다. 이 소멸자들이 이미 사라진 `GStringTable`/`GObjectGlobalSystem`을 `GetInstance()`로 부르면 `*nullptr`이다(지금은 안 부르지만 보장 장치가 없다). 강제 파괴 뒤 남은 `PSharedPtr` 소멸자는 해제된 카운터를 감소시킨다. 엔진 컨테이너를 static 저장소에 두면 안 되는 규칙(TODO 설계 규칙, 5-17)도 같은 뿌리다.

### 2-6. 문자열 (`String/`, 풀 밖)

- `PString`은 `std::string`(CRT 힙)을 들고, 해시 `_stringCode`만 계산한다. 풀을 쓰지 않는다.
- `PName`은 `GStringTable`에 문자열을 등록하고 `std::weak_ptr<atomic_int>`로 참조 수를 센다. 복사·소멸마다 `weak_ptr::lock()`(제어 블록 원자 연산 2회) + `fetch_add/sub`가 든다. `_DEBUG`에서는 `HRawString` 사본도 든다(`PName` 약 72B).
- `GStringTable::removeOldStringInfos`는 매 프레임 큐에서 1개를 꺼내 검사만 하고 **다시 넣지 않는다.** 참조가 0이어도 `FrameCount >= INT32_MAX` 조건이라 지우지 못하고, 큐가 비면 이후 등록된 문자열은 검사 대상도 아니다. 사실상 "영구 인터닝"인데 정리 코드가 남아 있어 의도가 불명확하다. `HStringInfo`는 narrow/wide 두 사본을 든다(`HHashMap` 노드 128B 클래스).

### 2-7. 통계 도구 (`Source/Editor/DevStatistics/MemoryStatistics.cpp`)

`HMemoryPool::GetStatInfo`가 청크 100MB를 블록 단위로 전부 걷고(30,768블록) 블록마다 `std::map<..., std::vector<HMemroyBlockStat>>`에 push한다. 위젯이 열려 있는 동안 매 프레임 이 비용을 낸다. 출력은 스레드별 헤더/사용/빈 비율 막대뿐이고 **루프 안에서 `MemoryChunkStateInfos[0]`을 참조해 모든 그룹이 메인 스레드 값을 보인다**(`MemoryStatistics.cpp:59-61`). 클래스별 사용률·피크·실패 횟수는 없다. 이번 32바이트 고갈은 이 도구로는 볼 수 없었다.

- 32B live는 `Startup Graphics Module` 시점 82, DevScene 로드·리드백 직후(29,889행) 275, 이후 **345행 주기로 3개씩** 증가(누수 간격 71·67·207행 반복 = 서브메시 드로우 2회 + 합성 드로우 1회의 PSO Finalize). 469,146행에서 4,096 도달, 201행 뒤 `Allocated 16 byte`에서 로그가 끝난다. 종료 시퀀스 없음, 프로세스 없음, 이벤트 로그·`%LOCALAPPDATA%\CrashDumps`에 기록 없음(디버거 아래 실행 또는 강제 종료로 보임). 병렬 세션이 `PipelineState.cpp` 주석에 "32바이트 풀 블록(4096개)이 고갈되면 push_back이 널 포인터에 생성자를 돌려 크래시"라고 관찰을 남겼다.

- 정상 상태 한 프레임(345회)의 풀 연산 구성: 16B 할당 47·해제 48, 128B 19·19, 64B 18·20, 32B 10·10, 8B 4·4, 4KB·1KB·256B·4B 각 1·1. 16B는 `_ITERATOR_DEBUG_LEVEL=2`의 컨테이너 프록시(컨테이너 생성마다 1개)와 `HList` 1~2원소 버퍼, 128B는 빈 `HHashMap`의 버킷 배열이다. 즉 **프레임당 컨테이너를 수십 개 만들고 버린다**(로컬 `HList<PSharedPtr<>>` 반환, `HResourceState` 복사 등).

## 5. 개선 방향 제안

결정은 사용자 몫이고, 여기서는 의존 관계와 효과 기준으로 순서를 제안한다.

### 단계 A — 안전장치 (작고 독립적, 즉시 가능)

1. **풀 실패를 실패로 만들기.** `HasSpace` 실패·1MB 초과 시 요청 크기·클래스·스레드를 Critical 로그로 남기고 (a) 시스템 힙 폴백(헤더에 표식) 또는 (b) 즉시 abort 중 하나를 택한다. `JG_ASSERT(문자열)` 두 곳을 조건식으로 고친다. `GMemoryGlobalSystem::Allocate`/`HAllocator::allocate`의 `nullptr` 처리. (TODO 5-23을 여기로 흡수)
2. **스마트 포인터 대입 수정.** 빈 rhs 대입 = `Reset()`, `operator=(nullptr_t)` 추가, 자기 대입 가드, 이동 후 rhs 비움. `= nullptr` 28곳이 의도대로 동작하는지 확인(특히 `ShutdownModule`류).
3. **할당 로그 분리.** `[Memory]` 할당/해제 로그를 컴파일 스위치(예: `JG_MEMORY_TRACE`) 아래로 옮기고 기본 꺼짐. `flush_on`은 `warn` 이상으로. 포맷 `%llu`/`%p` 수정.
4. **통계 도구 보수.** 인덱스 버그, 클래스별 live/피크/한도/실패 횟수 카운터(할당 경로에서 O(1) 증감), 청크 워크 제거.

### 단계 B — GC·스마트 포인터 구조

5. **제어 블록 통합.** RefCount/WeakCount/플래그를 풀 헤더(또는 객체 앞 고정 오프셋)에 두고 `AllocatedMemoryBlocks`·큐·`unique_ptr` 2개를 없앤다. `Wrap`이 O(1)·무락이 되고, 객체 파괴(Ref 0)와 메모리 반납(Weak 0)을 분리해 5-18을 해결한다.
6. **파괴 정책.** 참조가 0이 되는 순간 "지연 파괴 목록"에 넣고(순회 제거), 파괴는 프레임 경계에서 N프레임 지연 또는 GPU 펜스 값 기준으로. 순서는 등록 역순(LIFO)을 기본으로 하면 부모-자식 문제(P3)가 사라진다.
7. **종료 규약.** `forceFlush` 시점에 살아 있는 객체를 로그로 열거(누수 리포트)하고, 시스템 삭제 순서를 GC 이후로 옮기거나 GC 객체 소멸자에서 시스템 접근을 금지하는 검사 추가.

### 단계 C — 풀 재설계

8. **성장형 클래스.** 클래스별 고정 개수 대신 페이지(예: 64KB~1MB) 단위로 필요할 때 늘린다. 초기 예약은 실측(메인 피크 6,270블록·548KB)에 맞춰 수 MB로. 대형 블록(예: 64KB 이상)은 시스템 힙 직접 할당.
9. **스레드 간 해제.** 타 스레드 해제는 소유 청크의 반납 큐(락 또는 lock-free)에 넣고 소유 스레드 `Allocate`가 회수. `hash<thread::id>` 충돌 대비.
10. **정렬·`HAllocator` 완성.** `alignof(T)` 반영, `operator==/!=`, `is_always_equal`, 종료 후 `deallocate` 정책 명시.
11. **값 타입에서 `IMemoryObject` 분리 검토.** `PString`/`PName`/`PSharedPtr`의 vptr 제거 또는 GC 대상 표식을 별도 태그로.

### 단계 D — 관측

12. 프레임별 클래스 live 델타 리포트(이번 32B 누수 같은 "프레임당 +k" 자동 감지), 선택적 콜사이트 태깅(파일/행), 시작·종료 스냅샷 비교. 로그 기반 리플레이는 `Document/Memory/tools/memlog_stats.sh`로 지금도 가능하다.

### 검증 기준(개선 전후 공통)

- 정상 종료 시 풀 Allocate 수 == Deallocate 수, `Memory Chunk Shutdown` 2줄, 종료 코드 0.
- 정상 상태 프레임 구간에서 모든 클래스 live가 평탄(델타 0), 어떤 클래스도 한도 근접 없음.
- `Graphics PSO created`가 시작 뒤 증가하지 않음.
- 스레드 불일치 해제(`Dismatch`)가 있어도 손상 없음(현재는 경고만 남김).
