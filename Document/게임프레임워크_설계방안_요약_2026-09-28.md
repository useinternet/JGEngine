# 게임 프레임워크 설계 방안 요약

작성 2026-09-28. **엔진 시스템 설계** 검토. 콘텐츠(카드·규칙 데이터) 설계는 범위 밖.
전제: 엔진 레이어 / 게임 레이어 2계층. 게임 프레임워크는 엔진 레이어. 목표 장르: 턴제·보드·카드.

## 설계 방안 A. 씬 단일 계층 (Actor / Component)

**3줄 요약**
- 엔진은 World / Actor / Component 씬 시스템만 제공한다.
- 게임 규칙·턴·효과는 게임 레이어가 컴포넌트로 직접 구현한다.
- 규칙과 연출이 같은 오브젝트에서 실행된다.

**장점**
- 가장 단순. 리플렉션·GC·프리팹 등 기존 자산을 그대로 쓴다.
- 장르를 가리지 않는다.

**단점**
- 결정론·되돌리기·리플레이·AI 시뮬레이션·헤드리스 실행을 엔진이 보장하지 못한다. 게임마다 다시 만든다.
- 규칙이 연출 타이밍에 묶인다.
- 턴제 장르에 필요한 시스템(턴 상태 기계·명령·효과 해결)이 엔진에 없다.

---

## 설계 방안 B. 시뮬레이션 / 프레젠테이션 2계층

**3줄 요약**
- 엔진은 **시뮬레이션 커널**(결정론 상태 컨테이너 · 명령 · 이벤트 로그 · 스냅샷 · 턴 상태 기계 · 효과 해결 큐)과 **씬 계층**(A의 World / Actor / Component + 시퀀서)을 둘 다 제공한다.
- 게임 레이어는 커널 위에 규칙과 데이터를, 씬 위에 연출을 얹는다.
- 두 계층은 이벤트로만 연결된다. 씬은 시뮬레이션 상태를 읽기만 한다.

**장점**
- 되돌리기·리플레이·저장·AI·헤드리스·멀티플레이가 엔진 수준에서 보장된다.
- 연출이 규칙 타이밍에서 풀려나 자유롭다.
- 턴제·보드·카드 공통 시스템이 엔진에 한 번만 있다. 세 참조작(StS2·BG3·Gloomhaven)이 모두 이 방향이다.

**단점**
- API 가 두 벌이다. 계층 경계(해결 중 선택 입력, 연출 중 입력, 이벤트 정보량)를 설계해야 한다.
- 커널을 범용으로 만들려다 과설계할 위험이 있다.
- 실시간 장르에는 커널이 불필요하다.

---

## 설계 방안 C. ECS 프레임워크

**3줄 요약**
- 엔진은 Entity / Component / System 런타임 하나를 제공한다.
- 게임 상태는 컴포넌트 데이터, 규칙과 연출은 모두 시스템이다.
- 씬 오브젝트 모델 대신 ECS World 하나로 통일한다.

**장점**
- 상태가 균일한 데이터라 직렬화·복제·스냅샷이 기계적이다.
- 대량 오브젝트 성능. BG3 가 이 구조다.

**단점**
- 기존 리플렉션·GC·프리팹 자산 활용도가 낮고 에디터·툴링을 다시 만든다.
- 턴제 규칙의 깊은 분기에 시스템 순회 모델이 맞지 않는다.
- 1인 구현 비용이 가장 크다.

---

## 설계 방안 D. 노드 트리 (Godot 형)

**3줄 요약**
- 엔진은 단일 노드 트리와 씬 리소스를 제공한다.
- 조합은 자식 노드, 종류는 상속으로 표현한다.
- 성능은 데이터 지향 서버 계층이 맡는다.

**장점**
- 개념이 하나라 학습·직렬화·수명 관리가 단순하다.

**단점**
- 스크립트 언어 없이는 행동 조합이 상속에 갇힌다.
- 규칙/연출 분리가 없어 A 와 같은 한계를 가진다.

## 엔진 레이어 / 게임 레이어 경계 (B 기준)

| 엔진 레이어가 제공 | 게임 레이어가 구현 |
|---|---|
| 결정론 상태 컨테이너, 스냅샷, 직렬화 | 상태의 구체 필드(정의) |
| 명령 · 검증 · 이벤트 로그 인터페이스 | 구체 명령과 검증 규칙 |
| 턴 상태 기계 + 순서 정책 인터페이스 | 게임별 순서 정책 |
| 효과 해결 큐, 트리거 정렬 규칙, 해결 중 선택 대기 | 구체 효과와 트리거 |
| 보드 추상화 인터페이스 | 격자 종류 · 이동 규칙 |
| AI 인터페이스(합법 수 열거 · 평가) | 평가 함수 · 행동 정책 |
| 씬(World / Actor / Component), 시퀀서, 피킹, 카메라 | 연출 액터와 UI |
| 헤드리스 러너, 체크섬 검증 | 테스트 시나리오 |

의존 방향: 게임 → 엔진만. 커널 모듈은 Core 만 의존(Graphics/GUI 금지).
