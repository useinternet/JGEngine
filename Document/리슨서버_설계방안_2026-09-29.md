# 리슨 서버 설계 방안

작성 2026-09-29. **엔진 시스템 설계 검토. 소스 변경 없음.** 대상: GameFrameWorks(GameMaster 커널 · 월드) 위에 리슨 서버(호스트가 서버 겸 플레이어)를 얹는 방법.
기준 코드: 09-29 이름 변경 반영본(`PGameMaster` · `HGameplay*` · `JGGameMasterActor`). 관련: `GameFrameWorks_설계코드리뷰_2026-09-28.md`. 검증 기록: `Memory/2026-09-29_리슨서버_설계.md`.
범위: 턴제 커널(GameMaster) 복제. 실시간 월드(자유 이동)의 액터 복제는 다루지 않는다.

---

## 0. 결론

- **권장: 방안 A — 호스트 권한 명령 중계 + 결정론 복제.** 호스트의 `PGameMaster` 만 명령을 승인하고, 승인된 명령에 순번 · 체크섬을 붙여 전원에게 보낸다. 클라는 같은 명령을 자기 `PGameMaster` 복제본에 적용해 같은 이벤트로 연출한다.
- 커널이 이미 복제 재료를 갖고 있다: 입구 하나(`Submit`), 값 타입 상태, 시드 난수, 체크섬, 저장 문서(초기 + 현재 + 명령 로그). **새로 만들 것은 `GameFrameWorks/Network/` 폴더 하나(전송 + 세션)**이고, 기존 코드는 입구 몇 곳만 바뀐다.
- **싱글플레이도 같은 세션 경로(Standalone)를 탄다.** 호스트 자신의 입력도 원격 입력과 같은 줄에 선다. 멀티 전용 코드 경로를 만들지 않는다.
- **먼저 고칠 것:** 리뷰 C7(Load 후 트리거 순서가 달라짐 → 입장한 클라가 첫 명령부터 불일치), C1(죽은 ID 쓰기 — 원격 명령은 늦게 도착해 흔해진다), 규칙 지문(다른 빌드끼리 접속해도 모른다). 협동의 **동시 행동**은 커널 결정이 따로 필요하다(§5).
- 전송은 Winsock TCP. LAN · 직접 IP 로 접속하며, 인터넷 너머는 호스트가 포트를 열어야 한다.

## 1. 방안

### 방안 A. 명령 중계 + 결정론 복제 (권장)

**3줄 요약**
- 모든 명령은 호스트로 가서 검증 · 실행된다. 호스트는 `승인{순번, 명령, 체크섬}` 을 전원에게 보낸다.
- 클라는 복제 `PGameMaster` 에 같은 명령을 `Submit` 해 같은 이벤트를 얻고, 체크섬으로 일치를 확인한다.
- 입장 · 재접속 · 불일치 복구는 저장 문서 한 벌을 보내 이어받게 한다.

**장점**
- 기존 `Submit` · `Validate` · `Checksum` · 직렬화를 그대로 쓴다. 새 코드가 가장 적다.
- 메시지가 명령 크기(수백 바이트)다. 클라가 합법 수 · 미리보기를 로컬에서 계산해 UI 가 즉시 반응한다.
- 클라도 전체 상태와 로그를 가져 저장 · 리플레이가 그대로 된다.

**단점**
- 모든 클라가 전체 상태(덱 순서 · 시드)를 안다. 은닉 정보가 없다 — 협동은 무방, PvP 는 불가.
- 빌드 · 규칙 세트가 같아야 하고, 결정론 버그는 곧 불일치(desync)다.
- 체크섬이 상태 전체 JSON 직렬화라(`GameplayState.cpp:132`) 명령마다 전원이 비용을 낸다. 비용은 단계 2 에서 잰다.

### 방안 B. 호스트 단독 실행 + 이벤트 · 상태 복제

**3줄 요약**
- 규칙은 호스트에서만 돈다. 클라는 규칙 없이 이벤트와 상태(스냅샷 · 델타)를 받아 연출만 한다.
- 클라마다 볼 수 있는 것만 보낸다(은닉 정보).
- 클라의 합법 수 · 미리보기는 걸러진 상태로 계산하거나 호스트에 묻는다.

**장점**
- 은닉 정보와 정보 치트 방지 — PvP 가 된다.
- 클라 결정론이 필요 없다. 불일치가 구조적으로 없다.

**단점**
- 상태 델타(테이블 단위 차분) · 가시성 필터 · 질의 경로가 전부 새 코드다(大). 지금 이벤트는 연출용이라 상태를 재구성할 정보가 없다.
- 걸러진 상태로는 `EnumerateLegal` 이 틀릴 수 있다(숨은 카드가 조건인 규칙).
- 클라 조작이 매번 왕복을 기다린다.

### 방안 C. A + 비공개 영역만 호스트 보유

**3줄 요약**
- 기본은 A. 비공개 영역(상대 손패 · 덱)만 호스트가 쥐고, 플레이어별로 걸러 보낸다.
- 비공개 데이터에 닿는 명령은 호스트에서만 실행하고 결과를 보낸다.
- A 와 B 사이의 경계 규칙 설계다.

**장점**
- 협동은 A 와 같고, 비공개 정보가 있는 규칙도 받을 수 있다.

**단점**
- 클라 상태 ≠ 호스트 상태가 되어 전체 체크섬 검증이 깨진다. 세 방안 중 가장 복잡하다.

참고: boardgame.io 가 A → C 모양이다 — 무브는 기본으로 클라 · 서버 양쪽에서 실행, 비밀 상태는 `playerView` 로 플레이어별 제거, 비밀에 닿는 무브는 `client: false` 로 서버 전용. BG3 는 B 쪽(컴포넌트 복제 레지스트리, `턴제_보드_카드게임_프레임워크_방향성_2026-09-28.md` §2).

### 비교

| | **A 명령 중계** | B 상태 복제 | C 혼합 |
|---|---|---|---|
| 새 코드 양 | **小~中** | 大 | 大 |
| 대역폭 | **최소** | 중 | 소~중 |

**권장: A.** 목표 장르가 협동이라 A 의 유일한 약점(은닉 정보)이 문제가 되지 않고, 새 코드가 가장 적다.

## 2. 구조 (방안 A)

```
게임 모듈        규칙(핸들러 · 효과 · 트리거) · 큐 · 엔트리 액터 · 로비 UI
──────────────────────────────────────────────────────────────────────────
GameFrameWorks
 Actors/         JGGameplayControllerActor ─ 로컬 입력 ─▶ JGGameMasterActor (입력 정책 · 큐 재생)
                                                           │ SubmitLocal        ▲ 이벤트 (관찰자 — 지금 그대로)
 Network/ (신규)  PGameplaySession   넷 모드 · 슬롯 · 소유 검사 · 명령 줄 · 체크섬 · 입장/재동기
                 INetTransport      메시지 단위 · 신뢰 · 순서 보장 — PNetTcpTransport (Winsock) · PNetLoopbackTransport (테스트)
                                                           │ Submit             │
 GameMaster/     PGameMaster (거의 그대로. 문서 Import/Export · 규칙 지문 추가)
```

명령 한 개:

```
[클라 B]  입력 → Controller.Commit → GameMasterActor (입력 정책) → Session.SubmitLocal
          → CommandRequest{clientSeq, 명령} ─────▶ [호스트] Session 폴링
                                                  ① 소유: 보낸 슬롯이 명령 행동자의 조작 주체인가 (ResolveChoice 는 Chooser)
                                                  ② 규칙: PGameMaster.Submit (Validate 포함)
                                                  ③ Executed · PendingChoice → CommandAccepted{seq, slot, clientSeq, 명령, 체크섬} 전원
                                                     Rejected → CommandRejected{clientSeq, 사유} B 에게만
[전원]    Accepted 수신 → 복제 PGameMaster.Submit(명령) → 체크섬 비교 → 이벤트 → GameMasterActor 가 큐 재생
[호스트]  로컬 입력 · AI 명령도 ①~③ 같은 줄. 네트워크만 건너뛴다
```

넷 모드: `Standalone`(지금 동작 — 네트워크 없는 호스트) · `ListenServer`(권한 + 로컬 플레이어) · `Client`(복제).

**결정론 추가 규칙 (A 의 전제)**
- 규칙 코드는 상태 + 명령 외 입력(시계 · 로컬 설정 · 연출 상태)을 읽지 않는다. 부동소수 금지(기존 규칙).
- 컴포넌트 필드는 전부 기본값 초기화. 미초기화 값도 JSON 에 실려 기계마다 체크섬이 달라진다. 디버그 빌드는 채움 패턴(풀 0xCD 등) 때문에 같아 보일 수 있어 릴리스에서야 드러난다.
- `PName` ID 는 문자열 내용 해시(`std::hash`, `String.cpp:433` → `StringTable.cpp:32`)라 같은 빌드면 프로세스 간 같다. 이름 인터닝 순서는 위험 요소가 아니다.
- 한 프로세스 테스트는 전역 상태(문자열 테이블 · 리플렉션 클래스 목록 · 정적 변수)를 공유해 프로세스 간 차이를 가린다. 2 프로세스 테스트를 따로 둔다(§6 단계 4).

## 4. 만들 것

### GameFrameWorks/Network/ (신규 폴더, 헤드리스 — Core · GameMaster/ 만 포함)

| 타입 (가칭) | 역할 | 크기 |
|---|---|---|
| `INetTransport` | `Host(port)` · `Connect(addr)` · `Send(peer, bytes)` · `Poll(out events)` · `Close(peer)`. 이벤트 = 연결 · 끊김 · 메시지 | 小 |
| `PNetTcpTransport` | Winsock 비블로킹 TCP, `uint32` 길이 접두 프레이밍, 최대 크기 검사, `TCP_NODELAY`(작은 메시지 지연 제거), 핑 · 타임아웃 | 中 |
| `PNetLoopbackTransport` | 한 프로세스 안 호스트 · 클라 쌍(단계 2 · 3 테스트용). 지연 · 끊김 주입 | 小 |
| `EGameplayNetMode` · `HGameplayPlayerSlot` | 넷 모드 3개. 슬롯 = 번호 · 조작 주체 번호 · 피어 · 이름 · 재접속 토큰(GUID) · 접속 여부 | 小 |
| 메시지 | `Hello` · `Welcome`(문서) · `Refuse` · `CommandRequest` · `CommandAccepted` · `CommandRejected` · `ResyncRequest` · `Document` · `StartGame` · `Travel` · `Ping`. 페이로드 JSON(`IJsonable`), 문서만 zlib | 中 |
| `PGameplaySession` | 넷 모드, 슬롯 표, 소유 검사, 명령 줄, 방송, 체크섬 비교, 입장 · 재접속 · 재동기, 끊김 알림, 호스트 AI 구동, 폴링 | 中~大 |

**빌드 주의 (검증함).** PCH 가 `WIN32_LEAN_AND_MEAN` 없이 `Windows.h` 를 들여와(`PCH.h:27` `d3d12.h` · `PCH.h:43` `Rpc.h` · `PlatformDefines.h:7`) 구버전 `winsock.h` 가 먼저 들어간다. 그 뒤에 `winsock2.h` 를 넣으면 **오류 102건**(C2011 `sockaddr` 재정의 …). `winsock2.h` · `ws2tcpip.h` 를 `PCH.h` 맨 앞(`d3d12.h` 보다 먼저)에 두고 `#pragma comment(lib, "ws2_32.lib")` 를 붙이면 빌드 · `WSAStartup` 성공. 공유 PCH 변경이라 전체 재빌드가 필요하고 다른 세션과 조율해야 한다.

## 5. 선행 조건 — 리뷰 항목이 네트워크에서 드러나는 모습

| 항목 | 네트워크에서의 증상 | 시점 |
|---|---|---|
| C7 `Load` 가 `Finalize` 를 안 부름 (R7, `GameMaster.cpp:275`) | 문서로 입장한 클라의 트리거 순서가 호스트와 달라 첫 명령부터 체크섬 불일치 | 세션 전 |
| C1 죽은 ID 쓰기 (R1–R3) | 원격 명령은 오래된 상태를 보고 만들어져 죽은 ID 가 흔하다 → 재사용된 인덱스의 새 엔티티를 덮음 | 세션 전 |
| D10 규칙 지문 없음 | 다른 빌드끼리 접속해도 모른다 | 핸드셰이크 |
| **동시 행동 (새 결정)** | 커널은 행동자 하나(`GameplayTurnState.h:11` `CurrentActor`), 선택자 하나(`GameplayChoice.h:10` `Chooser`)만 안다. 협동의 "같은 편 동시 행동", "전원 동시 선택"(예: 글룸헤이븐 라운드 시작 카드 선택)을 표현할 수 없다. 줄 세우기는 세션이 하므로 커널은 "행동 가능 집합"과 "다중 선택자"만 알면 된다. 라운드 시작 선택은 리뷰 D1(페이즈 큐화)이 먼저 | 게임 레이어 전 |

## 6. 순서

| 단계 | 내용 | 합격 기준 |
|---|---|---|
| 0 | C7 · C1 수정, `PGameMaster` 문서 Import/Export · 규칙 지문, 에이전트 러너 분리 | `gmtest` 75/75 유지, 문서 왕복 후 체크섬 동일 |
| 1 | 전송(루프백 → TCP), PCH Winsock 순서 | 루프백 · 2 프로세스 TCP 에코, 1 MB 메시지 왕복, 끊김 검출 |
| 2 | `PGameplaySession` 3 모드, 핸드셰이크 · 시작 · 명령 중계 · 체크섬 | 한 프로세스 호스트 1 + 클라 3, 슬롯마다 무작위 에이전트로 1,000 명령 → 모든 순번 체크섬 동일. 남의 행동자 명령 · 지문 다른 클라 거부. 명령당 체크섬 비용 측정 |
| 3 | 입장 · 재접속 · 재동기, 끊김 알림 | 500 명령 시점 입장 → 이후 체크섬 동일. 상태를 고의로 바꾼 클라 → 검출 · 덤프 · 복구 |
| 4 | 2 프로세스 결정론 (`JGConsole nethost` / `netjoin`) | 프로세스 3개 1,000 명령 체크섬 동일 |
| 5 | 월드 연결: 세션 소유 · GameMasterActor 경유 · 컨트롤러 소유 검사 · 런처 인자 · 최소 로비(ImGui) | 런처 2개(호스트 · 클라)로 한 전투 완주 |
| 6 | 동시 행동 커널 확장 (결정 4 가 "확장"일 때) | 2 명 동시 행동 · 동시 선택 시나리오 체크섬 동일 |

테스트는 세션 폴링을 직접 부른다(JGConsole 은 스케줄러를 돌리지 않는다). 한 프로세스에서 시나리오를 여러 개 돌리면 사이에 `GMemoryGlobalSystem::Flush()`.
