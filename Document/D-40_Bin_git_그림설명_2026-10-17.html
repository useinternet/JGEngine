D-40 그림으로 보기 — 빌드 결과(Bin)를 공개 git 저장소에 계속 넣을지

2026-10-17 엔진 총괄 · 커밋 · 푸시를 엔진 총괄이 묶어서 하게 되면서(보고함 H-001) 처음 쌓인 변경을 나누다 생긴 결정

한 줄로: 엔진을 빌드하면 나오는 실행 파일 · DLL · 라이브러리(Bin/DevelopEngine)를 지금까지 git 에 같이 넣어 왔습니다. 이번에 바뀐 Bin 은 126MB이고, 그중 Core.lib 하나가 56MB라 새 커밋 검사기(50MB 한도)에 걸립니다. 권고는 ② Bin 은 git 에서 빼고 소스에서 빌드입니다. 급하지 않습니다 — 답이 올 때까지 Bin 은 넣지 않고 소스 · 문서만 먼저 넣습니다.

1지금 생기는 일

빌드할 때마다 Bin 의 큰 파일들이 통째로 바뀝니다. git 은 바뀐 파일을 통째로 새로 저장하므로, 넣을 때마다 저장소 기록이 그만큼 커지고 지워지지 않습니다. 저장소는 공개라 누구나 받아 갑니다.

2고를 것 — Bin 을 어떻게

선택지좋은 점대가일
① 계속 넣기(하루 한 번)저장소만 받으면 바로 실행넣을 때마다 ~126MB 가 기록에 쌓여 한 달이면 몇 GB. Core.lib 가 100MB 를 넘으면 푸시 거부. 빌드 결과도 공개바로(검사기 예외 한 줄)
② 빼고 소스에서 빌드 권고저장소가 더 안 커지고, 큰 파일 · 100MB 걱정이 없음. 커밋이 소스 · 문서만이라 무엇이 바뀌었는지 보기 쉬움다른 PC 에서 받으면 먼저 빌드(약 1분). 2026-10-01 까지 올라간 옛 Bin 은 기록에 남음(지우려면 기록 다시 쓰기 — 하지 않음)바로(git rm --cached + 무시 목록, 이 PC 파일은 그대로)
③ Git LFS 로 넣기본체는 작고 받으면 바로 실행GitHub 무료 LFS 는 저장 · 전송 각 1GB/월 — Bin 을 몇 번 넣으면 넘어 비용. LFS 설치 · 설정반나절

3권고와 까닭

② 빼고 소스에서 빌드. 혼자 개발하고 PC 가 하나라 받자마자 실행할 일이 거의 없고, 엔진 전체 빌드는 약 1분입니다. 반면 Bin 을 넣으면 공개 저장소가 빠르게 커지고 Core.lib 하나 때문에 언젠가 푸시가 막힙니다.

고르지 않아도 정해 둔 것: 이번 첫 묶음(소스 · 문서 8 커밋)에는 Bin 을 넣지 않습니다. ① 이나 ③ 을 고르시면 그 방식으로 Bin 을 따로 한 커밋 넣습니다. 지금 이 PC 의 Bin 파일은 어느 쪽이든 그대로 남습니다.
