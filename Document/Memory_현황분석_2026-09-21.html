메모리 시스템 현황

메모리 풀은 "고정 크기 클래스 × 고정 개수" 구조라 한 클래스가 차면 nullptr을 돌려주고, 그 자리의 assert는 절대 발동하지 않습니다. 오늘 11:57에 끝난 실행 로그가 정확히 그 상태(32바이트 클래스 4096/4096)에서 끊겼습니다. 채운 것은 PSO 캐시의 프레임당 3개 누수였고 이건 병렬 세션이 고치는 중이지만, 풀·GC·스마트 포인터 쪽 취약점은 그대로입니다. 이 문서는 개선 작업에 앞서 구조와 실측, 문제점, 손댈 순서를 정리합니다.

요약

  • P0크래시
    풀 고갈은 무음 크래시로 나타난다. 크기 클래스가 다 차면 nullptr을 돌려주는데 JG_ASSERT("no memory space left.")는 문자열 리터럴 검사라 발동하지 않고, GMemoryGlobalSystem::Allocate도 HAllocator::allocate도 결과를 검사하지 않는다. 크래시 위치는 풀이 아니라 호출자의 placement new·vector 쓰기이고 원인을 알려주는 출력이 없다. 1 MB 초과 요청은 out_of_range로 죽는다. 코드로그
  • P0누수 원인
    32 B 클래스를 채운 것은 PSO 캐시 노드 누수다. D3D12_GRAPHICS_PIPELINE_STATE_DESC의 패딩 바이트까지 해시해 프레임마다 새 PSO를 만들고 캐시에 넣었다(프레임당 3개). 병렬 세션이 PipelineState.cpp에서 내용 기반 해시로 고치는 중이고(12:30 수정, 미커밋), 수정 후 실행 로그에서 PSO 생성 2회·누수 소멸을 확인했다. 풀 쪽 취약점은 그대로 남아 있다. 코드로그
  • P0의미론
    PSharedPtr/PWeakPtr 대입이 표준과 다르다. p = nullptr, p = 빈포인터, p = std::move(빈포인터)는 아무 일도 하지 않고, p = p는 참조를 잃는다. 스마트 포인터 멤버에 = nullptr을 대입하는 곳이 28곳이며 HJGGraphicsModule::ShutdownModule의 _graphicsAPI = nullptr도 해제되지 않는다. 재현코드
  • P1GC 구조
    GC는 FIFO 큐를 매 프레임 두 번 순회하며 살아 있는 객체를 다시 넣는다. 파괴 순서가 할당 순서(부모 먼저)라 2026-09-17 종료 크래시의 구조적 원인이 남아 있고, 참조 카운터가 별도 힙 객체라 WeakCount를 무시하고 해제한다(TODO 5-18). GC는 프레임 시작, 펜스 대기 전에 돌아 GPU 리소스 파괴가 GPU 완료와 무관하다. 코드
  • P1용량
    예약 대비 사용률이 0.5%다. 스레드별 청크 100.69 MB 두 개가 잡히는데 메인 청크의 피크 페이로드는 548 KB, 워커 청크는 5.5 MB다. 반대로 32 B 클래스는 정상 실행에서도 275개를 상시 쓰고, 누수가 있으면 4,096개를 넘긴다. 크기 클래스 개수 표가 실측 분포와 맞지 않는다. 로그
  • P1관측
    풀 할당·해제마다 Info 로그를 쓰고 매 줄 flush한다. 로그 469,347줄 중 469,222줄(99.97%)이 [Memory]이고 한 프레임에 풀 연산 345회가 돈다(16 B 할당 85회는 대부분 MSVC 디버그 이터레이터 프록시). 성능 측정과 로그 판독을 모두 방해한다. 로그코드

할당 경로

HMemoryChunk::Allocate(MemoryPool.cpp:78-116)와 GMemoryGlobalSystem::Allocate(Memory.h:565-600)의 실제 동작 순서입니다.

  1. HMath::AlignPowerOfTwo(size) → 올림 2의 제곱, 최소 41 << Log2(value)가 int 시프트라 1 GB 이상에서 넘치지만 현 한도 안에서는 무관합니다.
  2. HasSpace() → MemoryQueues.at(class) ✕1 MB 초과 = out_of_range_1_GB(실제 값 2 MB) 열거자는 있지만 큐가 없어 1 MB를 넘는 요청은 모두 예외로 죽습니다(종료 코드 3, 로그 없음). 기존 기록(5-23)의 "2 MB 한도"는 정확히는 1 MB입니다.
  3. 클래스가 비었으면 JG_ASSERT("no memory space left.") → return nullptr ✕assert 무효assert(문자열)이라 항상 참입니다. GMemoryGlobalSystem::Allocate는 검사 없이 new(MemPtr) T(...), HAllocator::allocate는 그대로 반환해 std::vector가 널에 씁니다. 크래시 위치는 풀이 아니라 호출자이고 원인을 알려주는 출력이 없습니다.
  4. Deallocate의 이중 해제 검사 = JG_ASSERT(true) !무효상태가 Allocated가 아니어도 그대로 큐에 되돌립니다.
  5. 성공하면 JG_LOG(Memory, Info, ...)포맷이 %u(uint64 ID)·%x(포인터)라 ID와 주소가 32비트로 절단돼 찍힙니다. 이 한 줄이 매 할당·해제마다 파일·콘솔 두 싱크에 flush됩니다.

GC 객체 수명

Memory.cpp의 garbageCollection/garbageCollectionInternal 기준입니다.

  • 비용
    객체 하나에 힙 할당 4번, 전역 재귀 뮤텍스 1회. 풀 블록 + HMemoryBlock(맵 노드, atomic 2개 → CRT 힙 3회) + 큐 push.
  • 순회
    참조 0이 되어도 즉시 파괴하지 않는다. Update() → garbageCollection(1) → garbageCollectionInternal(10240) 2회. 각 회차가 큐에서 최대 10,241개를 꺼내 RefCount==0이면 Destruction()→~IMemoryObject()→풀 반납→맵 erase, 아니면 다시 push. 살아 있는 객체 전부가 매 프레임 두 번 큐를 돕니다(객체 수에 선형).
  • 타이밍
    GC가 펜스 대기 전에 실행된다. GMemoryGlobalSystem은 시스템 목록 2번째라 GCoreSystem::Update 맨 앞, 스케줄러가 GraphicsBegin(PCommandQueue::Begin의 펜스 대기)을 돌리기 전에 돕니다. 프레임 N에 참조를 끊은 텍스처는 N+1 시작에 ComPtr이 풀리는데 그때 GPU는 아직 N을 실행 중일 수 있습니다. 지금은 DevScene 리소스가 장수해서 드러나지 않습니다.
  • 순서
    파괴 순서 = 큐 순서 = 할당 순서. 부팅 초기 객체(API, 큐, 할당자)가 그것을 쓰는 텍스처보다 먼저 죽습니다. 2026-09-17 크래시는 캐시 무효화 + null 가드로 무해화했을 뿐 구조는 그대로입니다(기존 P3).
  • 약참조
    WeakCount를 보지 않고 해제한다. 블록 erase로 unique_ptr<atomic> 두 개가 해제된 뒤에도 PWeakPtr::IsValid()가 _pRefCount->load()를 읽습니다(TODO 5-18). 풀이 같은 주소를 재발급하면 Wrap(ptr)이 다른 객체를 돌려줄 수 있습니다(ABA).
  • 조회
    Wrap<T>(ptr)은 전역 뮤텍스 + 해시 조회. PWeakPtr::Pin(), SharedWrap(this), HTaskHandle, 델리게이트 CreateSP 등 27곳이 매번 이 경로를 탑니다.
  • 검사
    Allocate<T>의 IMemoryObject 검사는 런타임 assert. 릴리스 구성에서는 통과하고 GC가 (IMemoryObject*)ptr로 가상 소멸자를 부르는 순간 UB가 됩니다. Wrap은 이미 static_assert입니다.

종료 순서

GCoreSystem::Destroy()(CoreSystem.cpp:81-122)와 GModuleGlobalSystem::Destroy()(Module.cpp:228-268). 빨간 점이 강제 파괴가 일어나는 지점입니다.

  1. 1
    시스템 Destroy() 역순. 모듈 시스템이 _moduleOrder 역순으로 ShutdownModule → Flush.
  2. 2
    GMemoryGlobalSystem::Flush() 참조 0인 객체를 반복 스윕으로 정리.
  3. 3 ~ 7
    UnRegister StringTable → Object → Module → Schedule → Timer. 스케줄러 삭제 시점에 PThread 28개의 참조가 풀립니다.
  4. 8
    UnRegister Memory → 소멸자에서 forceFlush. 참조가 남아 있어도 강제 파괴(bForce). 이때 살아 있는 대표 객체는 PThread 28개, PTimer, PSequentialIDGenerator, PWindowsJWindow. 이 소멸자들이 이미 사라진 GStringTable/GObjectGlobalSystem을 GetInstance()로 부르면 *nullptr입니다(지금은 안 부르지만 보장 장치가 없음). 강제 파괴 뒤 남은 PSharedPtr 소멸자는 해제된 카운터를 감소시킵니다.
  5. 9 ~ 10
    UnRegister Log → DLL 언로드. 엔진 컨테이너를 static 저장소에 두면 안 되는 규칙(TODO 설계 규칙, 5-17)도 같은 뿌리입니다.

문자열 · 통계 도구

문자열 (String/, 풀 밖)

  • PString은 std::string(CRT 힙)을 들고 해시 _stringCode만 계산합니다. 풀을 쓰지 않습니다.
  • PName은 GStringTable에 등록하고 std::weak_ptr<atomic_int>로 참조를 셉니다. 복사·소멸마다 lock()(원자 연산 2회) + fetch_add/sub. _DEBUG에서는 문자열 사본도 들어 약 72 B.
  • removeOldStringInfos는 매 프레임 큐에서 1개를 꺼내 검사만 하고 다시 넣지 않습니다. 참조 0이어도 FrameCount >= INT32_MAX 조건이라 못 지우고, 큐가 비면 이후 문자열은 검사 대상도 아닙니다. 사실상 영구 인터닝인데 정리 코드가 남아 의도가 불명확합니다.
  • HStringInfo는 narrow/wide 두 사본을 듭니다(노드 128 B 클래스).

통계 도구 (DevStatistics/MemoryStatistics.cpp)

  • HMemoryPool::GetStatInfo가 청크 100 MB를 30,768블록 단위로 전부 걷고 블록마다 std::map<…, std::vector>에 push합니다. 위젯이 열려 있는 동안 매 프레임 이 비용을 냅니다.
  • 출력은 스레드별 헤더/사용/빈 비율 막대뿐이고, 루프 안에서 MemoryChunkStateInfos[0]을 참조해 모든 그룹이 메인 스레드 값을 보입니다(MemoryStatistics.cpp:59-61).
  • 클래스별 사용률·피크·실패 횟수가 없어 이번 32 B 고갈은 이 도구로 볼 수 없었습니다.

개선 방향 제안

결정은 사용자 몫이고, 여기서는 의존 관계와 효과 기준으로 순서를 제안합니다. A는 작고 독립적이어서 바로 가능하고, B·C는 구조 변경입니다.

단계 A

안전장치

작고 독립적 · 즉시 가능
  1. 풀 실패를 실패로. HasSpace 실패·1 MB 초과 시 요청 크기·클래스·스레드를 Critical 로그로 남기고 (a) 시스템 힙 폴백(헤더 표식) 또는 (b) 즉시 abort. JG_ASSERT(문자열) 두 곳 수정. nullptr 처리. (5-23 흡수)
  2. 스마트 포인터 대입 수정. 빈 rhs 대입 = Reset(), operator=(nullptr_t) 추가, 자기 대입 가드, 이동 후 rhs 비움. = nullptr 28곳 확인.
  3. 할당 로그 분리. 컴파일 스위치(예 JG_MEMORY_TRACE) 아래로, 기본 꺼짐. flush_on은 warn 이상. 포맷 %llu/%p.
  4. 통계 도구 보수. 인덱스 버그, 클래스별 live/피크/한도/실패 카운터(O(1) 증감), 청크 워크 제거.
단계 B

GC · 스마트 포인터 구조

A 이후 · 5-18 해결
  1. 제어 블록 통합. RefCount/WeakCount/플래그를 풀 헤더(또는 객체 앞 고정 오프셋)에 두고 AllocatedMemoryBlocks·큐·unique_ptr 2개를 없앤다. Wrap이 O(1)·무락이 되고, 객체 파괴(Ref 0)와 메모리 반납(Weak 0)이 분리된다.
  2. 파괴 정책. 참조 0이 되는 순간 지연 파괴 목록에 넣고(순회 제거), 파괴는 프레임 경계에서 N프레임 지연 또는 GPU 펜스 기준. 순서는 등록 역순(LIFO)을 기본으로 → P3 해소.
  3. 종료 규약. forceFlush 시점 생존 객체를 로그로 열거(누수 리포트), 시스템 삭제 순서를 GC 이후로 옮기거나 소멸자에서 시스템 접근 금지 검사.
단계 C

풀 재설계

실측에 맞춘 용량
  1. 성장형 클래스. 고정 개수 대신 페이지(64 KB~1 MB) 단위로 필요할 때 늘린다. 초기 예약은 실측(피크 6,270블록·548 KB)에 맞춰 수 MB로. 대형 블록(64 KB 이상)은 시스템 힙 직접.
  2. 스레드 간 해제. 타 스레드 해제는 소유 청크의 반납 큐(락 또는 lock-free)에 넣고 소유 스레드 Allocate가 회수. hash<thread::id> 충돌 대비.
  3. 정렬 · HAllocator 완성. alignof(T) 반영, operator==/!=, is_always_equal, 종료 후 deallocate 정책.
  4. 값 타입에서 IMemoryObject 분리 검토. PString/PName/PSharedPtr의 vptr 제거 또는 GC 대상 표식을 별도 태그로.
단계 D

관측

회귀 방지
  1. 프레임별 클래스 live 델타 리포트(이번 32 B 누수 같은 "프레임당 +k" 자동 감지).
  2. 선택적 콜사이트 태깅(파일/행), 시작·종료 스냅샷 비교.
  3. 로그 기반 리플레이는 Document/Memory/tools/memlog_stats.sh로 지금도 가능.
